Chapter 3 — Spring REST

Chapter 3 puts the tennis-club Member on the web and then refines one detail per module: twenty-three web recipes plus a shared model, all built on the same in-memory MemberService. The first half is a migration from view beans to message converters — content negotiation, produces, @RequestBody, @Valid and ProblemDetail error bodies. Recipe 3.4 ships three blocking RestTemplate clients, and 3.6 finishes with chunked, asynchronous responses.

Mental model

Chapter map and module index

Every web module in this chapter is the same application. recipe_3_shared supplies the whole model layer — Member, Members, MemberService and the @Service-annotated InMemoryMemberService (three seeded members, an AtomicLong key generator, no persistence) — and each recipe_N_M_x module adds only a RestMemberController and a CourtRestConfiguration. Read it as a diff: put two variants side by side and find the single annotation, bean or return type that differs.

Two mechanisms compete through the first half of the chapter. A handler that returns a String view name lets a View write the response (3.1.i, 3.2.i, 3.2.ii and all of 3.5). A handler whose return value is the resource — through @ResponseBody, @RestController or ResponseEntity — lets an HttpMessageConverter write the response, and no view is resolved at all. The run from 3.1.i to 3.1.iii is exactly that migration.

Reading the progression. Inside a box, each arrow is a one-line diff. 3_1_i hands a view name to DispatcherServlet; 3_1_ii changes the return type to Members and adds @ResponseBody, which is why BeanNameViewResolver, MarshallingView and Jaxb2Marshaller all vanish from CourtRestConfiguration from that module onwards. 3_1_iv through 3_1_vi is purely the missing-resource case: a raw Member return type cannot express 404, ResponseEntity.notFound().build() can, and ResponseEntity.of is the shorthand for mapping an Optional onto exactly those two outcomes. (3_2_iii is the near-miss: its orElse(null) returns a null ResponseEntity, not a null body, so there is no 404 to be found.) The two arrows leaving 3_3_iv are deliberate: 3.4 and 3.5 stand apart from the chain, while 3.6 keeps the 3.3 controller shape and replaces only its return type.

Reading the model. InMemoryMemberService is package-private and reachable only through the interface, so the controller never names it; its @PostConstruct init() is what seeds Marten Deinum, John Doe and Jane Doe at keys 1, 2 and 3. Member carries both validation (@NotBlank on name, @NotBlank and @Email on email) and JAXB (@XmlRootElement); Members adds @XmlAccessorType(FIELD) with @XmlElement(name = "member"), which is what makes the XML element singular while the Java field stays plural — a detail Jackson ignores completely. CourtRestApplicationInitializer extends AbstractAnnotationConfigDispatcherServletInitializer, returns CourtRestConfiguration from getServletConfigClasses() with a null root context, and maps the servlet at "/". There is no web.xml anywhere under ch03/.

Recipe 3.1

3.1 — Putting a resource on the web

ch03/recipe_3_1_i/src/main/java/com/apress/spring6recipes/court/web/RestMemberController.java is the starting point: a @Controller with one @GetMapping("/members") method that takes a Model, puts a Members object into it under the attribute name members, and returns the String "membertemplate". The XML comes from CourtRestConfiguration, which declares three beans — a MarshallingView named exactly membertemplate, a Jaxb2Marshaller bound to Member.class and Members.class with JAXB_FORMATTED_OUTPUT, and a BeanNameViewResolver. The view name is a bean-name lookup, not a template path; that is the whole trick, and it is why no JSP or template file exists in the module.

3_1_ii deletes all three beans: the method returns Members and is annotated @ResponseBody, so the body is written by a converter chosen per request. 3_1_iii moves the same semantics onto the type with @RestController. 3_1_iv onward add the single-resource endpoint and then the status handling.

Reading the exchange. The first six hops are identical in all six variants: DispatcherServlet asks the RequestMappingHandlerMapping installed by @EnableWebMvc for a handler, and Model is filled in by a HandlerMethodArgumentResolver before the method runs. The split is at the return value. A String is a view name, so DispatcherServlet walks its ViewResolver beans — BeanNameViewResolver participates because CourtRestConfiguration declares one — and hands the whole model to MarshallingView, which calls Jaxb2Marshaller.marshal on the members attribute. A @ResponseBody return value never reaches view resolution: RequestResponseBodyMethodProcessor writes it through a converter instead. Keep the consequence in mind for 3.2: the view mechanism serialises the model map, the converter mechanism serialises the return value.

Two shipped defects to know before you run these

recipe_3_1_v and recipe_3_1_vi declare @ComponentScan(basePackages = "com.apress.springrecipes.court") — springrecipes, not spring6recipes. No such package exists in the chapter, so no controller is registered and /members answers 404. Every other module scans com.apress.spring6recipes.court.

Separately, recipe_3_1_v, recipe_3_1_vi and recipe_3_2_i each carry a second initializer in com.apress.spring6recipes.reactive.court.web whose import of reactive.court.web.config.CourtRestConfiguration has no matching source file in that module (only 3_2_iv and 3_2_v contain it). These are leftovers copied from the reactive chapter; the court.web initializer is the live one.

Recipe 3.2

3.2 — Choosing the representation

Recipe 3.2 asks "how do I offer JSON and XML from one endpoint?" and answers it three different ways.

  • 3.2.i — views. jsonmembertemplate is a MappingJackson2JsonView bean with setPrettyPrint(true), and the handler returns that name.
  • 3.2.ii — produces plus views. Two view beans (xmlmembertemplate as a MarshallingView, jsonmembertemplate as a MappingJackson2JsonView) and two handler methods for the same path, separated only by @GetMapping(value = "/members", produces = MediaType.APPLICATION_XML_VALUE) versus APPLICATION_JSON_VALUE. Both delegate to one prepareModel(Model) helper, so the only difference is the returned name.
  • 3.2.iii to 3.2.v — converters only. No view beans at all. One method, one return type, and the media type is settled by the converter list against the Accept header. Because Members is @XmlRootElement, Accept: application/xml yields XML with no configuration whatsoever.

Swapping the JSON library. ch03/build.gradle adds com.google.code.gson:gson to recipe_3_2_iv and recipe_3_2_v and nowhere else — and those modules declare no converter bean at all. Placing Gson on the classpath is the configuration: WebMvcConfigurationSupport.addDefaultHttpMessageConverters probes the classpath and appends GsonHttpMessageConverter. Note the honest consequence: it is appended after MappingJackson2HttpMessageConverter, so unless Jackson is removed from the list the JSON you see still comes from Jackson. That is the real difference between "Gson is available" and "Gson is used".

Reading the decision. The upper branch is view-driven and the lower is converter-driven; only one can fire for a given handler. Watch the JSON view first: MappingJackson2JsonView serialises the model map, so model.addAttribute("members", members) in 3_2_i produces a JSON object whose members property is the Members bean, which itself has a members array — one key too deep. Recipe 3.5 repairs exactly this with setModelKey("feedContent"). On the converter branch, produces in 3_2_ii is evaluated by RequestMappingInfoHandlerMapping before the method is chosen — it is a mapping condition, not a rendering hint — which is how two methods can own one path. If the client's Accept matches neither, no candidate handler survives and you get 406 rather than a fallback representation.

Recipe 3.3 i–ii

3.3 — Accepting a request body

From recipe_3_3_i the controller gains class-level @RequestMapping("/members"), so method annotations carry relative paths: @GetMapping with no value maps GET /members, and @GetMapping("/{memberid}") maps the single resource. Writing arrives as newMember(@RequestBody Member newMember) returning ResponseEntity.ok(memberService.save(newMember)); 3_3_ii changes that signature by one token, @Valid @RequestBody.

There is no @PutMapping, @DeleteMapping or @PatchMapping anywhere in ch03/, and no Location header is ever set: InMemoryMemberService.save calls sequence.getAndIncrement() unconditionally, so POST is create-only and answers 200, not 201.

Walking the hops. The client sends the body and its Content-Type; RequestMappingHandlerMapping matches the class-level @RequestMapping("/members") concatenated with the empty @PostMapping path. RequestResponseBodyMethodProcessor — a HandlerMethodArgumentResolver registered by @EnableWebMvc — asks the converters to read the stream; a media type no converter supports fails here with 415, before any user code runs. @Valid is honoured in the same resolver (from 3_3_ii), not in the controller body, because @EnableWebMvc wires an OptionalValidatorFactoryBean when a Jakarta Validation provider is present — here hibernate-validator, declared runtimeOnly in ch03/build.gradle. On the happy path save stores the instance under the next AtomicLong value and returns the same object; since Member has no id field, the assigned key is invisible to the client — the reason this chapter never demonstrates reading back what you just posted by URI.

Recipe 3.3 iii–iv

3.3.3 and 3.3.4 — Turning failures into responses

recipe_3_3_iii keeps error handling inside the controller:

@ExceptionHandler
@ResponseStatus(HttpStatus.BAD_REQUEST)
public Map<String, String> handle(MethodArgumentNotValidException ex) {
    return ex.getFieldErrors().stream()
        .collect(Collectors.toMap(FieldError::getField, FieldError::getDefaultMessage));
}

The return type is a Map from a @RestController, so Jackson writes it as a flat JSON object — {"name":"must not be blank","email":"must be a well formatted email address"}. It is not a ProblemDetail: no type, title or status member, and the keys come from FieldError.getField().

recipe_3_3_iv removes that method and adds CourtExceptionHandlers, a @ControllerAdvice extending ResponseEntityExceptionHandler. It overrides handleMethodArgumentNotValid(ex, headers, status, request), builds a map keyed by FieldError.getCode() (falling back to ObjectError.getObjectName() for object-level errors) with messages resolved through getMessageSource() and LocaleContextHolder.getLocale(), then performs the key move:

ex.getBody().setProperty("errors", errors);
return super.handleExceptionInternal(ex, null, headers, status, request);

Passing null as the body tells the base class to fall back to the ProblemDetail already attached to the exception — which is the very instance just mutated. So the customisation happens in place on the standard RFC 7807 payload rather than by replacing it. This class is present, unchanged, in recipe_3_6_i through recipe_3_6_iv.

Reading the failure path. The throw happens in the argument resolver, so newMember is never entered — validation is not an if statement in the controller. DispatcherServlet.processHandlerException then iterates its HandlerExceptionResolver beans, and ExceptionHandlerExceptionResolver looks first for an @ExceptionHandler declared on the handler that threw, then for one on any @ControllerAdvice bean. That lookup order is the difference between 3.3.iii and 3.3.iv: the advice is reusable across every controller in the servlet context, the local method is not. In the advice branch the status is not declared with @ResponseStatus but comes from ResponseEntityExceptionHandler itself (400 for this exception), and the payload is the framework ProblemDetail obtained through MethodArgumentNotValidException.getBody(), extended with one property instead of rebuilt. Note also that getMessageSource() is inherited from the base class and can be null here, which is why the source guards it and falls back to getDefaultMessage().

Recipe 3.4

3.4 — Calling the API from Java

The three 3.4 modules contain exactly one file each, Main.java, and no server code at all. They are plain-JVM clients pointed at a separately running server, which is why ch03/build.gradle gives recipe_3_4_* a Main-Class manifest entry. All three target http://localhost:8080/court/...: /court is the context path Tomcat derives from the WAR, because every web module in the chapter is built as court.war (war { archiveFileName = 'court.war' }).

ModuleCallResponse typeWhat it proves
3.4 i getForObject("http://localhost:8080/court/members", String.class) String Raw body through StringHttpMessageConverter; no binding, so the client needs no domain classes.
3.4 ii getForObject(uri, String.class, params) over .../members/{memberId} with Map.of("memberId", "1") String URI template expansion; the map key must match the placeholder name, no string concatenation.
3.4 iii getForObject("http://localhost:8080/court/members", Members.class) Members Binding onto the shared domain type, which only works if the server emitted a converter-written body — the double-nested JSON of the 3.2.i view does not bind.

Reading the topology. The edge labels make the point that one server satisfies all three clients: they differ only in how the response is bound, not in what they send. CourtRestApplicationInitializer is found by Tomcat's SpringServletContainerInitializer because there is no web.xml, and it registers the DispatcherServlet with CourtRestConfiguration as the servlet context configuration — there is no root context at all (getRootConfigClasses() returns null). Everything right of the arrow is in memory, so restarting the container resets the members to the three seeded rows; re-run 3.4.iii twice without a restart and you will see the list grow, which is the quickest way to observe that save never overwrites. Port 5005 is the JDWP socket enabled by the JAVA_OPTS line in ch03/Dockerfile.

Reading the client. getForObject is execute with HttpMethod.GET plus an extractor that discards the envelope; the only difference from getForEntity is that you lose status and headers. Three mechanisms sit on the path, in order: URI template expansion through RootUriTemplateHandler (which is why 3.4.ii can hand over a map instead of building the URL), the request factory (SimpleClientHttpRequestFactory from the no-arg constructor, meaning no pooling and no read timeout — a hung server blocks the client forever), and converter selection, driven by the requested response type. That last one explains the table above: String.class in 3.4.i and ii makes StringHttpMessageConverter the match and the Accept header accordingly, while Members.class in 3.4.iii asks for a JSON-capable converter and then maps onto the JAXB-annotated bean, which Jackson reads as an ordinary bean property. Nothing in this chapter uses WebClient, and RestClient does not exist in Spring 6.0.3 — blocking RestTemplate is the only client here.

Recipe 3.5

3.5 — One model, three documents

recipe_3_5_i is the chapter's proof that the view mechanism still earns its keep. It drops Member entirely and introduces TournamentContent, a record with an AtomicInteger id counter and a static of(author, date, name, link) factory. FeedController is a plain @Controller, not a REST one, with three @GetMapping methods that build a hard-coded list, store it under the fixed model key feedContent, and return a view bean name. CourtRestConfiguration supplies the three views: atomfeedtemplate is an AtomFeedView extending AbstractAtomFeedView, rssfeedtemplate an RSSFeedView extending AbstractRssFeedView (Rome 1.18.0), and jsontournamenttemplate a MappingJackson2JsonView with setModelKey("feedContent").

Reading the fan-out. Hops one to four are shared; only the returned name differs, and BeanNameViewResolver resolves it by looking up a bean with that exact name, so the correspondence between the String and the @Bean method is the entire configuration. The Rome views invert control: AbstractAtomFeedView and AbstractRssFeedView build and write the document, calling back into the two overridden methods, which read the model map and cast feedContent back to a list of TournamentContent. Both feed views derive their timestamp by sorting the publication dates and taking findFirst() — the earliest date, used as the feed's updated or lastBuildDate — and convert the LocalDate through atStartOfDay(systemDefault) because Rome still speaks java.util.Date. And observe setModelKey("feedContent") on the JSON view: it selects one model attribute to serialise, which is precisely what the 3.2.i view failed to do.

Recipe 3.6

3.6 — Streaming the response

Recipe 3.6 keeps the 3.3 controller and replaces only the return type of getRestMembers, so the response stays open while another thread produces chunks. All four modules add AsyncConfiguration, a WebMvcConfigurer whose configureAsyncSupport sets the async default timeout to five seconds and installs mvcTaskExecutor(), a ThreadPoolTaskExecutor with thread group name mvcTaskExecutor. Because @Configuration defaults to proxyBeanMethods = true, the call from configureAsyncSupport returns the same singleton the controller constructor injects as TaskExecutor — one pool doing both async dispatch and production.

  • 3_6_i returns a bare ResponseBodyEmitter; the worker sends one Member every 25 ms then complete(), with completeWithError(ex) if an IOException surfaces.
  • 3_6_ii wraps the same emitter in a ResponseEntity with HttpStatus.I_AM_A_TEAPOT and a Custom-Header — demonstrating that status and headers are committed up front, while the body keeps streaming.
  • 3_6_iii is a one-word change, new SseEmitter(), so each send is framed as a server-sent-events block; the sleep becomes 50 ms.
  • 3_6_iv keeps SseEmitter and sends SseEmitter.event().id(String.valueOf(member.hashCode())).data(member), adding a per-event id.

Reading the stream. DispatcherServlet sees a ResponseBodyEmitter return value and routes it to ResponseBodyEmitterReturnValueHandler rather than to a converter, because a single converter call cannot express "many writes over time". The handler binds the emitter to the live response, starts async processing with the AsyncTaskExecutor chosen in configureAsyncSupport, and lets the container thread go; findAll() may still be running when the handler returns. Each send serialises one Member through the same converter list as an ordinary response — which is why the switch from ResponseBodyEmitter to SseEmitter changes the framing, not the conversion. Two arithmetic facts: three seeded members at 25 or 50 ms is under 150 ms, so the five-second timeout never trips as written; and if you POST members first, the stream can exceed it and the exchange ends in an async timeout instead of completing cleanly. CourtExceptionHandlers is present unchanged in all four modules, so validation errors on POST keep producing the 3.3.iv ProblemDetail.

Practice

Building and running

Build a module

./gradlew :ch03:recipe_3_3_i:build     # compiles and packages court.war
./gradlew :ch03:build                  # the whole chapter, including recipe_3_shared

Gradle 7.6 (wrapper in the repo root) and a Java 19 toolchain. build.gradle adds --enable-preview to JavaCompile, Test and JavaExec, so anything you launch by hand needs the same flag.

Serve the WARs — the path the build ships

./gradlew :ch03:recipe_3_3_i:docker       # image s6r/court-rest:recipe_3_3_i
./gradlew :ch03:recipe_3_3_i:dockerRun    # container s6r-court-rest-recipe_3_3_i, -p 8080:8080

defaultTasks 'build', 'docker' means a bare ./gradlew :ch03:recipe_3_3_i also builds the image. One ch03/Dockerfile is shared by all modules: eclipse-temurin:19-jdk-alpine, Tomcat 10.1.4 fetched at build time, ROOT and the sample webapps deleted, court.war copied into webapps, and EXPOSE 8080 5005 with JDWP switched on. So the API lives at http://localhost:8080/court/members — /court comes from the WAR name, not from a configured context path. Docker must be running: unlike chapter 2, ch03/build.gradle applies war, com.palantir.docker and com.palantir.docker-run but no embedded-server plugin, so the alternative is copying build/libs/court.war into your own Servlet 6 container (Tomcat 10.1 or Jetty 11). There are no application.properties, JSPs, SQL scripts or credentials anywhere in ch03/ — the only data store is a HashMap.

Run the 3.4 clients

# server first, in another shell
./gradlew :ch03:recipe_3_3_i:dockerRun

./gradlew :ch03:recipe_3_4_iii:uberJar
java --enable-preview -jar ch03/recipe_3_4_iii/build/libs/recipe_3_4_iii-all.jar

recipe_3_4_* sets Main-Class in the plain jar manifest, but that jar carries no dependencies; the root build's uberJar task (classifier all) is the one that actually runs. recipe_3_4_iii needs recipe_3_shared on the classpath for Members, which the build already wires.

Prerequisites and gotchas found in the source

  • Docker is the only external dependency of the chapter (for serving); nothing needs a database or broker.
  • recipe_3_1_v and recipe_3_1_vi scan com.apress.springrecipes.court, a package that does not exist here, so /members 404s until corrected to spring6recipes.
  • recipe_3_1_v, recipe_3_1_vi and recipe_3_2_i each contain an extra initializer in com.apress.spring6recipes.reactive.court.web importing a configuration class absent from that module; even in 3_2_iv and 3_2_v, where it exists, it registers a second DispatcherServlet also mapped at "/".
  • Only 3_2_iv and 3_2_v have Gson on the classpath, so their converter list differs from 3_2_iii's although the Java sources look identical.
  • Two AbstractAnnotationConfigDispatcherServletInitializer classes in one WAR would both be picked up by Tomcat's SpringServletContainerInitializer; if a module fails to start, delete or fix the reactive one first.

Reading guide

How to use these pages

Every chapter page follows the same shape, so you can drop into any chapter cold:

  • A Module Map table listing every recipe number in the chapter, the Gradle modules implementing it, and the key classes to open first.
  • Diagrams — class, sequence, flowchart and state diagrams chosen to suit the subject, each with a Reading the flow note that walks the arrows in order and names the Spring mechanism responsible.
  • A Running section with real Gradle paths and any Docker, database or broker prerequisite the source actually requires.

Diagrams render from a vendored, self-contained copy of Mermaid 12 in docs/assets/mermaid.min.js, so these pages work offline straight from the filesystem — open docs/index.html in a browser, or serve the folder:

cd docs
python -m http.server 8080      # then browse http://localhost:8080/

Trust the code, not the picture

Each page cites the module paths its classes came from. Where a page and the source disagree, the source wins — the recipes are small and quick to open. Cross-references between chapters are deliberate: chapters 10, 11 and 12 all touch messaging and each page states where its own boundary lies.

Index

Chapter index

Reading the ladder. The arrows are teaching order, not build order — every recipe module is independent at build time. Chapter 1 sits at the root because everything else in the book is an application of the container: chapter 2 and 3 layer an HTTP dispatcher over it, chapter 5 intercepts those requests with a filter chain, chapters 6 and 7 add a persistence and transactional-proxy layer beneath them, and chapters 8 to 12 move the same bean-and-proxy model out to brokers, jobs and external systems. Chapter 13 then tests all of it and chapter 14 wraps the service beans of chapters 6 and 7 in a caching proxy.

Topology

Build topology

The multi-module build is generated rather than declared: settings.gradle walks the repository from the root and includes any directory whose name begins with recipe or appendix, pruning anything that does not match ^(ch|recipe|appendix). Adding a recipe directory therefore adds a Gradle project with no edit to settings.gradle.

Reading the topology. build.gradle in the root applies java to every subproject except spring-6-recipes-dependencies, then adds the BOM and shared-resources only to projects whose name contains recipe. The BOM is wired as enforcedPlatform, which is the load-bearing detail: it pins transitive Spring versions and refuses to let a recipe module override them, so a dependency added without a version inside a recipe resolves to the platform's version. The root build also excludes commons-logging, JUnit 4 and the vintage engine from every configuration, which is why every recipe in the book tests on the JUnit Platform.

Hands on

Prerequisites and running

  • JDK 19+ — the toolchain target is 19 and every compile, test and exec task adds --enable-preview, so preview features used in the book's code require a JVM new enough to accept that flag.
  • A Gradle daemon JDK caveat. The wrapper is gradle-7.6, which cannot run on Java 21 (Unsupported class file major version 65). gradle.properties works around this by setting org.gradle.java.home to a local JDK 17 install while the toolchain still compiles at 19. That path is machine-specific — change or remove it for your own machine before building.
  • Docker for chapters 2, 3, 4, 5 and 10, which apply com.palantir.docker and com.palantir.docker-run, and for chapter 13's Testcontainers recipes.
# Everything
./gradlew build

# One chapter's recipes
./gradlew :ch01:build

# A single recipe: compile, then run its main class
./gradlew :ch05:recipe_5_1_ii:compileJava
./gradlew :ch05:recipe_5_1_ii:build

# A web recipe that needs a servlet container (chapter 2 uses Gretty)
./gradlew :ch02:recipe_2_1_i:war

# Fat jar for a runnable recipe
./gradlew :ch01:recipe_1_1_i:uberJar

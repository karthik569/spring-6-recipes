Chapter 2 — Spring MVC

Chapter 2 builds one web application — the tennis-club Court reservation system — and changes a single mechanism per module. Twenty-two WAR modules plus recipe_2_shared walk from raw servlet bootstrapping through handler mappings, interceptors, form binding with validation, content negotiation and PDF/Excel views. It is the only chapter that ships a deployable court.war, and the build wraps it in both a Gretty embedded Tomcat and a Palantir Docker image so you can actually serve it.

Mental model

Chapter map and module index

Read Chapter 2 as a diff. recipe_2_shared supplies the entire model layer once — Reservation, Player, SportType, PeriodicReservation, the @Service InMemoryReservationService, a Spring Validator and a Converter — and every recipe_2_N_M module adds only the controllers, JSPs and @Configuration classes needed to demonstrate one Spring MVC feature. Two @Controller beans recur almost everywhere: WelcomeController bound to /welcome, and ReservationQueryController bound to /reservationQuery. From 2.8 the form-handling trio ReservationFormController / ReservationValidator / reservationForm.jsp takes over as the subject of study.

Each module applies war, org.gretty and the Palantir plugins (see ch02/build.gradle), and the non-shared modules all depend on project(":ch02:recipe_2_shared"). The output of every one of them is a WAR renamed to court.war.

The spine

The request path

Everything in the chapter hangs off one pipeline. The DispatcherServlet (registered as the servlet named court in recipe_2_1_i) receives the request, asks its RequestMappingHandlerMapping for a handler, invokes the controller method, and passes the returned view name to the configured ViewResolver. This trace uses the real collaborators from recipe_2_6_i / recipe_2_1_iii.

Reading the flow. Hop by hop: the servlet container hands the request to DispatcherServlet.doDispatch (the servlet is named court in recipe_2_1_i/src/main/java/com/apress/spring6recipes/court/web/CourtServletContainerInitializer.java). The RequestMappingHandlerMapping supplied by @EnableWebMvc matches the class-level @RequestMapping("/reservationQuery") plus the @PostMapping method sumbitForm and returns a HandlerExecutionChain. The controller delegates to InMemoryReservationService.query and drops the result into the Model under reservations, then returns the logical view name. Because no body is written, DispatcherServlet resolves that name through InternalResourceViewResolver (prefix /WEB-INF/jsp/, suffix .jsp, from ViewResolverConfiguration) into an InternalResourceView, which forwards to the JSP. The JSP runs a JSTL c:forEach over the reservations attribute and renders the table back to the browser.

Recipe 2.1

Bootstrapping the DispatcherServlet

The three recipe_2_1_* modules are the same app wired three ways, showing the move off Servlet 3.0 boilerplate onto Spring's own initializer base class. All three map the servlet and register CourtConfiguration (@Configuration @ComponentScan("com.apress.spring6recipes.court") @EnableWebMvc). The only real difference is who creates the DispatcherServlet and the set of URL patterns.

Reading the flow. Path i is the raw route: you implement ServletContainerInitializer.onStartup, build an AnnotationConfigWebApplicationContext, wrap it in a DispatcherServlet and register it yourself with ctx.addServlet("court", …). Paths ii and iii delete all of that by extending AbstractAnnotationConfigDispatcherServletInitializer: Spring's built-in SpringServletContainerInitializer discovers it, and you only override getServletConfigClasses (returning CourtConfiguration.class) and getServletMappings. The one behavioural delta between ii and iii is the mapping array — iii adds /welcome alongside /. getRootConfigClasses() returns null in all of them, so the whole context is the single servlet context.

Shared model

The Court domain and its collaborators

The whole chapter manipulates one aggregate. Reservation carries bean-validation annotations (@NotNull @Size(min = 4) on courtName, @Min(8) @Max(22) on hour, @DateTimeFormat(iso = …DATE) on date, @Valid on the nested player) that recipes 2.9 onward rely on. A Spring Validator and a Converter — both @Component beans in the shared module — are what later modules inject.

Reading the model. Reservation is a composition of a Player and a SportType — the @Valid on player cascades bean validation into Player.name/Player.phone (@NotEmpty). InMemoryReservationService is package-private and @Service-annotated, seeds two Tennis #1/Tennis #2 rows, and make() counts matching court/date/hour rows to throw ReservationNotAvailableException (a RuntimeException) — that exception is what 2.8 and 2.10 catch. SportTypeConverter turns the form's numeric sportType string back into a SportType by delegating to ReservationService.getSportType, and ReservationValidator enforces the weekday/holiday hour windows via Errors.reject.

Recipes 2.3–2.5

Handler interceptors

Interceptors wrap the controller call without touching it. A WebMvcConfigurer adds them, and path patterns scope them. Two concrete interceptors ship: MeasurementInterceptor (a StopWatch that injects a processingTime model attribute in postHandle) and ExtensionInterceptor (which sets a Content-Disposition download header based on the .pdf/.xlsx suffix). Recipe 2.4/2.5 layer a LocaleChangeInterceptor on top.

Reading the flow. InterceptorConfiguration (recipe_2_3_i/…/config/InterceptorConfiguration.java) implements WebMvcConfigurer.addInterceptors(InterceptorRegistry) and calls registry.addInterceptor(measurementInterceptor()) — no path pattern, so it applies to every mapped request. The second registration in 2.3_ii chains .addPathPatterns("/reservationSummary*") to scope ExtensionInterceptor. preHandle returning true lets the chain proceed; if it returned false the controller would be skipped. postHandle runs after the handler but before rendering, which is why MeasurementInterceptor.postHandle can still add processingTime to the ModelAndView and have it appear in the view. LocaleChangeInterceptor (2.4/2.5) is registered through I18NConfiguration.addInterceptors with paramName language, working with the CookieLocaleResolver that resolveViewName consults.

Recipes 2.8–2.9

Form binding and validation errors

The reservationForm.jsp is a Spring <form:form> bound to the reservation model attribute, with one <form:errors> tag per field. recipe_2_9_iv is the canonical case: the POST argument carries @Validated, @InitBinder installs ReservationValidator as the binder's validator, and a BindingResult parameter receives any failures. If the result has errors the controller returns the same view instead of saving.

Reading the flow. On @SessionAttributes("reservation") the form-backing object is kept in the session across the GET and POST. The GET setupForm creates a fresh Reservation (pre-filling Player from @RequestParam username in 2.9_ii onward) and adds it to the model; the @ModelAttribute("sportTypes") method (2.9_iii) feeds the select. On POST, the argument is annotated @ModelAttribute("reservation") @Validated, so Spring's WebDataBinder binds the request parameters onto the object — using the registered SportTypeConverter to turn sportType into a real SportType — then runs validation. @InitBinder in recipe_2_9_iv/…/ReservationFormController.java calls binder.setValidator(reservationValidator), so the errors come from ReservationValidator.validate, and a BindingResult immediately after the model argument captures them without throwing. result.hasErrors() being true returns "reservationForm"; only the clean branch calls reservationService.make(...) and status.setComplete() to clear the session before redirecting to reservationSuccess.

Recipes 2.8.iii, 2.10, 2.11

Failures as views

Three competing mechanisms turn a thrown exception into a rendered page, and the chapter shows their evolution: an ExceptionHandlerExceptionResolver backed by local @ExceptionHandler methods (2.8.ii), the same methods lifted into a @ControllerAdvice ExceptionHandlingAdvice (2.8.iii, 2.10), and — earlier — a SimpleMappingExceptionResolver driven by properties (2.8.i).

Reading the flow. In recipe_2_8_i the resolver comes from ErrorHandlingConfiguration: configureHandlerExceptionResolvers adds a SimpleMappingExceptionResolver whose Properties map the fully-qualified ReservationNotAvailableException name to view reservationNotAvailable, with defaultErrorView("error") for anything else. In recipe_2_8_ii the controller declares @ExceptionHandler(ReservationNotAvailableException.class) and a catch-all @ExceptionHandler locally, dispatched by Spring's built-in ExceptionHandlerExceptionResolver. From recipe_2_8_iii (and reused verbatim in 2.10) those methods move into @ControllerAdvice ExceptionHandlingAdvice, making them apply across every controller in the context. In recipe_2_11 the advice pattern is inverted for the summary page: a local @ExceptionHandler catches ServletRequestBindingException from a malformed date parameter and rethrows a ReservationWebException.

Recipes 2.7, 2.11

Content negotiation and document views

Recipe 2.7 registers media types and switches on the path extension; 2.11 uses that to serve the same model as HTML, PDF or Excel. The trick is a BeanNameViewResolver: the negotiated view name plus extension (for example reservationSummary.pdf) matches the name of a view bean, and that bean (AbstractPdfView / AbstractXlsxView) renders the document itself instead of forwarding to a JSP.

Reading the flow. recipe_2_11/…/config/ViewResolverConfiguration.java calls configureContentNegotiation to register html, pdf (MediaType.APPLICATION_PDF) and xls (application/vnd.ms-excel) with favorPathExtension(true), then configureViewResolvers enables content negotiation, registers the JSP resolver, and adds a BeanNameViewResolver. The controller returns the plain logical name reservationSummary; the request's .pdf/.xls extension determines the media type, and BeanNameViewResolver looks up a bean literally named reservationSummary.pdf or reservationSummary.xls — the two @Bean(name = …) methods returning PdfReservationSummary (extends AbstractPdfView, builds a com.lowagie.text.Table) and ExcelReservationSummary (extends AbstractXlsxView, uses Apache POI). The ExtensionInterceptor from 2.3 then decorates the response with a Content-Disposition filename.

Chapter-specific infrastructure

How the WAR is served: Gretty vs Docker

Unlike the rest of the book, Chapter 2 produces a real deployable. ch02/build.gradle applies war, renames the artifact to court.war, and gives you two ways to run it: an embedded Tomcat 10 through Gretty, or a container image through the Palantir plugins and ch02/Dockerfile (Eclipse Temurin 19 on Alpine, Tomcat 10.1.4, debug port 5005).

Reading the flow. The subprojects block in ch02/build.gradle skips the shared module and applies war, com.palantir.docker, com.palantir.docker-run and org.gretty to every other module, with defaultTasks 'build', 'docker'. The war block sets archiveFileName = 'court.war'. On the Gretty branch gretty { servletContainer = 'tomcat10'; contextPath = '/' } means tomcatRun boots an embedded Tomcat on the default port 8080 at the root context. On the Docker branch the docker block names the image s6r/court-web:$project.name (so s6r/court-web:recipe_2_11), copies the built court.war into the Dockerfile's $CATALINA_HOME/webapps/, and dockerRun starts a container s6r-court-web-$project.name mapping 8080:8080; the Dockerfile also opens JDWP on 5005 for remote debugging.

Build and run

Building and running

All commands run from the repository root against the fully-qualified Gradle project path (:ch02:<module>). Nothing needs a database or external broker — the service is the in-memory InMemoryReservationService — but serving a page needs either Gretty or Docker, because these are WARs deployed into a servlet container.

Prerequisites found in source. Docker is genuinely required if you run the default tasks or the docker/dockerRun goals — defaultTasks 'build', 'docker' is set in ch02/build.gradle and the Dockerfile downloads Tomcat at build time. If you only want a page on screen without Docker, use the Gretty tomcatRun task. recipe_2_11 and recipe_2_12 additionally pull openpdf and poi-ooxml for the document views, and validation messages come from messages.properties/messages_de.properties resolved by the ResourceBundleMessageSource in 2.5 onward.

Chapter 4 — Spring WebFlux

The servlet stack of chapters 2 and 3 is gone: every recipe here builds an HttpHandler from a Spring ApplicationContext and lets Reactor Netty (or a Servlet 6 container) serve it, with endpoints that hand back Mono and Flux instead of values. Six recipe families cover one concern each — bootstrapping, JSON endpoints, error handling, Thymeleaf views, WebClient consumption and functional router endpoints — all on a single in-memory domain: a court-club Member registry. Read the async claims with a sceptic's eye: the service layer in this chapter is synchronous, so the diagrams show where the asynchrony is (I/O, encoding, subscription) and where it only looks like it.

Chapter map

Mental model and module map

Every WebFlux app in this chapter is assembled the same way. A WebFluxConfiguration class (@Configuration + @EnableWebFlux + @ComponentScan, implementing the no-op marker WebFluxConfigurer) seeds an AnnotationConfigApplicationContext, and WebHttpHandlerBuilder.applicationContext(context).build() turns that context into a single HttpHandler. That handler is then adapted to whichever transport the recipe chooses. There is no DispatcherServlet, no web.xml, no thread-per-request pool — the equivalent of the front controller is DispatcherHandler, an internal collaborator of the built handler.

The domain example shrinks from the court reservations of chapters 2–3 to a club member registry: a Member record (name, email, phone, later a SportType preferredType) held in InMemoryMemberService inside ch04/recipe_4_shared. The old reservation model survives only in the package name com.apress.spring6recipes.reactive.court.

Ignore the compiled leftovers

ch04/recipe_4_1_i/out/production/classes/ and the bin/ directories contain stale IDE output under the older package com.apress.springrecipes.reactive.court — InMemoryReservationService, Reservation, Player, ReservationQueryController. None of those have sources anywhere in ch04/; nothing in this page is derived from them.

Reading the flow. Follow the left spine first: 4.1 produces a running server and nothing else — its only endpoint is WelcomeController.welcome, which returns Mono.just("Hello …"). From 4.2 onward each module re-declares the identical WebFluxConfiguration (sometimes with one extra override) and adds exactly one concern: configureHttpMessageCodecs in 4.2, a @ControllerAdvice bean in 4.3, three view beans and a configureViewResolvers override in 4.4. The bottom edge is the one real runtime coupling: 4.5_i has no server, it dials http://localhost:8080/ and prints whatever a 4.2-style MemberController.list sends back, so the data it shows comes from InMemoryMemberService.init in recipe_4_shared. 4.6_i is the endpoint model swapped out underneath the same service, which is why it hangs off 4.4 rather than continuing the chain.

Recipe 4.1

Bootstrap: one HttpHandler, three launchers

ch04/recipe_4_1_i/src/main/java/com/apress/spring6recipes/reactive/court/ReactorNettyBootstrap.java is the whole server: context, WebHttpHandlerBuilder, new ReactorHttpHandlerAdapter(handler), then HttpServer.create().host("0.0.0.0").port(8080).handle(adapter).bind().block() and a System.in.read() to hold main. Recipe 4.1_ii drops the bootstrap class and instead implements WebApplicationInitializer: the same builder call, but the adapter is a ServletHttpHandlerAdapter registered as servlet dispatcher-handler on mapping "/" with setAsyncSupported(true) — without that flag the servlet container would time out the non-blocking dispatch. Recipe 4.1_iii deletes even that: WebFluxInitializer extends AbstractReactiveWebInitializer and contributes only getConfigClasses() returning WebFluxConfiguration.class, because the base class already performs the context creation, the WebHttpHandlerBuilder call, the adapter creation and the servlet registration. The controller is byte-for-byte the same in all three (module i declares @RequestMapping("/welcome") on the class and @RequestParam(defaultValue = "World"); ii and iii put the path on @GetMapping("/welcome") and keep the default value).

Reading the flow. Three lanes, one shared left-hand node. In each lane the context is refreshed first, so @ComponentScan from the base package com.apress.spring6recipes.reactive.court registers WelcomeController and the WebFluxConfigurer before any request can arrive; then WebHttpHandlerBuilder walks the context for its infrastructure beans (WebFluxConfigurationSupport defaults plus any WebFluxConfigurer it finds) and produces the HttpHandler. The adapters differ only in transport: ReactorHttpHandlerAdapter plugs into HttpServer.handle(...), ServletHttpHandlerAdapter plugs into a servlet registration. Note what does not appear in the WAR lanes: bind().block() and System.in.read() are exclusive to i, since the container owns the process lifecycle there. Both WAR modules are built with the war plugin plus providedCompile jakarta.servlet-api, which is why jakarta.servlet.ServletContext compiles but is absent from the fat classpath.

Recipes 4.2–4.4 vs 4.6

Annotated endpoints vs functional endpoints

This is the chapter's central fork, and the source makes it unusually clean because the two models wrap the identical service call. The annotated form (ch04/recipe_4_2_i/src/main/java/.../web/MemberController.java) is a @RestController @RequestMapping("/members") with @GetMapping Flux<Member> list() and @PostMapping Mono<Member> create(@RequestBody Member member) — the path, the method and the status are all implicit, and the response body is whatever the returned publisher emits. The functional form (ch04/recipe_4_6_i/src/main/java/.../WebFluxConfiguration.java) declares @Bean RouterFunction<ServerResponse> membersRouter(MemberController handler) built by RouterFunctions.route().GET("/members", handler::list).POST("/members", handler::create).build(), where the handler is a bare @Component whose methods are Mono<ServerResponse> list(ServerRequest request) and create(ServerRequest request). Here the status is explicit (ServerResponse.ok()), the request body is pulled by hand with request.bodyToMono(Member.class), and the element type has to be named a second time in .body(member, Member.class) so the writer knows what the wrapped publisher carries.

Reading the flow. A request enters DispatcherHandler, which consults its registered HandlerMappings in order and stops at the first match — that is why both lanes are drawn from the same req node and why the two models can coexist: RouterFunctionMapping finds the bean, RequestMappingHandlerMapping finds the annotated controller, and neither knows about the other. In the left lane the argument resolver for @RequestBody defers the actual create(...) invocation until Jackson has produced a Member; in the right lane create(ServerRequest) runs immediately, but only to build the pipeline — request.bodyToMono(Member.class).flatMap(memberService::save) is inert until ServerResponse.ok().body(member, Member.class) is itself subscribed by the handler. That is the single most important asymmetry between the models in this chapter, and it is easy to miss: in 4.6_i the memberService.save reference is bound eagerly, while in 4.2_i save is not even called until the body arrives. 4.6_i proves the coexistence point in one file: its WebFluxConfiguration has the router bean, and @ComponentScan still drags in the annotated WelcomeController on /welcome — though that module registers no view resolver and declares no Thymeleaf dependency, so only /members is genuinely usable there.

Recipes 4.2, 4.3, 4.6

Where the asynchrony actually lands

Say it plainly before drawing anything: nothing in ch04/recipe_4_shared is asynchronous. InMemoryMemberService.save writes into a ConcurrentHashMap and returns Mono.just(member); findAll is Flux.fromIterable(members.values()), a snapshot of an already-materialised collection; @PostConstruct init() seeds three members through Flux.just(...).flatMap(this::save).subscribe(). The reactive types are the endpoint contract, not proof of non-blocking I/O. What is genuinely non-blocking is everything the recipes do not write: Reactor Netty accepting connections, the response body being encoded into DataBuffers and flushed as signals arrive, and the request body being decoded lazily.

The blocking calls that do exist are bind().block(), in all twelve ReactorNettyBootstrap classes of the chapter, and System.in.read() in eleven of them (4.6_i omits it and stays up anyway, because Netty's event-loop threads are non-daemon). Both park the main thread only; no block(), toFuture() or Thread.sleep appears anywhere on the request path.

What the chapter deliberately leaves out

Grep ch04/ for ServerSentEvent, TEXT_EVENT_STREAM, WebSocketHandler, Flux.interval, delayElements, R2dbc or WebTestClient: zero hits in sources. So a Flux<Member> served with Accept: application/json is aggregated into one JSON array by the encoder rather than streamed record by record — per-element streaming would need application/x-ndjson or text/event-stream, and neither appears. The webapp/ folder inside recipe_4_4_i (index.html, app.js, webstomp.js) is a STOMP-over-WebSocket browser client pointed at ws://localhost:8080/echo-ws/echo-endpoint with /topic/echo and /app/echo; ch04 has no server side for it and no addResourceHandlers registration, so it is never served.

Reading the flow. The par lanes are two independent subscriptions that can interleave on the same event loop — that is the point of drawing them in parallel. Read the left lane's hand-off carefully: list() returns before a single Member exists, so the arrow from MC back to DH carries an unstarted Flux; only ResponseBodyResultHandler subscribing to it (the Note over) causes findAll's iterator to be pulled. In the right lane the order matters the other way round: the body must be decoded before create(@RequestBody Member member) can be called at all, so save — and its synchronous ConcurrentHashMap.put — happens on whatever thread the decoder completed on. Because save and findAll never touch the network or disk, that thread is never held longer than the map operation; put a real JDBC or HTTP call in there and the same diagram becomes an event-loop stall. The codec node is not decorative: WebFluxConfiguration in 4.2_i, 4.2_ii and all three 4.3 modules overrides configureHttpMessageCodecs(ServerCodecConfigurer configurer) and installs configurer.defaultCodecs().jackson2JsonEncoder(new Jackson2JsonEncoder(mapper)) with SerializationFeature.WRITE_DATES_AS_TIMESTAMPS disabled — 4.4 and 4.6 do not override it and fall back to the detected default.

Recipes 4.2–4.4

Object graph: service, records, collaborators

The dependency shape is deliberately tiny, which makes it worth pinning down exactly. MemberService is a public interface exposing Flux<Member> findAll(), Mono<Member> findById(long) and Mono<Member> save(Member); its only implementation, InMemoryMemberService, is @Service and deliberately package-private, so controllers depend on the abstraction even though the scan finds the bean from the same root package. Note the shadowing trick in the module layout: 4.2_ii, all three 4.3 modules, and 4.4_iii–v declare their own com.apress.spring6recipes.reactive.court.domain.Member under src/main/java, and that compiled class wins over the identically named record in recipe_4_shared because module output precedes dependencies on the classpath. Same simple name, three different shapes.

Reading the graph. The realization edge from InMemoryMemberService up to MemberService is the only Spring-managed contract in the chapter: every MemberController variant, annotated or functional, receives that interface through a constructor parameter, which is why no module declares a @Bean for it — @ComponentScan plus @Service is enough. The three Member boxes are not a hierarchy; the dotted ..> edges say "this module ships its own record and the shared one is invisible to it". MemberValidated is the one annotated @NotBlank String name, @NotBlank @Email String email, String phone; MemberForm is the four-component one, name, email, phone, SportType preferredType, and the extra constructor this(name, email, phone, null) in it is load-bearing in a way that is easy to miss: InMemoryMemberService is compiled against the three-argument record in recipe_4_shared, so once a module shadows that record the inherited @PostConstruct init() only links if the local record still offers a three-argument constructor. The SportTypeRepository pair is the chapter's honest note about reactive purity: findAll returns a Flux but findById returns a blocking Optional, and that second method is the one SportTypeConverter calls.

Recipe 4.3

Error handling with @ControllerAdvice

All three modules change the same two lines of input — @Valid @RequestBody Member member and @RequestParam String name without a default — and differ only in what catches the resulting exception. 4.3_i is hand-written: an empty-by-content @ControllerAdvice class whose @ExceptionHandler(WebExchangeBindException.class) method is @ResponseBody and returns Flux<ErrorMessage>, built with Flux.fromIterable(ex.getFieldErrors()).map(this::toErrorMessage) where toErrorMessage reads fe.getField() and fe.getDefaultMessage() into the nested record ErrorMessage(String field, String message). 4.3_ii is two lines: @ControllerAdvice public class GlobalErrorHandler extends ResponseEntityExceptionHandler { } — no handler methods, because the base class already carries one per framework exception. 4.3_iii keeps the base class and overrides a single protected hook, handleWebExchangeBindException(WebExchangeBindException ex, HttpHeaders headers, HttpStatusCode status, ServerWebExchange exchange) returning Mono<ResponseEntity<Object>>, to translate the violation messages through getMessageSource() for the request's locale and stash them on the exchange before delegating to super.handleExceptionInternal(ex, null, headers, status, exchange). Two details that matter when you run them: HttpStatusCode (not the old HttpStatus) is the Spring 6 signature, and 4.3_iii imports Map, MissingRequestValueException and ServerWebInputException without using any of them.

Reading the flow. The decision node is the fork the recipes exist to show: validation is triggered while the annotated argument resolver is producing Member, so the exception surfaces before MemberController.create is ever entered and must be caught by advice, not by the controller. The advice itself is invoked by the annotated-@ExceptionHandler resolution strategy that @EnableWebFlux registers, and it is looked up after the handler method fails — which is why 4.3_ii needs no @ResponseBody (its inherited methods already return ResponseEntity) while 4.3_i must declare it explicitly to write a Flux as JSON. The dashed bottom edge is the practical difference between the variants: from 4.3 onward WelcomeController.welcome declares @RequestParam String name with no default value, so a missing name raises a different exception that only the two base-class variants know how to map.

Recipe 4.4

Reactive Thymeleaf views

Five modules, one controller rewritten each time. 4.4_i swaps @RestController for @Controller and adds the three Thymeleaf beans to WebFluxConfiguration: SpringResourceTemplateResolver (prefix classpath:/templates/, suffix .html, TemplateMode.HTML), SpringWebFluxTemplateEngine, and ThymeleafReactiveViewResolver, registered through configureViewResolvers(registry.viewResolver(thymeleafReactiveViewResolver())). Its handler methods return view names, sometimes inside a publisher: Mono<String> add(Model model) returns Mono.just("member") after putting an empty Member in the model, and create composes Mono.just(member).map(memberService::save).then(Mono.just("redirect:member-success")) — the .then discards the saved member so the outcome is a redirect. welcome.html is the clearest reactive-view idiom in the book: the controller does model.addAttribute("today", Mono.just(LocalDate.now())) and the template consumes ${#temporals.format(today, 'dd-MM-yyyy')}, i.e. a publisher is a legitimate model attribute because the reactive resolver subscribes to it before rendering. 4.4_ii adds @GetMapping("/{id}") with findById(id).defaultIfEmpty(...).doOnNext(m -> model.addAttribute("member", m)).then(Mono.just("member")). 4.4_iii adds @ModelAttribute("sportTypes") Flux<SportType> so the select in member.html can iterate ${sportTypes}. 4.4_iv registers SportTypeConverter via addFormatters(FormatterRegistry). 4.4_v swaps that for validation — @Valid, @NotBlank, @Email, @NotNull SportType and an explicit if (bindingResult.hasErrors()) return Mono.just("member") — and, notably, drops the converter registration: SportTypeConverter is still in the source but without @Component, and addFormatters is gone, so preferredType binds with default conversion only.

Reading the flow. Trace the top chain first: it is plain bean wiring executed once at context refresh — thymeleafTemplateResolver() is fed to thymeleafTemplateEngine(), which is fed to thymeleafReactiveViewResolver(), and the WebFluxConfigurer.configureViewResolvers callback adds that last bean to the ViewResolverRegistry that @EnableWebFlux uses to build its view-resolution result handler. Then the request chain: welcome() returns the literal "welcome", the result handler treats it as a view name, the resolver writes the rendered template into the response body — and note that a handler may return String or Mono<String> here with no other change, because the view-name publisher is simply subscribed. model.addAttribute("today", Mono.just(LocalDate.now())) is the interesting hop: nothing in the controller forces that Mono, so the value reaching ${today} is only produced during rendering, which is exactly what makes the Thymeleaf reactive engine necessary (a plain SpringTemplateEngine would print the publisher). The dashed lower edges are 4.4_iv's contribution: a Converter<String, SportType> handed to the FormatterRegistry, consulted when the submitted <select> value has to become a SportType record, and reading through the same SportTypeRepository.findById that @ModelAttribute("sportTypes") streamed to the browser.

Reading the states. BlankForm and DetailForm are the two @GetMapping methods of MemberController; both end in the same view name member, and the detail one only fills the model once findById emits, via doOnNext inside the returned chain. The transition that earns its place is Posted -> BlankForm: only in 4.4_v does create inspect BindingResult.hasErrors() and short-circuit back to the form, which is what makes the th:if="${#fields.hasErrors('email')}" and th:errors="*{email}" spans in member.html produce red text instead of a silently redirected record. In 4.4_i through iv the BindingResult parameter is declared and never read, so an invalid submission falls into the Broken path and still redirects. One template is orphaned in all five modules: members.html, which iterates ${members}, is never resolved because no handler method in ch04 returns the view name members.

Recipe 4.5

WebClient as a reactive consumer

4.5_i is the only module in the chapter that consumes rather than serves, and it ships two main methods that differ in exactly one type argument. Both do WebClient.create("http://localhost:8080/").get().uri("/members").accept(MediaType.APPLICATION_JSON) .exchangeToFlux(cr -> cr.bodyToFlux(X.class)).subscribe(System.out::println) and then System.in.read(). In Main, X is String; in ClientWithMapping it is Member, which is why this module — like 4.2 — declares jackson-databind and jackson-datatype-jsr310 in ch04/build.gradle.

Reading the flow. The exchange is deliberately two-phase. The arrow S-->>W: status and headers, body still unread is what exchangeToFlux guarantees: you get a ClientResponse before the body is touched, and the lambda's cr.bodyToFlux(Member.class) is the only thing that requests the bytes — which is why the client must consume the returned Flux fully, since exchangeToFlux leaves connection release in your hands rather than doing it for you as retrieve() would. The element type on the return edge explains the two classes: with String.class each decoded JSON array element arrives as a JSON text String you print as-is, with Member.class the same array elements are bound to the record's components, so the console output is Member[name=…, email=…, phone=…]. The final note is the whole reason System.in.read() is in both files: subscribe returns immediately, so without a parked main the JVM would race the prints. Point it at recipe_4_6_i on 8090 instead (edit the base URL) and the same client exercises the functional endpoint model unchanged.

Practicalities

Building and running the recipes

ch04/build.gradle applies java plus com.github.johnrengelman.shadow to every subproject whose name does not contain shared, and adds implementation project(":ch04:recipe_4_shared"), spring-context, spring-webflux and reactor-netty-http to all of them; build is finalized by shadowJar. Thirteen of the sixteen modules are self-contained servers or clients with no external infrastructure.

  1. Compile and package one recipe. 
    ./gradlew :ch04:recipe_4_1_i:build
    Output: ch04/recipe_4_1_i/build/libs/recipe_4_1_i-6.0.0-SNAPSHOT-all.jar.
  2. Run the Reactor Netty recipes. The application plugin is not applied anywhere in ch04, so the fat jar has no Main-Class manifest entry — run it with -cp and name the bootstrap class (this is the pattern the repo's own docs/walkthrough_run_recipe.md uses): 
    java -cp ch04/recipe_4_1_i/build/libs/recipe_4_1_i-6.0.0-SNAPSHOT-all.jar \
  com.apress.spring6recipes.reactive.court.ReactorNettyBootstrap
    Same shape for recipe_4_2_i, recipe_4_2_ii, recipe_4_3_i|ii|iii, recipe_4_4_i…v and recipe_4_6_i. Press ENTER to stop anything with System.in.read(); 4.6_i has to be killed, since its main returns while the non-daemon event loops keep the JVM up.
  3. Probe the endpoints. GET http://localhost:8080/welcome?name=World (in 4.1 the name parameter is optional, from 4.3 it is required), GET http://localhost:8080/members, POST http://localhost:8080/members with {"name":"...","email":"...","phone":"..."}, and the form pages /welcome and /members plus /members/{id} for 4.4. 4.6_i answers the same paths on 8090.
  4. Run the client. Start a 4.2-style server on 8080 first, then 
    java -cp ch04/recipe_4_5_i/build/libs/recipe_4_5_i-6.0.0-SNAPSHOT-all.jar \
  com.apress.spring6recipes.reactive.court.ClientWithMapping
    or ...reactive.court.Main for the untyped variant.
  5. Recipe 4.1_ii and 4.1_iii are WARs. Either deploy build/libs/recipe_4_1_ii.war to a Servlet 6 container (Tomcat 10.1, Jetty 11 — jakarta.servlet-api is providedCompile), or use the palantir tasks configured in ch04/build.gradle: ./gradlew :ch04:recipe_4_1_ii:docker then ./gradlew :ch04:recipe_4_1_ii:dockerRun builds s6r/court-flux:recipe_4_1_ii, starts a container named s6r-court-flux-recipe_4_1_ii and maps 8080:8080.

Prerequisites and traps found in the source

  • Java 19 toolchain. The root build.gradle pins JavaLanguageVersion.of(19) and adds --enable-preview to compile, test and exec. On this machine gradle.properties sets org.gradle.java.home to a JDK 17, so a JDK 19+ must be resolvable (toolchain auto-provisioning, or run Gradle itself on 19). The repo walkthrough uses C:\Users\sahuk\.jdks\openjdk-23\bin\java.exe to execute the jars.
  • Port collisions. Everything binds 8080 except 4.6_i (8090), and only one server can hold a port at a time. 4.1_i binds 0.0.0.0 (all interfaces) while every other bootstrap binds localhost — the only recipe reachable from outside the machine.
  • The ch04 Dockerfile expects court.war. ch04/Dockerfile builds eclipse-temurin:19-jdk-alpine with Tomcat 10.1.4, then COPY court.war $CATALINA_HOME/webapps/ — but no build script renames the WAR, and palantir files war.outputs drops recipe_4_1_ii.war into the context. Rename the artifact or set the WAR archive name before building the image. It also exposes 5005 for JDWP.
  • Validation needs an EL implementation. 4.2_ii, 4.3_* and 4.4_v add hibernate-validator and org.glassfish:jakarta.el; drop the latter and message interpolation fails at runtime, not at compile time.
  • No database, broker or cache. The only state is InMemoryMemberService's ConcurrentHashMap — restart the process and the seeded three members plus anything POSTed are gone. 4.5_i also has no test or server, so it is useless unless another module is running.

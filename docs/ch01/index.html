Chapter 1 — Spring Core Tasks

Everything in this chapter is about one object: the ApplicationContext. Fifty-nine runnable modules take a plain Sequence, a shop made of Product, ShoppingCart and Cashier, and a calculator pair, and walk them through bean definition, injection, scope, lifecycle, externalised values, factory creation, profiles, AspectJ advice and load-time weaving. No web layer, no database — every module is a main method that boots a container and prints.

Overview

Mental model and module map

Every module in ch01/ is the same four-act shape: a configuration source declares beans, a context is booted from it, a client (always Main or a Demo class) asks the context for a bean, and the bean does something printable. The chapter's variety comes from swapping one of those four parts: a @Bean method instead of XML, a scanned @Component instead of a declared bean, a prototype instead of a singleton, an advice chain wrapped around the returned object.

Two domains carry the load. The sequence examples (ch01/recipe_1_1_i … recipe_1_4_ii, plus recipe_1_25_*) use one tiny class, Sequence with a PrefixGenerator collaborator, so that injection and qualifier mechanics are all that is visible. The shop examples (recipe_1_2, recipe_1_5_i … recipe_1_6_ii, recipe_1_8_*, recipe_1_9_*, recipe_1_10_*, recipe_1_11, recipe_1_12, recipe_1_24_*) add state — a cart holding products, a cashier appending to a file — so scope, lifecycle callbacks and events have somewhere to land. A third domain, the calculator pair (ArithmeticCalculator / UnitCalculator) and the complex number follow-on (Complex, ComplexCalculator), exists only to give AspectJ something to advise in recipe_1_13_i … recipe_1_22. recipe_1_23_* swaps both for TaskExecutor beans.

Worth knowing before you read the diagrams

Chapter 1 contains no SpEL. Grepping the whole chapter for #{ or ExpressionParser returns nothing: the only expressions used are ${…} property placeholders and a classpath: resource string, both resolved by PropertySourcesPlaceholderConfigurer (recipe_1_6_i) rather than by the SpEL engine. Likewise there is no BeanFactoryPostProcessor implementation and no InitializingBean / DisposableBean in the chapter — the init and destroy stories are told with @Bean(initMethod, destroyMethod) and the Jakarta annotations.

Reading the flow. The left column is what you hand the container: a @Configuration class (recipe_1_2/…/shop/config/ShopConfiguration.java), a package name to scan (recipe_1_1_ii/…/sequence/Main.java passes the base package straight into the constructor), a programmatic supplier (recipe_1_25_i), an @Imported second config (recipe_1_3_vii) or an XML document (recipe_1_9_iii/…/resources/appContext.xml). The middle node is the ApplicationContext, which is also a BeanDefinitionRegistry and a PropertySourcesCapableEnvironment. The right column is what comes back out of getBean: a shared Product, a ShoppingCart whose scope decides whether the second call is the same object, and — from recipe_1_13_i onwards — not the target object at all but a proxy that wraps it.

Reading the graph. Product is abstract in every module (ch01/recipe_1_2/src/main/java/com/apress/spring6recipes/shop/Product.java) with two concrete subtypes, Battery and Disc; that single abstract type is what makes bean ambiguity interesting later, because three @Bean methods all declare Product as their return type. ShoppingCart holds a list of Product and, in most variants, hands out Collections.unmodifiableList from getItems() — recipe_1_12 is the exception and returns the live list. Cashier depends on ShoppingCart only as a method argument, never as a field, so it is a stateless service bean while the cart is stateful; that asymmetry is the whole point of recipe 1.5. CheckoutEvent and CheckoutListener exist only in recipe_1_24_i and recipe_1_24_ii. In recipe_1_6_i and recipe_1_6_ii Product grows a third constructor argument, discount, plus getDiscount(), and in recipe_1_10_iii its price field loses final so the factory bean can call the package-private setPrice.

Recipes 1.3 – 1.4

Injecting collaborators

Recipe 1.3 is the chapter's "same problem, seven mechanisms" set. The problem: Sequence needs a PrefixGenerator, and there is more than one implementation in the container. The seven modules solve it at seven different points, and the differences are visible in two places only — the annotations on Sequence and the signature of the @Bean method in …/sequence/config/SequenceConfiguration.java.

Reading the graph. Follow one edge at a time. Constructor-inject from a method parameter: in recipe_1_3_iv sequenceGenerator(PrefixGenerator prefixGenerator) declares the dependency in its signature, the container resolves that parameter by type and hands it in, and the constructor stores it — no annotation anywhere on Sequence. Setter-inject: recipe_1_3_i keeps the same parameter mechanism but calls generator.setPrefixGenerator(prefixGenerator) on the object it constructed with new Sequence("A", 100000). Annotation-driven: recipe_1_3_v drops the parameter and puts @Autowired on the field, so AutowiredAnnotationBeanPostProcessor populates it after instantiation; recipe_1_3_iii declares the field as an array and gets every PrefixGenerator bean. recipe_1_3_vi adds @Qualifier("datePrefixGenerator") on the field, the setter parameter and the @Bean method parameter, because those are three separate resolution points. recipe_1_4_i swaps Spring's annotation for Jakarta's @Resource(name = "datePrefixGenerator"), which resolves by bean name first; recipe_1_4_ii uses @Inject with @DatePrefixAnnotation, a custom annotation itself meta-annotated with jakarta.inject.Qualifier and placed on the candidate class rather than on the injection point.

Reading the chain. The interesting hop is 1_3_iii → 1_3_iv: three @Bean methods competing on type is exactly when a qualifier becomes mandatory. 1_3_vii is the structural one — SequenceConfiguration declares only sequence(PrefixGenerator prefixGenerator), and @Import(PrefixConfiguration.class) pulls in a second configuration class that owns datePrefixGenerator(); the container treats imported definitions as if they were declared locally, so the method parameter still resolves. 1_3_ii is the outlier: it has no config class at all, because new AnnotationConfigApplicationContext("com.apress.springrecipes.sequence") scans a package and @Service SequenceService / @Component("sequenceDao") SimpleSequenceDao register themselves. 1_3_iii's Sequence also shows the cost of field injection: its Sequence(String suffix, int initial) constructor assigns nothing to the autowired array, and getSequence() iterates it, so the object is only usable after the post-processor has run.

Stale references in the 1.4 / 1.3 XML path

recipe_1_4_i/src/main/resources/appContext.xml runs context:component-scan base-package="com.apress.springrecipes.sequence.config" — the pre-Spring-6 package, which contains no classes on this module's classpath — and recipe_1_4_ii boots the same way from Main but ships no appContext.xml in src/main/resources at all. The Java sources under com.apress.spring6recipes.sequence are the authoritative part of these two modules; getBean("sequenceGenerator") there is reading for shape, not something to execute.

Recipes 1.5, 1.8, 1.9, 1.25

Scope and lifecycle

recipe_1_5_i and recipe_1_5_ii differ by exactly one annotation, and the difference shows up in the printed output. Both Main classes look the cart up twice — by type in recipe_1_5_i, by bean name in recipe_1_5_ii — and put different products in each cart; with the bare @Component the second call returns the same object, so cart 2 prints AAA, CD-RW and DVD-RW together.

Reading the sequence. Hop 1 is the client asking the context by bean name in recipe_1_5_ii/…/shop/Main.java, or by type in recipe_1_5_i/…/shop/Main.java — the resolution outcome is identical, because the scanned definition is the only ShoppingCart. Hop 2 is the container consulting the scope recorded on the definition: @Component alone leaves it singleton, so the first instantiation is cached and later lookups are cache hits; @Scope("prototype") makes the container run the full creation path every time. That is why recipe_1_5_i prints three items in cart 2. Two corollaries the source makes explicit: recipe_1_8_iii and recipe_1_8_v add @Lazy to the prototype so nothing is pre-instantiated, and they retrieve through context.getBeanProvider(ShoppingCart.class).getIfAvailable(), which is the idiomatic way to keep asking for a new instance without holding the context. A prototype handed to a singleton is injected once, which is why no ch01 bean tries it: the cart is always fetched from the context directly. recipe_1_25_iii reaches the same scope switch from code, with a BeanDefinitionCustomizer calling bd.setScope(BeanDefinition.SCOPE_PROTOTYPE) and bd.setLazyInit(true).

Reading the sequence. The Cashier bean keeps a BufferedWriter, so it needs a start-up and a shut-down step, and the chapter shows three ways to attach them. recipe_1_8_i/…/shop/config/ShopConfiguration.java declares @Bean(initMethod = "openFile", destroyMethod = "closeFile") and the Cashier class carries no annotation at all; recipe_1_8_ii and recipe_1_8_iii move the same contract onto the class with @PostConstruct and @PreDestroy; recipe_1_8_v strips both mechanisms — its Cashier still declares openFile() and closeFile(), but nothing in the module names them, so no container callback reaches them. The BeanPostProcessor pair is the other half of this recipe: AuditCheckBeanPostProcessor prints every bean type it sees and returns the reference untouched, while ProductCheckBeanPostProcessor pattern-matches bean instanceof Product in both hooks. The registration difference between recipe_1_9_i and recipe_1_9_ii is the lesson: (i) lets @ComponentScan find the processors, (ii) declares them as static @Bean methods so the container can instantiate a post-processor without first instantiating and proxying the configuration class that declares it. Because post-processors run around every bean, the same two hooks also fire for aaa, cdrw and dvdrw — which is why the (ii) processor prints the product names.

recipe_1_8_iv belongs to this cluster conceptually but uses the sequence domain: two @Component implementations of PrefixGenerator compete, and @Primary on DatePrefixGenerator plus @DependsOn("datePrefixGenerator") on the consumer's @Bean method settles both which candidate wins and which definition gets created first.

Recipes 1.6 – 1.7

Externalised values and messages

recipe_1_6_i and its _ii sibling are the only modules in the chapter that load a properties file into the container. The mechanism is two-part and easy to misread: @PropertySource("classpath:discounts.properties") puts the file into the environment, and PropertySourcesPlaceholderConfigurer — declared as a static @Bean method — is what actually rewrites ${…} strings. The three @Value fields on the configuration class are then read by ordinary field injection and passed into product constructors.

Reading the flow. Everything left of defs happens during context refresh, before any application bean exists: the annotation registers a PropertySource with the Environment, and the configurer walks the registered definitions. The step that surprises people is defs to flds: @Value("${specialcustomer.discount:0}") is not resolved inside the definition, it is a field on ShopConfiguration itself, injected by AutowiredAnnotationBeanPostProcessor before the container invokes any @Bean method on that instance — which is why new Battery("AAA", 2.5, true, specialCustomerDiscountField) sees 0.1 rather than zero. The :0 suffix is the default that keeps the module working if a key is missing; discounts.properties supplies 0.1, 0.15 and 0.2. recipe_1_6_ii adds the resource branch: @Value("classpath:banner.txt") injects a Resource, that resource goes into the BannerLoader constructor, and the loader's @PostConstruct showBanner() opens banner.getURI() with Files.lines — proof that the annotation is resolved to a real file, not a string. The dotted edge at the bottom is deliberately outside the container: the same module's Main also reads the file directly with PropertiesLoaderUtils after the context is closed, showing the properties file is an ordinary classpath resource.

recipe_1_7 keeps the same "the container resolves the value" idea for text instead of numbers. Its configuration class declares exactly one bean, messageSource() returning a ReloadableResourceBundleMessageSource with basename classpath:messages and setCacheSeconds(1); the bean name matters, because the context looks up a MessageSource by that id and delegates getMessage to it. Main then resolves two keys against messages_en_US.properties, the second with an argument array — new Object[] { "[DVD-RW 3.0]", LocalDateTime.now() } — matching the {0} and {1} placeholders in the bundle.

Recipes 1.10 – 1.12

Factory beans and profiles

Recipe 1.10 asks: what if the object a @Bean method returns is not created by calling a constructor? recipe_1_10_i answers with a static helper, ProductCreator.createProduct("aaa") whose body is a switch expression; the container never learns about the helper, because the @Bean method hides it. recipe_1_10_ii promotes the helper into a bean of its own — productCreatorFactory() returns a ProductCreator built over a Map.of("aaa", …, "cdrw", …, "dvdrw", …) — and the three product @Bean methods each declare ProductCreator productCreator as a parameter, so the factory instance is injected by type. recipe_1_10_iii is the genuine Spring construct: DiscountFactoryBean extends AbstractFactoryBean<Product> with setProduct, setDiscount, getObjectType() returning product.getClass() and createInstance() that discounts the price in place and returns the same object. Requesting discountFactoryBeanAAA therefore yields a Product, not the factory — while the module's Main keeps asking for the untouched aaa, cdrw and dvdrw beans, so the discounted and undiscounted objects are both visible.

The same FactoryBean shape reappears once more in the chapter, at recipe_1_23_ii/…/executors/ExecutorsConfiguration.java: ScheduledExecutorFactoryBean is a bean whose product is a ScheduledExecutorService, and the factory is configured with a ScheduledExecutorTask that itself takes the Runnable. PropertySourcesPlaceholderConfigurer (recipe 1.6) is the third FactoryBean-adjacent infrastructure bean.

Recipes 1.11 and 1.12 change the question to which definition is registered at all. Four configuration classes declare the same bean ids aaa, cdrw, dvdrw with different prices; @Profile decides which class contributes.

Reading the flow. The three setup hops in Main are the recipe: profiles are set on the environment before the definitions are read, the classes are registered (by scan here, by context.register(ShopConfigurationGlobal.class) in recipe_1_11/…/shop/Main.java), and only then does refresh() evaluate the conditions. Two @Profile values on one class, { "summer", "winter" }, are an any-of test, so ShopConfigurationSumWin is active for either. Skipped classes contribute nothing, which means the bean ids aaa, cdrw and dvdrw come from a single class and never collide. The 1_11 to 1_12 delta is deliberate: recipe_1_11's ShopConfigurationGlobal has no @Profile so it always applies, while in recipe_1_12 it is annotated @Profile("global") and the second active profile is what brings it back — and its Cashier switches from new Cashier("checkout", path) to new Cashier(path) plus setBeanName(name), taking the output file name from the bean id.

Recipes 1.13 – 1.17

AspectJ advice and pointcuts

Five annotations do all the work in this cluster: @EnableAspectJAutoProxy on CalculatorConfiguration (which registers the auto-proxy creator), @Aspect @Component on the advice class, and an execution pointcut on each advice method. Because StandardArithmeticCalculator is a package-private class implementing an interface, the object that getBean returns is a JDK dynamic proxy, not the target — the reason recipe 1.14 can print a different value for joinPoint.getTarget() and joinPoint.getThis().

Reading the sequence. Hop 1: Main never holds a StandardArithmeticCalculator; it holds the proxy registered under that bean definition. Hop 2: the proxy asks its interceptor chain for the advices applicable to div, sorted by aspect order — in recipe_1_15_ii that is @Order(0) on CalculatorValidationAspect and @Order(1) on CalculatorLoggingAspect, and recipe_1_15_i achieves the same ordering by having both aspects implement org.springframework.core.Ordered and return 0 and 1 from getOrder(). Validation therefore runs first, and it only matches methods with two double parameters because its pointcut is execution(* *.*(double, double)). Hop 3 is the target invocation itself; div throws IllegalArgumentException("Division by zero") when b == 0. The return edge is where @AfterReturning(returning = "result") in recipe_1_13_iii binds the value, and the failure edge is where @AfterThrowing(throwing = "ex") in recipe_1_13_iv logs instead; recipe_1_13_v replaces the whole set with one @Around that calls joinPoint.proceed() inside a try/catch, which is the only variant that can both log and rethrow from a single method. Recipes 1.16 and 1.17 do not change the chain — they change how its matching is expressed: @Pointcut named loggingOperation() reused by all five advices inside one aspect (1.16 i), moved to a separate CalculatorPointcuts type and referenced by fully-qualified name (1.16 ii), then replaced by @annotation, @within, within(Type+) composed with ||, and a parameter-binding pointcut execution(* *.*(..)) && target(target) && args(a,b) that lets logParameter(Object target, double a, double b) take the arguments as method parameters (1.17).

Recipes 1.18 – 1.22

Introductions and load-time weaving

Spring's proxy-based AOP can only add advice to interfaces the target already implements — except with @DeclareParents. In recipe_1_18/…/calculator/CalculatorIntroduction.java two fields declare MaxCalculator and MinCalculator against com.apress.spring6recipes.calculator.StandardArithmeticCalculator with defaultImpl pointing at SimpleMaxCalculator and SimpleMinCalculator. That is what makes (MaxCalculator) arithmeticCalculator legal in Main. recipe_1_19 pushes it further: @DeclareParents(value = "com.apress.spring6recipes.calculator.Standard*Calculator", defaultImpl = SimpleCounter.class) attaches Counter to both calculators, and @After("execution(* com.apress.spring6recipes.calculator.*Calculator.*(..)) && this(counter)") binds the introduced mixin as an advice parameter so each call increments that proxy's own counter — Main then prints two different counts.

Reading the graph. Two edges carry the introduction story: the solid implemented by the target line is what the JDK proxy could do on its own, and the dotted never implemented in source line is the gap CalculatorIntroduction fills — the proxy is created implementing the introduced interfaces and delegates max() to a SimpleMaxCalculator. For Counter the delegation is observable per proxy, which is why recipe_1_19/Main prints two distinct counts. The right-hand pair of edges is a different mechanism: ComplexCachingAspect advises call(... Complex.new(int, int)), i.e. the calling code, not the target object, and Spring's proxy AOP cannot do that. It needs AspectJ, which this chapter wires up four different ways: recipe_1_20_ii relies on META-INF/aop.xml with a weaver/include within="com.apress.spring6recipes.calculator.*" element and an aspects/aspect name=ComplexCachingAspect declaration; recipe_1_20_iii (and recipe_1_21) turn weaving on from code, in an ApplicationContextInitializer that wraps the bean classloader in DefaultContextLoadTimeWeaver and calls AspectJWeavingEnabler.enableAspectJWeaving(ltw, beanClassLoader) before refresh(); recipe_1_22 declares the same intent declaratively with @EnableLoadTimeWeaving, @EnableSpringConfigured and a static AspectJWeavingEnabler bean, and its commented-out initializer line in Main is the difference between the two styles. recipe_1_21 adds the only trick that makes a woven aspect injectable-aware: Aspects.aspectOf(ComplexCachingAspect.class) returns the AspectJ instance, which the @Bean method then primes with a cache pre-loaded with keys "2,3" and "3,5" — so the first new Complex(2, 3) is a cache hit. recipe_1_22's Complex is the payoff of weaving: an object created with new inside StandardComplexCalculator.add still gets its @Autowired setFormatter(ComplexFormatter) called, so toString() can delegate to the formatter instead of hard-coding the pattern. All four weaving modules require the AspectJ weaver on the JVM (-javaagent:aspectjweaver.jar, declared through the spring-instrument or aspectjweaver dependencies in their build files), so they are the least runnable part of the chapter.

Recipes 1.23 – 1.24

Task executors and application events

recipe_1_23_i/…/executors/ExecutorsDemo.java is pure JDK: cached, fixed, single-thread, result-bearing, virtual-thread and scheduled executors, each wrapping the same DemonstrationRunnable. recipe_1_23_ii keeps that class as the @Component and moves the executors into the container. Seven @Bean methods in ExecutorsConfiguration cover the Spring-side map: SyncTaskExecutor runs on the calling thread, SimpleAsyncTaskExecutor spawns a thread per task, TaskExecutorAdapter wraps Executors.newCachedThreadPool(), ThreadPoolTaskExecutor is tuned with core 50, max 100, setAllowCoreThreadTimeOut(true) and setWaitForTasksToCompleteOnShutdown(true), ConcurrentTaskExecutor wraps Executors.newVirtualThreadPerTaskExecutor(), and ScheduledExecutorFactoryBean plus ScheduledExecutorTask (period 50) is the factory-bean case. SpringExecutorsDemo @Autowireds all of them plus the runnable and submits from a @PostConstruct submitJobs(), so SpringExecutorsDemo.main — this module has no Main class — is just try (var ctx = new AnnotationConfigApplicationContext(cfg)) {} — closing the context is what shuts the thread pools down, and ThreadPoolTaskExecutor's wait-for-completion flag is what makes that shutdown orderly.

recipe_1_24_i and recipe_1_24_ii are the publish/consume pair, and the two variants differ on both sides at once.

Both modules publish twice — cashier.checkout(cart1) and cashier.checkout(cart2) — and both carts are prototype-scoped, so the two CheckoutEvent objects carry distinct item lists. That is the payoff for the scope work in recipe 1.5: had the cart still been a singleton, cart 2's event would have replayed cart 1's contents.

Build and run

Building and running

Each recipe is its own Gradle subproject; settings.gradle walks the tree and includes any directory whose name matches ^ch.* and contains recipe, so module paths look like :ch01:recipe_1_1_i. Chapter modules do not apply the application plugin — ch01/build.gradle applies com.github.johnrengelman.shadow to every subproject and wires build to be finalizedBy('shadowJar'), which is why there is no run task.

# build one module and its fat jar
./gradlew :ch01:recipe_1_1_i:build

# run it: classpath jar plus the real main class
java -cp ch01/recipe_1_1_i/build/libs/recipe_1_1_i-6.0.0-SNAPSHOT-all.jar \
     com.apress.spring6recipes.sequence.Main

# the JUnit ones (only recipe_1_1_i, recipe_1_1_ii and recipe_1_25_i carry tests)
./gradlew :ch01:recipe_1_1_i:test
  • Toolchain. build.gradle pins a Java 19 toolchain and adds --enable-preview to compile, test and exec JVM args; gradle.properties sets org.gradle.java.home to a JDK 17 and -parameters is enabled for the whole build. Run the compiled jars with a JDK 19 that also gets --enable-preview, or the class files are rejected.
  • Dependencies. spring-context everywhere (added by ch01/build.gradle); spring-aop plus aspectjrt/aspectjweaver from recipe_1_13_i on; spring-instrument in recipe_1_20_iii and spring-aspects in recipe_1_22; jakarta.inject-api in recipe_1_4_ii. Every module also gets shared-resources, whose only class is com.apress.spring6recipes.utils.Utils (used by recipe 1.23) plus a simplelogger.properties.
  • No infrastructure. Nothing in ch01 needs Docker, a database, a broker or a port. Side effects on disk are limited to Cashier appending checkout.txt under java.io.tmpdir (recipes 1.8, 1.9, 1.11, 1.12) and BannerLoader reading banner.txt.

Before you run: verified stale spots

These modules carry first-edition leftovers, confirmed by reading the files rather than by guessing:

  • Thirteen calculator Main classes (recipe_1_13_ii … recipe_1_17_iv) ask for getBean("arithmeticCalculator", …), but StandardArithmeticCalculator is annotated with a bare @Component in every one of them — the generated id is standardArithmeticCalculator. recipe_1_13_i, 1_18 and 1_19 avoid the issue by requesting getBean(ArithmeticCalculator.class) and getBean(UnitCalculator.class). From recipe_1_13_ii onwards StandardUnitCalculator does declare @Component("unitCalculator"), so only the arithmetic lookup is broken in those thirteen modules.
  • Every appContext.xml in the chapter scans com.apress.springrecipes.* (no 6) while all classes live in com.apress.spring6recipes.* — in recipe_1_16_i, recipe_1_16_ii and recipe_1_17_ii that XML is unused anyway, because those Main classes boot from the Java config.
  • recipe_1_9_iv/…/sequence/Main.java and recipe_1_4_ii/…/sequence/Main.java load appContext.xml, which does not exist in either module; recipe_1_3_ii scans com.apress.springrecipes.sequence.
  • recipe_1_8_iv/…/sequence/Main.java asks for bean "sequence" while its config declares sequenceGenerator().
  • 48 of the 56 build.gradle files in ch01 set Main-Class to com.apress.springrecipes.<domain>.Main — the pre-Spring-6 package — so java -jar on the fat jar fails even when the code compiles; use -cp with the real class name as shown above. Only recipe_1_1_ii, recipe_1_8_ii, recipe_1_8_iii, recipe_1_20_i … recipe_1_22 name the correct package.
  • recipe_1_25_i, recipe_1_25_ii and recipe_1_25_iii have no build.gradle; they inherit the Java and shadow plugins from the parent builds.

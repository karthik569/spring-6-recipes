Chapter 7 — Spring Transaction Management

The whole chapter is one domain example — a bookshop that decrements BOOK_STOCK and debits ACCOUNT for the price of a book — replayed with seven different ways of obtaining a transaction. It starts at bare java.sql.Connection auto-commit, walks through PlatformTransactionManager, TransactionTemplate and the declarative @Transactional proxy, then spends the rest of the chapter on the three things that actually decide whether money is lost: propagation, the rollback exception rule, and isolation. Every recipe is a Main class against a live PostgreSQL database, so the outcome you see is the real commit boundary, not a mock.

Mental model

Overview and module map

Spring's transaction support has exactly two moving parts, and every recipe in ch07/ is a different combination of them. The first is a PlatformTransactionManager (or its reactive twin ReactiveTransactionManager) that knows how to turn a resource — a JDBC Connection, an R2DBC ConnectionFactory session — into a transaction: switch auto-commit off, set the isolation level, commit, roll back, hand the resource back. The second is who calls those methods. Recipes 7.1 do it with raw JDBC calls. Recipes 7.3 call the manager by hand. Recipes 7.4 hand the call to TransactionTemplate. Recipes 7.5–7.9 let a proxy call it via TransactionInterceptor. Recipe 7.10 lets a woven AspectJ aspect call it, with no proxy at all.

Two facts about the data explain almost every run in the chapter. ch07/recipe_7_1_i/src/main/resources/bookstore.sql seeds book 0001 at PRICE = 30 and user1 at BALANCE = 20, and the ACCOUNT table carries CONSTRAINT positive_balance CHECK (BALANCE >= 0). So the third statement of every purchase — UPDATE ACCOUNT SET BALANCE = BALANCE - 30 — violates a database constraint and blows up. The chapter is deliberately built so the failure path is the default path: the interesting question is never "did the money move" but "how much of the damage survived". Second, the checkout recipes pass List.of("0001", "0002") but 0002 is never inserted anywhere in the chapter, so the second loop iteration would fail on the SELECT PRICE read instead of the balance write.

Not in the source

Only REQUIRED and REQUIRES_NEW appear anywhere in ch07/. Propagation.NESTED, SUPPORTS, MANDATORY, NOT_SUPPORTED and NEVER are never used, and no module uses rollbackForClassName, noRollbackForClassName, value (transaction manager qualifier) or a custom TransactionManager bean name. There is no src/test directory in any of the 17 modules, so nothing here is verified by an automated test — the proof is the database.

Reading the map. The right-hand side never changes: something obtains a Connection from the DataSource the manager holds, calls setAutoCommit(false), and later calls commit() or rollback() on it. What the chapter varies is the left-hand side — who is allowed to make that call. Follow the arrows from 7.1 to 7.10 and the amount of code you own shrinks: in 7.1_i you hold the Connection yourself; in 7.3_i you hold a TransactionStatus and hand it back; in 7.4 you hold nothing but a callback; in 7.5–7.9 you hold nothing at all, because TransactionInterceptor invokes the manager around your method. The dashed arrow to 7.10 marks the one structural break: AdviceMode.ASPECTJ replaces the container-supplied proxy with advice woven into the class itself, so the arrow bypasses bean creation entirely.

Reading the graph. The important edge is BookShopCashier --> BookShop. The cashier is constructed with the bean, and from recipe 7.5 on that bean is a proxy, so every purchase call inside checkout re-enters the transaction advice — which is why propagation is even a question. Note the two shapes the abstraction takes: JdbcBookShop and TransactionalJdbcBookShop both extend JdbcDaoSupport, which supplies the JdbcTemplate and forces setDataSource; the difference is that the second one carries a PlatformTransactionManager field, which recipe 7.5 removes. On the reactive side there is no JdbcDaoSupport equivalent — TransactionalR2dbcBookShop holds a DatabaseClient and either a ReactiveTransactionManager (7.3) or a TransactionalOperator (7.4). Book is in the graph only because it is in the source: from recipe_7_7_i on every module ships a Book bean class that nothing in the transactional path reads.

Recipe 7.1 — ch07/recipe_7_1_i, ch07/recipe_7_1_ii

Recipe 7.1 — transactions without Spring

recipe_7_1_i is the control experiment. ch07/recipe_7_1_i/src/main/java/com/apress/spring6recipes/bookshop/JdbcBookShop.java opens one connection with try (var conn = dataSource.getConnection()) and issues three statements through it. DriverManagerDataSource does not pool or wrap anything, so the connection arrives with PostgreSQL's auto-commit on: the SELECT PRICE is its own transaction, the UPDATE BOOK_STOCK is its own transaction and is durable the instant executeUpdate returns, and only then does the UPDATE ACCOUNT run — and fail, because 20 - 30 violates positive_balance. The SQLException is wrapped in a RuntimeException and thrown, and the book is one copy short of what the customer paid nothing for.

recipe_7_1_ii fixes it with three JDBC calls and nothing else: conn.setAutoCommit(false) at the top, conn.commit() after the third statement, and a nested catch (SQLException ex) { conn.rollback(); throw ex; }. Same connection, same statements, same failure — but now the stock decrement is a pending change on a transaction that gets rolled back, so the database ends exactly where it started.

Reading the states. Trace the top lane: with auto-commit on, each arrow is a separate transaction, so "StockGone" is a committed fact by the time the balance update throws — the damage is not recoverable by any amount of later error handling. That is the whole argument for the bottom lane. In 7.1_ii the state that matters is "Pending": setAutoCommit(false) turns the connection into a transaction, so the constraint violation on statement three can be undone by conn.rollback(). Two details worth carrying into the Spring recipes. First, 7.1_ii's rollback is keyed on SQLException; had the failing statement thrown a RuntimeException — a null ResultSet dereference, say — conn.rollback() would be skipped and the outer try-with-resources would silently close the connection. Second, both variants read the price with rs.next(); price = rs.getInt("PRICE") and never check the return value, so a missing ISBN gives price = 0 rather than an error. Spring's JdbcTemplate.queryForObject, used from recipe 7.3 on, throws EmptyResultDataAccessException in that case instead.

Recipe 7.3 and 7.4 — ch07/recipe_7_3_i, ch07/recipe_7_4_i, ch07/recipe_7_4_ii

Recipes 7.3 and 7.4 — programmatic transactions

Recipe 7.3 hands the job to Spring but keeps the ceremony in your code. ch07/recipe_7_3_i/src/main/java/com/apress/spring6recipes/bookshop/TransactionalJdbcBookShop.java builds a DefaultTransactionDefinition (so: REQUIRED, ISOLATION_DEFAULT, read-write, no timeout), asks the injected DataSourceTransactionManager for a TransactionStatus, runs three getJdbcTemplate() calls, and then calls commit(status) — or, in catch (DataAccessException e), calls rollback(status) and rethrows. The manager and the DAO support are pointed at the same DriverManagerDataSource bean in BookstoreConfiguration, which is what makes this work at all: DataSourceTransactionManager.doBegin binds a ConnectionHolder to the current thread in TransactionSynchronizationManager, and DataSourceUtils.getConnection — which is what JdbcTemplate calls — finds that bound holder instead of opening a second connection. Change nothing else and the updates are in the manager's transaction; bind the manager to a different DataSource and you get three independent auto-commit transactions and a very convincing illusion of correctness.

Recipe 7.4 replaces the hand-rolled begin/commit/rollback with TransactionTemplate. In recipe_7_4_i the template is created inside purchase — new TransactionTemplate(transactionManager) per call — and the body is an anonymous TransactionCallbackWithoutResult whose doInTransactionWithoutResult(TransactionStatus ts) receives the status but ignores it. In recipe_7_4_ii the only change is structural: BookstoreConfiguration declares a transactionTemplate bean and the service takes it in the constructor. The transaction semantics are identical, and both are now safer than 7.3 — TransactionTemplate.execute rolls back on any RuntimeException or Error escaping the callback, not only on the DataAccessException that 7.3's catch clause happens to name.

Reading the calls. Hop 2 is the whole transaction: getTransaction returns a TransactionStatus that is a token, not a resource — you never touch the Connection directly again. Hop 4 is the mechanism people forget: the ConnectionHolder is a thread-bound object, which is why the three JdbcTemplate calls at hops 6, 8 and 9 share one transaction without being passed it, and why moving work to another thread silently moves it out of the transaction. Note that TransactionalJdbcBookShop.purchase catches DataAccessException only; a RuntimeException from anywhere else in the body would skip rollback(status) and leave the transaction open on the way out — the connection would be closed by DriverManagerDataSource's caller-side cleanup with an undecided transaction, i.e. a database-side implicit rollback that the code never asked for. The final hop is the reason the chapter keeps pushing toward declarative transactions: rethrowing after rollback is correct here, but the pair rollback + throw is exactly what the proxy does for you later.

The reactive twins in the same modules

Recipes 7.3, 7.4 and 7.5 each ship a second, parallel implementation under .../bookshop/reactive/ that swaps PlatformTransactionManager for ReactiveTransactionManager and JDBC for R2DBC. TransactionalR2dbcBookShop in recipe_7_3_i calls txManager.getReactiveTransaction(def), which returns Mono<TransactionStatus>, then chains balance.then(txManager.commit(status)) with .onErrorResume(ex -> txManager.rollback(status).then(Mono.error(ex))) — the same begin/commit/rollback shape, but the rollback is an operator in the pipeline rather than a catch clause, because there is no thread to bind a resource to. recipe_7_4_i collapses that into TransactionalOperator.create(txManager) plus balance.as(tx::transactional); recipe_7_4_ii injects the TransactionalOperator as a bean, mirroring the JDBC change. recipe_7_5_i drops the operator and puts @Transactional on a method returning Mono<Void>.

Three defects in the reactive variants, straight from source

  • None of the four reactive Main classes loads its own configuration. ch07/recipe_7_3_i/src/main/java/com/apress/spring6recipes/bookshop/reactive/Main.java imports com.apress.spring6recipes.bookshop.config.BookstoreConfiguration — the JDBC one — and then asks the context for reactive.BookShop. There is no such bean in that config, so it ends in NoSuchBeanDefinitionException. You have to point it at ReactiveBookstoreConfiguration yourself.
  • Each of those mains does purchase(...).subscribe(x -> counter.countDown()) on a Mono<Void>. A Mono<Void> completes without emitting, so the onNext consumer never runs and counter.await() blocks forever. Use doOnSuccess or block().
  • ch07/recipe_7_5_i/.../reactive/ReactiveBookstoreConfiguration.java:60 calls new TransactionalR2dbcBookShop(to, cf) while the class declares a single-argument TransactionalR2dbcBookShop(ConnectionFactory cf). That module does not compile — the checked-in bin/main/.../ReactiveBookstoreConfiguration.class still carries an "Unresolved compilation" marker from the IDE compiler.

Only the JDBC half of the chapter is runnable as committed. Everything below describes the JDBC path unless it says otherwise.

Recipe 7.5 — ch07/recipe_7_5_i

Recipe 7.5 — declarative transactions and the proxy

Recipe 7.5 is where the chapter stops being about API calls. BookstoreConfiguration gains @EnableTransactionManagement (which is @Import(TransactionManagementConfigurationSelector.class), defaulting to AdviceMode.PROXY and proxyTargetClass = false), and JdbcBookShop.purchase is annotated @Transactional with no attributes. The TransactionTemplate bean declared in the same config is left over from 7.4 and unused. The business method now contains no transaction code whatsoever, and the price of that cleanliness is a proxy: because JdbcBookShop implements BookShop and proxyTargetClass is false, context.getBean(BookShop.class) returns a JDK dynamic proxy, not a JdbcBookShop.

That has two consequences the recipes lean on. First, the transaction only exists where the proxy is crossed: an internal this.purchase(...) call would bypass the advice entirely, which is why every variant in 7.6 routes through the injected BookShop bean rather than a locally created instance. Second, asking the container for the concrete type would fail — getBean(JdbcBookShop.class) has no match, so context.getBean(BookShop.class) is not a style preference but a requirement.

Reading the proxy path. Hops 2–4 are the annotation becoming a plan: TransactionAspectSupport.determineTransactionAttribute builds a RuleBasedTransactionAttribute from the annotation, and with an attribute-less @Transactional you get REQUIRED with ISOLATION_DEFAULT and no rollback rules, so the defaults in the rollback section apply unchanged. The decision at hop 12 is the only interesting branch: transactionAttribute.rollbackOn(ex) answers yes for this unchecked exception, DefaultTransactionStatus is marked rollback-only, and rollback(status) is called. Had the target returned normally, hop 12 becomes commitTransactionAfterReturning and the physical commit happens after your method has finished but before control reaches Main at hop 14 — so anything you log at the end of purchase is logging work that is not yet durable. The exception you get back in Main is the target's own exception, untranslated and unwrapped: the proxy never converts a rollback into a different failure, which matters when you are tempted to catch it.

Recipe 7.6 — ch07/recipe_7_6_i, recipe_7_6_ii, recipe_7_6_iii

Recipe 7.6 — propagation across two beans

Now there are two proxies in the call chain: BookShopCashier.checkout and, inside its isbns.forEach(isbn -> bookShop.purchase(isbn, username)), the injected BookShop proxy. The three modules change only the pair of propagation values.

  • recipe_7_6_i — checkout is a bare @Transactional, purchase is a bare @Transactional. Both REQUIRED. One physical transaction, begun by the cashier and merely joined by each purchase; the inner TransactionStatus is a participating one whose flush/commit request is a no-op. If any book fails, everything the whole checkout did is undone at the cashier's boundary.
  • recipe_7_6_ii — checkout becomes @Transactional(propagation = Propagation.REQUIRES_NEW) while purchase stays REQUIRED. Because Main calls checkout from outside any transaction, "requires a new one, suspending any existing one" and "create one if none exists" produce the same physical outcome: one transaction, still shared with the participating purchases. The propagation change is real but unobservable from this entry point — which is the point of the variant.
  • recipe_7_6_iii — now purchase is REQUIRES_NEW too, and the difference bites: the cashier's transaction is suspended, unbound from the thread, and each purchase gets its own connection and its own commit boundary. A purchase that succeeds is durable even when a later purchase throws and even when the cashier's own transaction rolls back.

Wiring note, because it is easy to misread: recipe_7_6_i's config declares the bean as Cashier cashier(BookShop) and JdbcBookShop bookShop(DataSource), while _ii and _iii declare BookShopCashier cashier(BookShop) and _iii declares the shop as BookShop bookShop(DataSource). All three mains do getBean(Cashier.class), which is safe in every case — the declared return type of the bean method is never the runtime type once the proxy wraps it.

Walking the tree. The only edge that decides a commit boundary is whether the status was created or joined. Take 7.6_i: checkout arrives at "no transaction bound", goes left to doBegin, and the two purchase calls take the REQUIRED branch into "join" — so their apparent commit is the no-op at the bottom left, and the single real commit is the cashier's. Take 7.6_iii: the same two purchase calls instead take the REQUIRES_NEW branch, the cashier's holder is unbound before the body runs, and each purchase terminates at "commit here", which is drawn as irreversible on purpose — the arrow labelled cannot be undone by the caller is the difference between a checkout that is atomic and one that is not. The global rollbackOnly leaf is the trap in 7.6_i: because a participating status cannot roll back a physical transaction on its own, a failure in book two marks the whole cashier transaction doomed even if the cashier catches the exception, and the later commit then throws. The dangling node at the bottom records what the chapter does not do: NESTED (a JDBC savepoint inside the same transaction) is never configured, so nothing here suspends-and-resumes at a savepoint.

Reading the suspend. Two connections are open simultaneously between doSuspend and doResume — that is the cost of REQUIRES_NEW, and with DriverManagerDataSource (no pool) it is invisible only because Postgres has connections to spare. Watch the two doResume arrows, one per branch: after each inner transaction finishes, holder A is rebound, so checkout's transaction continues as if nothing happened. Now the asymmetric outcome, which is the lesson: in the success branch the inner commit is already durable when control returns to the loop, so a later failure cannot take it back — with 7.6_i the same later failure would have erased both books. And at the bottom, checkout's own rollback destroys nothing, because the cashier's transaction never executed a statement; it only ever suspended one. A useful corollary for safety-critical code: if the outer transaction did write before calling a REQUIRES_NEW method, the row locks it holds would block the second connection, and the suspended transaction would deadlock against its own continuation — 7.6_iii avoids that purely because checkout delegates all its writes.

Recipe 7.7 — ch07/recipe_7_7_i through recipe_7_7_v

Recipe 7.7 — isolation levels and a racing writer

The five modules of 7.7 are one program with two dials. JdbcBookShop.increaseStock is annotated with a bare @Transactional: it does UPDATE BOOK_STOCK SET STOCK = STOCK + ?, prints the new value, sleeps 10 seconds via Utils.sleep(10000), prints "Book stock rolled back" and throws new RuntimeException("Increased by mistake") — a rollback the program demands, driven straight out of the default rule for unchecked exceptions. JdbcBookShop.checkStock is annotated @Transactional(isolation = ...), reads the stock, and sleeps 10 seconds too. Main starts one thread, waits 5 seconds, starts the other, so the two transactions overlap for about 5 seconds while one of them holds a decision the other wants to read.

ModulecheckStock isolationThread order in MainWhat the overlap is meant to expose
recipe_7_7_iIsolation.READ_UNCOMMITTEDThread 1 = increaseStock, Thread 2 = checkStockthe reader sees the writer's uncommitted +5 (a dirty read)
recipe_7_7_iiIsolation.READ_COMMITTEDThread 1 = increaseStock, Thread 2 = checkStockthe same window, but the reader must not see the pending value
recipe_7_7_iiiIsolation.READ_UNCOMMITTEDThread 1 = checkStock, Thread 2 = increaseStockdirty read with the reader started first

recipe_7_7_vIsolation.SERIALIZABLEThread 1 = checkStock, Thread 2 = increaseStockfull serialisation, at the price of blocking or a serialisation failure

Spring does not implement any of these itself. DataSourceTransactionManager.doBegin translates the attribute into exactly two JDBC calls on the borrowed connection — setTransactionIsolation(TRANSACTION_READ_UNCOMMITTED) and, for readOnly in 7.9/7.10, setReadOnly(true) — plus setAutoCommit(false), and then gets out of the way. Every guarantee, and every missing guarantee, belongs to the database.

Why 7.7_i and 7.7_ii look identical on the shipped PostgreSQL setup

PostgreSQL does not implement READ UNCOMMITTED: asking for it silently gives you READ COMMITTED, so the dirty read the recipe is written to demonstrate cannot occur there. The book's own XML leftovers in these modules point at jdbc:derby://localhost:1527/bookshop, a DBMS where it can. Treat "which anomaly appears" as a database property, confirmed here only as far as the isolation constant in the annotation; recipe_7_7_iv's REPEATABLE_READ and recipe_7_7_v's SERIALIZABLE are the two levels PostgreSQL honours, and the SERIALIZABLE run is the one where the writer may be aborted with a 40001 serialization error rather than simply blocked. 7.7_iii is a duplicate of 7.7_i with the thread order flipped, so it changes nothing on Postgres either.

Reading the interleaving. The writer's increaseStock is annotated with a bare @Transactional, i.e. Isolation.DEFAULT, which tells Spring to leave the connection's isolation level alone — so hop 3 runs at whatever PostgreSQL defaults to (READ COMMITTED) and holds an exclusive lock on the row for its whole 10-second sleep. The reader's isolation, set at hop 7 by setTransactionIsolation inside its own doBegin, decides what hop 9 returns. In 7.7_i and 7.7_iii the annotation says READ_UNCOMMITTED and the intended printed answer is 15 — a value that is then destroyed at hop 11 — which is precisely the anomaly the recipe exists to show, and precisely the one PostgreSQL refuses to let you have. In 7.7_ii, 7.7_iv and 7.7_v the reader prints 10, the rollback is invisible, and the transaction has behaved. The two sleeps are the point of the design: without a 10-second body and a 5-second stagger there is no window, and the recipe would appear to prove nothing. Finally, note the exception never reaches Main: 7.7 wraps the writer in try { ... } catch (RuntimeException e) { }, so the only evidence of the rollback is the printed line and the database afterwards.

Recipes 7.8 and 7.9 — ch07/recipe_7_8_i, ch07/recipe_7_9_i

Recipes 7.8 and 7.9 — which exceptions roll back

Both modules put the same three attributes on JdbcBookShop.purchase:

@Transactional(propagation = Propagation.REQUIRES_NEW,
             rollbackFor = IOException.class,
             noRollbackFor = ArithmeticException.class)

(recipe_7_8_i spreads it over four lines, recipe_7_9_i puts propagation on one line with the rest; recipe_7_10_i keeps the same two rollback rules but downgrades REQUIRES_NEW to REQUIRED, because with the AspectJ weaver the point is advising the call, not the boundary.)

The default rule that these two attributes invert is: RuntimeException and Error roll back, checked exceptions commit. rollbackFor = IOException.class adds a rule for a checked exception, so an IOException now forces a rollback instead of a quiet commit. noRollbackFor = ArithmeticException.class removes an unchecked one, so a divide-by-zero in purchase would leave the stock decrement and the balance debit committed — the exception still propagates to the caller, and the caller sees a stack trace over data that was written. Rules are matched with instanceof walking up the class hierarchy, and when both a rollback rule and a no-rollback rule match, Spring picks the one whose exception type is closest to the thrown class; a subclass of IOException such as FileNotFoundException would still roll back, and a subclass of ArithmeticException such as the stack-overflowing ones would still commit. Note also that neither rule is reachable from these sources: nothing in ch07 throws IOException or ArithmeticException, and the only exception that actually fires is the DataAccessException from the violated check constraint, which is unchecked and unmatched by any rule.

Recipe 7.9's real addition is on the read method:

@Transactional(isolation = Isolation.SERIALIZABLE, timeout = 30, readOnly = true)
public int checkStock(String isbn) { ... Utils.sleep via Thread.sleep(10000) ... }

timeout = 30 is not a watchdog that aborts a slow transaction. For DataSourceTransactionManager it is carried into the TransactionDefinition and applied as a JDBC statement timeout by DataSourceUtils.applyTransactionTimeout on statements that participate in the transaction; time spent in Java between statements — such as the 10-second sleep inside checkStock — is not metered, so the shipped bodies cannot reach 30 seconds of database work and the timeout never fires. readOnly = true becomes Connection.setReadOnly(true); Spring does not police it, so writing from a read-only transaction is refused by the driver and the database, or accepted, depending on the pair you are using. It is an optimisation hint, not a security boundary.

Walking the rules. Start at the top: a caught exception is a committed transaction. That is why recipe_7_6_i's checkout must not catch anything — the moment it swallows a purchase failure, the surviving writes commit. Then the two annotation-derived lists are consulted before the default rule, which is the counter-intuitive part: rollbackFor and noRollbackFor do not merely refine the default, they can reverse it in both directions, and the COMMIT leaf on the noRollbackFor branch is the one that costs money. Only if neither list matches does the platform default apply — RuleBasedTransactionAttribute.rollbackOn returns true for RuntimeException and Error, false for anything else. The bottom-right node keeps the picture honest: the rollback rules declared in 7.8 and 7.9 are never triggered by their own code paths, so if you run those modules you are watching the unchecked default branch, not the attribute you configured. And note the "rethrow" at both exits — the proxy changes the transaction outcome, never the exception identity, so Main's catch still has to name the right type.

Recipe 7.10 — ch07/recipe_7_10_i, plus the XML in ch07/recipe_7_7_*

Recipe 7.10 — AspectJ weaving, and the XML nobody loads

recipe_7_10_i's configuration is three lines different from 7.9's:

@Configuration
@EnableTransactionManagement(mode = AdviceMode.ASPECTJ)
@EnableLoadTimeWeaving
public class BookstoreConfiguration { ... }

AdviceMode.ASPECTJ makes the annotation registrar import the AspectJ configuration instead of the proxy one, so there is no TransactionInterceptor advisor and no JDK proxy: AnnotationTransactionAspect is woven into BookShopCashier and JdbcBookShop as they are loaded, and the beans the container hands back are plain instances. That buys two things the proxy cannot give — self-invocation inside a bean is advised, and non-public methods can be — at the price of a JVM-level requirement, spelled out in ch07/recipe_7_10_i/src/main/java/com/apress/spring6recipes/bookshop/Main.java's javadoc: run with -javaagent:build/lib/spring-instrument-6.0.x.jar so that InstrumentationLoadTimeWeaver can hand the JVM's Instrumentation to AspectJ. Without the agent the weaving silently does not happen and the annotations do nothing. ch07/build.gradle is what adds spring-aspects, spring-instrument and aspectjweaver to this one module.

The three XML files under ch07/recipe_7_7_*/src/main/resources/ are byte-identical across all five 7.7 modules and are loaded by nothing — no class in ch07 mentions ClassPathXmlApplicationContext or any of the three filenames, and every Main builds an AnnotationConfigApplicationContext over BookstoreConfiguration. They are reference material rather than live configuration: spring-beans.xml is the declarative equivalent of 7.5 (<tx:annotation-driven/>, pointing at jdbc:derby://localhost:1527/bookshop with org.apache.derby.jdbc.ClientDriver, which is not on the ch07 classpath); aspectj-beans.xml is the XML form of 7.10 (<tx:annotation-driven mode="aspectj"/> with <context:load-time-weaver/> and <context:spring-configured/>); and classic-beans.xml is the pre-annotation style, hand-wrapping each target in a TransactionProxyFactoryBean.

Reading the two lanes. The left lane is what happens when Main asks for BookShop.class in 7.5–7.9: the auto-proxy creator post-processes the bean definition, the advisor's pointcut finds the @Transactional method, and the container hands back a java.lang.reflect.Proxy — which is why a request for the concrete JdbcBookShop type would fail and why bookShop.purchase(...) called from inside JdbcBookShop itself would not be advised. The right lane removes the container from the loop: the weaving happens at class-load time, driven by an Instrumentation instance that only the -javaagent can supply, so the advice is unconditional on how the object was created. That is the honest trade the recipe makes, and the reason 7.10's purchase can safely be REQUIRED. The dashed edge at the bottom records a dead path: classic-beans.xml would have wired cashier's bookShop property to bookShopTransactional (a TransactionProxyFactoryBean with PROPAGATION_REQUIRES_NEW on purchase) — which is 7.6_iii's propagation expressed in XML — but BookShopCashier has a final field and a constructor and no setter, and JdbcBookShop has no default constructor, so that file would not start even if something loaded it.

7.10 is the quiet regression to watch

recipe_7_10_i copies 7.9's purchase but changes REQUIRES_NEW to REQUIRED. Combined with checkout's REQUIRED, the whole checkout is once again a single transaction — the same topology as 7.6_i, reached by a different mechanism. So the AspectJ recipe tests where the advice comes from, not the propagation, and its data outcome differs from 7.9_i, where each purchase commits alone.

Practice

Running the recipes

1. Database first — nothing in the chapter creates it

Every ch07 configuration points at jdbc:postgresql://localhost:5432/bookstore with postgres / password. The repo's own helpers do not provision that database: bin/postgres.sh starts a container with POSTGRES_DB=vehicle and bin/docker-compose-all.yml uses POSTGRES_DB=vehicles with a ch09 vehicle.sql init script. So no ConnectionFactoryInitializer and no gradle task will build the schema for the JDBC recipes — you run it yourself:

docker run --name s6r-postgres -e POSTGRES_PASSWORD=password -p 5432:5432 -d postgres:14-alpine
docker exec -it s6r-postgres psql -U postgres -c 'CREATE DATABASE bookstore'
docker exec -i s6r-postgres psql -U postgres -d bookstore < ch07/recipe_7_1_i/src/main/resources/bookstore.sql

The bookstore.sql files are identical in all 17 modules except recipe_7_3_i and recipe_7_5_i, which use CREATE TABLE IF NOT EXISTS so their reactive initializer can re-run. They do not drop or truncate, so a second run does not reset BALANCE and STOCK — re-seed between recipes or you will be reading leftovers.

2. Build

./gradlew :ch07:recipe_7_5_i:build          # compile one module
./gradlew :ch07:build                        # the whole chapter
./gradlew :ch07:recipe_7_6_iii:uberJar       # runnable fat jar

Module paths come from settings.gradle, which includes every recipe_* directory it walks, so ch07:recipe_7_6_iii is the real project path. ch07/build.gradle gives all ch07 subprojects spring-context, spring-jdbc and the PostgreSQL driver, adds spring-r2dbc plus r2dbc-postgresql to 7.3, 7.4 and 7.5, adds spring-aspects, spring-instrument and aspectjweaver to 7.10, and sets Main-Class to com.apress.spring6recipes.bookshop.Main on every uberJar. There is no application plugin and no run task in this repository, and no module has tests, so build means "compile". Java 19 is the configured toolchain in the root build with --enable-preview on compile, test and exec, and spring-6-recipes-dependencies/build.gradle pins the Spring version to 6.0.3 through spring-framework-bom. One machine-specific trap: gradle.properties hard-codes org.gradle.java.home=C:/Program Files/Java/jdk-17.0.4.1, so if that JDK is not where it says, Gradle will not even start — override it with -Dorg.gradle.java.home=... or your own ~/.gradle/gradle.properties.

3. Run

java -jar ch07/recipe_7_6_iii/build/libs/recipe_7_6_iii-6.0.0-SNAPSHOT-all.jar

Then inspect the damage, which is the actual output of every recipe in this chapter:

docker exec -it s6r-postgres psql -U postgres -d bookstore \
  -c 'SELECT * FROM BOOK_STOCK' -c 'SELECT * FROM ACCOUNT'
  • 7.1_i leaves STOCK = 9, BALANCE = 20; every other module leaves both at their seeded values, because the balance update fails on positive_balance before anything can commit. To see the happy path you must fund the account: UPDATE ACCOUNT SET BALANCE = 100 WHERE USERNAME = 'user1' and insert the second book the checkout recipes ask for, INSERT INTO BOOK (ISBN, BOOK_NAME, PRICE) VALUES ('0002','The Second Book', 10) with matching BOOK_STOCK. Without that, 7.6_i and 7.6_iii produce the same visible result and the propagation difference stays hypothetical.
  • 7.7, 7.8, 7.9 are timed, not instant: each transactional body sleeps 10 seconds and Main staggers the threads by 5, so expect roughly 15–20 seconds of console output per run and no exit code to read. Their exceptions are swallowed by design (catch (RuntimeException e) { }), so the printed "Book stock rolled back" line is your only signal.
  • 7.10 needs the agent or nothing happens. spring-instrument is a runtime dependency of this module, not something uberJar leaves lying around as a standalone jar, so take it from the Gradle cache and pass it before -jar: java -javaagent:"$HOME/.gradle/caches/modules-2/files-2.1/org.springframework/spring-instrument/6.0.3/spring-instrument-6.0.3.jar" -jar ch07/recipe_7_10_i/build/libs/recipe_7_10_i-6.0.0-SNAPSHOT-all.jar. That is the instruction the module's own Main javadoc gives (-javaagent:build/lib/spring-instrument-6.0.x.jar, assuming you collected the dependency jars there yourself). Without the agent the annotations are inert and the writes commit as in 7.1_i.
  • 7.2 does not exist as a module; if you are following the book, the XML it describes is in ch07/recipe_7_7_*/src/main/resources/ and is inert, as explained in Recipe 7.10.

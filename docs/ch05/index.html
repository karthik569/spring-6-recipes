Chapter 5 — Spring Security

The chapter takes one application — a to-do board — and adds security to it in increments: first the bare @EnableWebSecurity defaults, then the authentication entry point, then where the users actually come from, then how access rules are expressed, and finally per-object ACLs and the reactive equivalent. Every servlet recipe is a war module that depends on ch05/recipe_5_shared and changes nothing except com.apress.spring6recipes.board.security.TodoSecurityConfig, so the diffs between recipes are exactly the diffs between configuration calls. The one thing to hold in your head is that a Spring Security configuration is not a set of rules — it is a factory for a servlet filter chain, and the rules are read by a single filter at the end of it.

What the chapter builds

The domain object is com.apress.spring6recipes.board.Todo — id, owner, description, completed — persisted by ch05/recipe_5_shared/src/main/java/com/apress/spring6recipes/board/JdbcTodoRepository.java against an embedded H2 database named todos. TodoController is mapped to /todos and renders Thymeleaf templates that also live in the shared module, including templates/login.html and templates/logout-success.html. Because the shared module is a java-library, its templates and its schema.sql/data.sql land on the WAR classpath and are picked up by TodoWebConfig via the classpath:/templates/ prefix.

Nothing about the application changes between recipes. What changes is one class per module: …/board/security/TodoSecurityConfig.java. That makes the chapter unusually diagrammable — each recipe is a distinct shape of the filter chain, not a distinct program. Four clusters emerge from the source:

  • 5-1 to 5-3 — the chain and its entry points: defaults, HTTP Basic versus form login, a custom login page, logout, and the user store (in-memory, JDBC, custom SQL, BCrypt, LDAP).
  • 5-4 to 5-5 — how access rules are expressed: custom AuthorizationManagers, SpEL strings, bean references in SpEL, and method-level @Secured/@PreAuthorize/@PostFilter.
  • 5-6 to 5-7 — a leftover Spring Security 5 configuration style, and ACLs.
  • 5-8 — the same ideas on ServerHttpSecurity with WebFlux and R2DBC.

Three things the source does not contain

No recipe in ch05/ configures remember-me, OAuth2/OpenID Connect or JWT resource server support, or a custom jakarta.servlet.Filter/AuthenticationEntryPoint. Grepping the chapter for rememberMe, oauth2, jwt, OncePerRequestFilter and addFilterBefore returns nothing but the logoutSuccessUrl hits. Those topics belong to other chapters; the diagrams below describe only what is actually wired here.

Two more source-level gaps worth knowing before you run anything: the custom JDBC queries in 5-3-iii onwards read member and member_role, and no schema.sql anywhere in ch05/ creates those tables — only USERS, AUTHORITIES and the ACL_* set. And recipe_5_5_iii and recipe_5_6_i subclass WebSecurityConfigurerAdapter and call antMatchers(...), both of which were removed from spring-security-config:6.0.1 (verified against the jar: HttpSecurity.authorizeRequests() survives but AbstractRequestMatcherRegistry now only offers requestMatchers), so those two modules do not compile in this repository as pinned.

How security enters a servlet application

There is no web.xml in this chapter. Two WebApplicationInitializer subclasses, both in recipe_5_shared and each recipe respectively, do the registering at container startup, and the order they register in is the order requests pass through them. TodoWebInitializer extends AbstractAnnotationConfigDispatcherServletInitializer and maps TodoWebConfig to the DispatcherServlet with getRootConfigClasses() returning null — so there is no root web application context at all. TodoSecurityInitializer extends AbstractSecurityWebApplicationInitializer and creates its own AnnotationConfigWebApplicationContext registering WebSecurityConfiguration.

The interesting detail is the difference between the recipes here. All of 5-1 to 5-5-ii and 5-7 use the no-argument form of AbstractSecurityWebApplicationInitializer, and rely on TodoSecurityConfig being reachable as a @Configuration — which it is, because it sits in com.apress.spring6recipes.board.security and TodoWebConfig declares @ComponentScan("com.apress.spring6recipes.board"). Only recipe_5_5_iii and recipe_5_6_i pass it explicitly, with super(TodoSecurityConfig.class) in the initializer's constructor.

Reading the wiring. SpringServletContainerInitializer (contributed by spring-web) finds both initializers on the WAR classpath. The security one calls onStartup, which registers a DelegatingFilterProxy under the literal name springSecurityFilterChain and stores the context it created under a ServletContext attribute — those two strings are the only hard-coded facts in AbstractSecurityWebApplicationInitializer, and the proxy resolves the real FilterChainProxy lazily by bean name. The web one registers DispatcherServlet plus the servlet filters from getServletFilters(), which in this chapter is exactly HiddenHttpMethodFilter. TodoWebConfig then contributes @EnableWebMvc, @EnableTransactionManagement, the Thymeleaf view resolver, the embedded DataSource and a DataSourceTransactionManager. One consequence worth holding on to: HiddenHttpMethodFilter rewrites POST plus _method=DELETE into a real DELETE request, and it runs inside the servlet registration, while the security proxy is registered against the context. Since AuthorizationFilter only ever sees the method it is handed, the relative order of these two registrations decides whether requestMatchers(HttpMethod.DELETE, "/todos/*") can match the deletes the templates actually emit. Neither initializer declares an @Order, so do not assume it.

@EnableWebSecurity is what turns the plain @Configuration into the bootstrap. It imports WebSecurityConfiguration (the springSecurityFilterChain bean itself), HttpSecurityConfiguration (the request-scoped HttpSecurity prototype the recipes' securityFilterChain(HttpSecurity) method receives), AuthenticationConfiguration, and — via SpringWebMvcImportSelector, only when DispatcherServlet is on the classpath — WebMvcSecurityConfiguration. That last one is why <form th:action> in the shared templates silently acquires a hidden _csrf input: it registers a RequestDataValueProcessor, plus the argument resolvers behind @AuthenticationPrincipal.

The security filter chain

This is the chapter's defining structure. HttpSecurity is a builder whose output is a java.util.List<jakarta.servlet.Filter>; the order is not the order you write the DSL calls but a fixed table in FilterOrderRegistration. The numbers below are read out of spring-security-config-6.0.1 itself, and the presence of each filter is traced to the DSL call in the recipes — httpSecurity() applies csrf, logout, exceptionHandling, requestCache, securityContext, servletApi, sessionManagement, headers, anonymous and DefaultLoginPageConfigurer without being asked, which is why recipe_5_1_ii's empty class is not "no security" but "the whole chain with every URL protected".

Walking the arrows. FilterChainProxy.doFilter runs the list once, guarded by its own firewalledRequest wrapper. SecurityContextHolderFilter (600) pulls a SecurityContext out of the session through SecurityContextHolderFilter's repository and puts it in the holder before anything downstream, and clears it in a finally. CsrfFilter (1000) rejects any state-changing method whose _csrf parameter does not match the token in the HttpSessionCsrfTokenRepository — wrapped in a LazyCsrfTokenRepository by default — which is precisely what recipe_5_1_iii opts out of with http.csrf().disable() and what recipe_5_1_iv opts back into with csrfTokenRepository(new CookieCsrfTokenRepository()). UsernamePasswordAuthenticationFilter (1900) acts only on POST /login; every other request falls through. DefaultLoginPageGeneratingFilter (2100) only serves GET /login when no custom login page was configured — in 5-2-iii onward loginPage("/login") takes over and the generated page steps aside, which is why /login there resolves through TodoSecurityConfig.addViewControllers instead. AnonymousAuthenticationFilter (3100) is the reason the holder is never empty: if nothing authenticated, it installs an AnonymousAuthenticationToken. That matters because AuthorizationFilter (3600) is the last filter — it sits below ExceptionTranslationFilter (3400) deliberately, so that the exceptions it throws on its way back up are converted into a 302 or a 403 rather than escaping to the container. Read the two dotted edges as the actual control flow of a denied request: 3600 throws, 3400 catches.

recipe_5_1_ii is the sharpest illustration. Its entire configuration is ch05/recipe_5_1_ii/src/main/java/com/apress/spring6recipes/board/security/TodoSecurityConfig.java — @Configuration @EnableWebSecurity public class TodoSecurityConfig { }. No SecurityFilterChain bean, no user store. The request-scoped HttpSecurity still gets all nine default configurers, so AuthorizationFilter denies everything that is not permitted by rule and there is no rule, and with no UserDetailsManager bean AuthenticationConfiguration generates a single random password user at startup.

Authenticating a submission

Form login is a POST to a URL that no controller owns. In every recipe from 5-2-iii onward that URL is /login, the form is ch05/recipe_5_shared/src/main/resources/templates/login.html, and the parameter names are the defaults username and password. Three settings on FormLoginConfigurer drive the outcome: defaultSuccessUrl("/todos") from 5-2-iv, failureUrl("/login?error=true"), and the loginPage("/login").permitAll() pair that both points the entry point at the custom page and adds the permit-all rule.

Walking the hops. UsernamePasswordAuthenticationFilter.attemptAuthentication reads the two parameters and produces an unauthenticated UsernamePasswordAuthenticationToken; the filter then calls this.getAuthenticationManager().authenticate(...), which in these recipes is the AuthenticationManager that AuthenticationConfiguration derives from the single UserDetailsManager bean — a ProviderManager holding one DaoAuthenticationProvider. That provider does two things in order: retrieveUser through the UserDetailsService half of the manager, then additionalAuthenticationChecks through the PasswordEncoder. On success the SessionAuthenticationStrategy chain runs before the context is saved — CsrfAuthenticationStrategy migrates the CSRF token and SessionManagementAuthenticationStrategy records the session — which is why the JSESSIONID changes between the login POST and the redirect. On the failure branch the exception never reaches the container: AbstractAuthenticationProcessingFilter catches it, publishes it as an AuthenticationFailureEvent, stores it in the session under SPRING_SECURITY_LAST_EXCEPTION, and hands over to the failure handler. That session attribute is what the template reads: ${session.SPRING_SECURITY_LAST_EXCEPTION.message} inside the th:if="${param.error != null}" block in login.html — a contract between the failure handler and the view that is easy to miss because neither side mentions the other.

Logout is the mirror image and is only configured from 5-3-i onward: http.logout().logoutSuccessUrl("/logout-success").permitAll(). LogoutFilter sits at order 1100, upstream of everything, and delegates to SecurityContextLogoutHandler (invalidate the session, clear the holder) and CsrfLogoutHandler, then to SimpleUrlLogoutSuccessHandler pointed at the view-controller registered for /logout-success.

What each state means in code. Anonymous is not "no authentication" — AnonymousAuthenticationFilter has installed an AnonymousAuthenticationToken named anonymousUser, and AuthorizationFilter's manager sees it as lacking USER. Authenticating is a single request, not a dwell state; it exists only inside UsernamePasswordAuthenticationFilter.doFilterInternal. Authenticated means a SecurityContext with a real token has been written to the session by SecurityContextRepository, and it persists across requests until it expires or logout runs — the two arrows leaving it. Note what is deliberately absent: there is no RememberMeAuthenticationFilter state anywhere in this chapter, because no recipe calls http.rememberMe(); the fifth state the book discusses for other applications simply is not exercised here.

Principals, authorities, roles

Every recipe in the chapter seeds the same three principals, and the vocabulary choice across the recipes is the point. They are built with User.withDefaultPasswordEncoder().username(...).password(...).authorities("USER", "ADMIN") and — from 5-3-i — keyed by e-mail address rather than by short name, so the principal name doubles as the Todo.owner value that TodosController writes and that recipe_5_5_ii's @PostAuthorize later compares against authentication.name.

The distinction the recipes draw repeatedly is authority versus role. authorities("USER") stores the literal string USER, which hasAuthority("USER") matches exactly. hasRole('ROLE_ADMIN'), as used in the SpEL strings of recipe_5_4_ii and recipe_5_4_iii, strips a configured prefix before comparing — so it only matches an authority literally called ROLE_ADMIN, which none of these users have. That is a real trap in those two recipes and it is visible straight from the source: the same config that grants USER/ADMIN as authorities tests for a prefixed role.

Reading the graph. The left-hand branch is the store side: UserDetailsManager extends UserDetailsService, which is why a single bean method can both authenticate and administer — and why 5-3-ii's initializeUsers can call users.createUser(user1) on the same object that DaoAuthenticationProvider later calls loadUserByUsername on. recipe_5_1_iii returns the interface type UserDetailsManager from a bean method whose body constructs InMemoryUserDetailsManager; 5-3_ii swaps only the constructor argument from two Users to the injected DataSource. The right-hand branch is the request side: after a successful authentication the UsernamePasswordAuthenticationToken stores the UserDetails as its principal (or the username string, if hideUserDetails is set, which it is not here) and copies the authorities across. WebAuthenticationDetails is the field that makes recipes 5-4 possible at all — LocalhostAuthorizationManager.check and AccessChecker.hasLocalAccess both pattern-match authentication.getDetails() against it to reach getRemoteAddress(), and it is populated automatically by WebAuthenticationDetailsSource on the login filter, not by anything in this chapter. MapReactiveUserDetailsService implements UserDetailsService too, which is how 5-8 keeps the same seeds while the rest of the stack goes reactive.

Where the users come from

Five backends appear across the chapter, and swapping between them is a one-bean edit. The JDBC family is where the reading pays off: recipe_5_3_ii uses JdbcUserDetailsManager with Spring Security's default SQL against USERS and AUTHORITIES — tables that recipe_5_shared/src/main/resources/schema.sql does create — while recipe_5_3_iii overrides both queries to read member and a member/member_role join, and keeps calling createUser, which still writes to users/authorities. That asymmetry is the recipe's lesson as much as its bug: reads and writes on JdbcUserDetailsManager are configured separately.

Reading the branches. The first three subgraphs all terminate in DaoAuthenticationProvider, and AuthenticationConfiguration finds the UserDetailsManager bean by type — that autowiring is why none of these recipes mentions a provider, an AuthenticationProvider bean or an AuthenticationManagerBuilder anywhere; the only explicit manager in the chapter is the LDAP one. Password encoding is the other injected collaborator: 5-3-iv adds a BCryptPasswordEncoder bean and that is the entire diff against 5-3-iii, because GlobalAuthenticationConfigurerAdapter picks up a single PasswordEncoder bean and hands it to the provider — which is also why recipe_5_5_iii and recipe_5_6_i, from the adapter era, have to wire it by hand with auth.jdbcAuthentication().passwordEncoder(passwordEncoder()).dataSource(dataSource()). The LDAP branch replaces the provider rather than the store: 5-3-v builds a context source over ldap://ldap-server:389/dc=spring6recipes,dc=com, points userDnPatterns("uid={0},ou=people") at the entries in ch05/recipe_5_3_v/src/main/resources/ldap/users.ldif, and sets populator.setRolePrefix("") so the group cn values admin and user become authorities verbatim and can satisfy hasAuthority("ADMIN") unchanged. Its authenticationManager bean is then consumed by the form-login filter, and docker-compose.yml in the same module maps the OpenDS container's 389 to host 1389 and links it as the hostname ldap-server — the URL above only resolves inside that compose network.

The authorisation decision

authorizeHttpRequests does not produce a filter per rule. It produces one AuthorizationFilter holding an ordered list of RequestMatcher/AuthorizationManager pairs, and the decision is first-match-wins. The rules the recipes declare are, in order: requestMatchers(HttpMethod.DELETE, "/todos/*").hasAuthority("ADMIN"), then requestMatchers("/todos", "/todos/*").hasAuthority("USER"). Everything else — /login, /logout — is permitted by the DSL calls that configure those screens, and there is no anyRequest() clause in any recipe, so unlisted URLs fall to the default deny.

Walking the decision. AuthorizationFilter asks its RequestMatcherDeferredRegister-built list for the first entry whose matcher accepts the request, then calls AuthorizationManager.check(Supplier, RequestEntry) and inspects the returned AuthorizationDecision; a null or false decision throws AccessDeniedException. The supplier is lazy on purpose — an anonymous user does not pay for expression evaluation at all. The three variants in 5-4 are three different answers to the same sentence. recipe_5_4_i composes managers: AuthorityAuthorizationManager.hasAuthority short-circuits, then LocalhostAuthorizationManager.check pattern-matches authentication.getDetails() as WebAuthenticationDetails and string-compares getRemoteAddress(). recipe_5_4_ii hands the same predicate to SpEL as "hasRole('ROLE_ADMIN') and (hasIpAddress('127.0.0.1') or hasIpAddress('0:0:0:0:0:0:0:1'))" through WebExpressionAuthorizationManager, which evaluates it against a WebSecurityExpressionRoot. recipe_5_4_iii swaps the inline IP test for a bean reference — @accessChecker.hasLocalAccess(authentication) — resolved through the BeanResolver that WebMvcSecurityConfiguration contributes, so AccessChecker, a plain @Component, becomes part of the authorisation rule while keeping the and spelling of the expression language. recipe_5_4_ii additionally carries ExtendedWebSecurityExpressionHandler and ExtendedWebSecurityExpressionRoot adding a localAccess() method — but note that its TodoSecurityConfig never registers that handler and writes the predicate inline instead, so the extension is present in the module and unused. That is the honest reading of the source, not an oversight in this page.

hasRole is not hasAuthority

recipe_5_4_ii and recipe_5_4_iii ask for hasRole('ROLE_ADMIN') while every seeded principal carries the authority ADMIN. hasRole prepends a role prefix (default ROLE_) to its argument and compares against the authority list, so the argument should have been 'ADMIN', not 'ROLE_ADMIN'. Every DELETE in those two recipes takes the deny branch regardless of who issues it from where. Recipes 5-1, 5-2, 5-3, 5-5 and 5-7 all use hasAuthority("ADMIN") and are unaffected.

Method security

URL rules stop at the controller boundary; a TodoService injected anywhere else would not pass through AuthorizationFilter at all. Recipes 5-5 add @EnableMethodSecurity and put the rules on the implementation. The annotation you enable determines the interceptor chain registered for you: securedEnabled = true in recipe_5_5_i, prePostEnabled = true in recipe_5_5_ii and recipe_5_5_iii.

Walking the hops. @EnableMethodSecurity imports MethodSecuritySelector, which picks SecuredMethodSecurityConfiguration or PrePostMethodSecurityConfiguration according to the flags and registers an auto-proxy advisor over TodoServiceImpl — the class is package-private and annotated @Service, so the bean is proxied by interface through TodoService. The before-advice is AuthorizationManagerBeforeMethodInterceptor; the after-advice, present only for @PostAuthorize and @PostFilter, is AuthorizationManagerAfterMethodInterceptor and PostFilterAuthorizationMethodInterceptor. Because the decision is made before the join point, a denial never touches the database — hop 8 returns without ever calling findAll(). Differences between the three variants, from the source: recipe_5_5_i uses @Secured with bare authority strings, and on remove lists { "USER", "ADMIN" }, which SecuredAuthorizationManager treats as any-of; recipe_5_5_ii adds @PostAuthorize("returnObject.owner == authentication.name") on findById, whose signature still returns an Optional because that is what the shared TodoService declares — so returnObject is the Optional, not the Todo inside it; recipe_5_5_iii changes that method to return Todo while leaving @Override on it, and puts the filtering expression shown at hop 12 on listTodos instead. recipe_5_7_i keeps the same interceptors and merely changes the expressions to hasPermission(...), which is the door into the next section.

Two caveats the recipes do not address. First, self-invocation: complete(long id) calls findById(id) on this, so the annotated method is entered without the proxy and its security annotation is not consulted for that internal hop. Second, recipe_5_5_i and recipe_5_5_ii redefine TodoServiceImpl in their own source set, shadowing the shared module's class of the same fully-qualified name, which is what makes the annotations take effect at all. recipe_5_5_iii does neither cleanly: its findById returns Todo against an interface method declared Optional<Todo> (and it drops the java.util.Optional import while still returning todoRepository.findOne(id)), and its configuration extends WebSecurityConfigurerAdapter — so method security is only buildable as written in 5-5-i and 5-5-ii.

Per-object ACLs

Recipe 5-7-i is the only module in the chapter that reaches beyond roles to per-row permissions. It adds spring-security-acl in ch05/build.gradle, ships the four ACL_SID/ACL_CLASS/ACL_OBJECT_IDENTITY/ACL_ENTRY tables in its own schema.sql, and wires the ACL object graph in a second configuration class, TodoAclConfig. ehcache.xml is present in the module and declares a cache named aclCache, but the configuration uses CaffeineCacheManager — the EhCache file is a leftover from an earlier edition.

Reading the dependencies. The constructor of TodoAclConfig takes the DataSource that recipe_5_shared's TodoWebConfig.dataSource() produces, so ACL state lives in the same H2 database as the to-do rows. BasicLookupStrategy is the read path — it joins the four ACL_* tables and populates SpringCacheBasedAclCache, whose PermissionGrantingStrategy is a DefaultPermissionGrantingStrategy wrapping a ConsoleAuditLogger, so every allow and deny prints. JdbcMutableAclService is the write path and is what TodoServiceImpl.save calls: it builds an ObjectIdentityImpl(Todo.class, todo.getId()) and then six insertAce calls, granting READ, WRITE and DELETE to a PrincipalSid of the new owner's name and the same three to a GrantedAuthoritySid("ADMIN"). The link that makes hasPermission work at all is the quiet one: TodoServiceImpl never references AclPermissionEvaluator, but GlobalMethodSecurityConfiguration.afterSingletonsInstantiated looks up a PermissionEvaluator bean by type and calls setPermissionEvaluator on the DefaultMethodSecurityExpressionHandler — so the bean named permissionEvaluator here is what makes hasPermission(filterObject, 'read') resolve to an ACE lookup rather than failing. AclEntryVoter, with the attribute ACL_MESSAGE_DELETE, is the legacy voting path and is not referenced by any annotation in the module.

The module also contains a bug worth naming: the @PreAuthorize expressions on complete and remove pass the type string 'com.apress.springrecipes.board.Todo', while the class is com.apress.spring6recipes.board.Todo. ObjectIdentityImpl resolves that string reflectively, so those two methods would fail on a class-not-found rather than on a permission decision, whereas the @PostFilter on listTodos passes the Todo object itself and is immune.

Reactive security

The 5-8 modules drop the WAR, the servlet API and the shared module entirely: WebFluxConfiguration plus ReactorNettyBootstrap.main() start an HttpServer on localhost:8080 directly, and persistence goes through DatabaseClient over r2dbc:h2:mem:///todos. Security moves with them: @EnableWebFluxSecurity instead of @EnableWebSecurity, ServerHttpSecurity instead of HttpSecurity, and a SecurityWebFilterChain instead of a SecurityFilterChain — the same shape, but the reactive chain is WebFilters over Monos, so AuthenticationWebFilter, CsrfWebFilter, SecurityContextServerWebExchangeWebFilter, ReactorContextWebFilter, ExceptionTranslationWebFilter and AuthorizationWebFilter replace their servlet counterparts.

Walking the progression. 5-8-i is the reactive twin of recipe_5_1_ii: @EnableWebFluxSecurity alone, so ServerHttpSecurity applies its own defaults, every exchange is denied, and MapReactiveUserDetailsService supplies users marten/secret and admin/admin — note these are short names, not the e-mail principals of the servlet recipes. 5-8-ii adds the springWebFilterChain(ServerHttpSecurity) bean returning http.httpBasic().and().build(), which puts an AuthenticationWebFilter with a ServerHttpBasicAuthenticationConverter in front of AuthorizationWebFilter. 5-8-iii changes one word to http.formLogin(), and the two modules then share the rest of their code: a securityPages RouterFunction in WebFluxConfiguration serving GET /login from the template, wrapped in a HandlerFilterFunction that copies the CsrfToken out of the exchange attributes so Thymeleaf can render it, plus SecurityControllerAdvice doing the same via @ModelAttribute. 5-8-iv switches to the lambda form throughout — formLogin((f) -> f.loginPage("/login")), csrf(ServerHttpSecurity.CsrfSpec::disable), authorizeExchange((auth) -> auth.pathMatchers("/login").permitAll()) — and so drops the need for the CSRF router filter, which is why its securityPages builds the route without .filter(csrfToken()) even though the method is still defined. 5-8-v is the one to read closely: it re-enables CSRF on a CookieServerCsrfTokenRepository, adds pathMatchers("/todos").hasAuthority("USER"), and replaces the delete rule with .access(this::todoRemoveAllowed) — a method returning Mono<AuthorizationDecision>, exactly the reactive AuthorizationManager contract that LocalhostAuthorizationManager implements on the servlet side. Inside it, isOwner reads the id exchange-primitive variable and calls todoService.findById(id)... ending in .block(). That blocking call on a WebFlux worker is in the source, not in this description of it, and it is the reason 5-8-v is the end of the progression rather than a template.

Building and running the recipes

Every module is a Gradle project in the root settings file, addressed as :ch05:recipe_5_x_y. The chapter's build script applies war, com.palantir.docker and com.palantir.docker-run to every recipe module except the shared one, and the 5-8 modules additionally skip the servlet dependencies.

# compile one recipe (shared module is built as a dependency)
./gradlew :ch05:recipe_5_3_iv:build

# the chapter's declared default task for each recipe is clean + build
./gradlew :ch05:recipe_5_1_iii

# jar the whole thing up if you want to run it outside Gradle
./gradlew :ch05:recipe_5_3_iv:uberJar

# 5-8-x has no war to deploy: it is a plain main class on Reactor Netty
./gradlew :ch05:recipe_5_8_v:run 2>/dev/null || \
  java -cp "$(ls ch05/recipe_5_8_v/build/libs/*all.jar)" com.apress.spring6recipes.todo.ReactorNettyBootstrap

Deploying a servlet recipe

Non-5-8 recipes produce todos.war — the name is forced by war { archiveFileName = 'todos.war' } in ch05/build.gradle so that ch05/Dockerfile can copy it to ROOT.war. That Dockerfile downloads apache-tomcat-10.0.27 onto eclipse-temurin:19-jdk-alpine, deletes the default webapps, exposes 8080 and 5005 for JDWP, and runs catalina.sh run. The dockerRun block maps 8080:8080 and names the container s6r-todos-security-<module> from image s6r/todos-security:<module>, so:

Two notes on the toolchain. The root build pins a Java 19 toolchain and --enable-preview for every recipe module, and gradle.properties hard-codes org.gradle.java.home to a single machine's JDK 17 path — drop that line if your JDK lives elsewhere. And dockerRun will fail on any port already taken, so only one recipe at a time.

Chapter 12 — Spring Integration

Seventeen small console applications that put the enterprise integration patterns on Spring's own message bus: @EnableIntegration, a Java DSL IntegrationFlow bean, and endpoints (adapters, transformers, splitters, aggregators, routers, gateways) wired through channels. Every recipe is driven by one of three triggers — a JMS message into ActiveMQ Artemis, a file dropped into a directory the flow polls, or a method call on a gateway interface.

Mental model

Overview and module map

Each module is the same shape: one @Configuration @EnableIntegration class, one or more @Bean IntegrationFlow methods built with the fluent DSL, one or more annotated POJOs holding the business method (@Transformer, @ServiceActivator, @Splitter, @Router), and a Main that opens an AnnotationConfigApplicationContext and then either blocks on System.in.read() or sends a trigger. There is no web container and no XML: grep the chapter and the only Spring descriptors are Java annotations.

Two toy domains carry all the traffic. The Customer record (id, firstName, lastName, telephone, creditScore) recurs across the JMS, file, transform, split and route recipes; the myholiday package (VacationService, HotelReservationSearch, HotelReservation) carries the request-reply gateway recipe. Messages are Spring Integration messages — org.springframework.messaging.Message with a payload plus a header map — never raw JMS or file objects for long.

Where this chapter stops and chapters 10 and 11 start

The three chapters share a broker and a vocabulary, so the boundary is worth fixing from the build files rather than from the chapter titles:

  • Only ch12/build.gradle declares Spring Integration. It adds spring-integration-core to every subproject, spring-integration-jms to the JMS recipes, spring-integration-file to the file recipes, and spring-batch-integration to recipe_12_9. The platform comes from spring-integration-bom:6.0.0 in spring-6-recipes-dependencies/build.gradle.
  • Chapter 11 is plain spring-jms. Its post-office recipes use JmsTemplate, JmsGatewaySupport, @JmsListener with @EnableJms, and custom MessageConverters. No flows, no channels, no Message abstraction.
  • Chapter 10 is the older "enterprise integration" toolkit — JMX, @Scheduled, JavaMailSender, WebServiceTemplate, remoting — not messaging at all.
  • Verification: org.springframework.integration and org.springframework.messaging are imported by Java files in ch12/ only; a grep over ch10, ch11, ch13 and ch14 returns nothing. Chapter 12 is the only Spring Integration chapter in this repository, even though chapter 10's description line reads "Spring Enterprise Integration".

Reading the flow. Read the clusters in that order: every later recipe reuses the adapter and transformer vocabulary of the earlier ones.

Recipe 12-2

Consuming JMS messages: the adapter decides the payload

recipe_12_2_i/src/main/java/.../IntegrationConfiguration.java defines three beans and one flow. The connection beans are pure Spring JMS — an ActiveMQConnectionFactory for tcp://localhost:61616 wrapped in a CachingConnectionFactory, plus a JmsTemplate that exists only so Main can produce a message. The interesting line is the flow:

IntegrationFlow
    .from(Jms.messageDrivenChannelAdapter(connectionFactory)
              .extractPayload(true).destination("recipe-12-2"))
    .handle(messageProcessor)
    .get();

Jms.messageDrivenChannelAdapter builds a message-driven (push) source: it wraps a JMS MessageListener on the Artemis queue, so nothing polls. extractPayload is the whole difference between the two variants. With true, the adapter hands Spring Integration the JMS body, and InboundHelloWorldJMSMessageProcessor.handleIncomingJmsMessage receives Message<Map<String, Object>> and logs the map. With false (recipe_12_2_ii), the jakarta.jms.Message itself becomes the payload — the same handler, renamed handleIncomingJmsMessageWithPayloadNotExtracted, casts msgWithJmsMessageAsPayload.getPayload() to MapMessage and rebuilds the map by reading getString("firstName"), getString("lastName"), getLong("id"). Keeping the JMS message is how you reach JMS-only features (properties, JMSCorrelationID, redelivery); extracting the payload is how you stop JMS types leaking into business code. Note that _ii also adds @ComponentScan, which does nothing here — every handler is already declared with an @Bean method.

Reading the flow. Top path: Main.main calls jmsTemplate.convertAndSend("recipe-12-2", customer); the default SimpleMessageConverter turns the Map into a JMS MapMessage; Artemis delivers it to the listener container behind the message-driven channel adapter; the adapter extracts the body and publishes a Spring Message onto the flow's implicit point-to-point channel; the .handle(...) endpoint (a ServiceActivatingMessageHandler created from the @ServiceActivator method) consumes it and returns void, so the flow ends there. Bottom path: identical until the adapter, which with extractPayload(false) skips conversion and puts the raw JMS message in the payload, forcing the handler to do the conversion itself. Caveat visible in the source: in recipe_12_2_ii the flow listens on recipe-16-2 while Main sends to recipe-15-2, so as committed the second variant never receives the message its own producer sends.

Recipes 12-3 and 12-4

Polling a directory and binding message headers

Recipe 12-4 is the file counterpart of 12-2 and shows the other half of the endpoint model. A file adapter cannot push, so the flow adds a consumer-side poller:

IntegrationFlow
    .from(Files.inboundAdapter(directory).patternFilter("*.csv"),
          c -> c.poller(Pollers.fixedRate(Duration.ofSeconds(10))))
    .handle(messageProcessor())
    .get();

The directory is injected with @Value("${user.home}/inboundFiles/new/") File directory and the second .from argument is a Consumer that decorates the endpoint spec — that is how the DSL attaches a SourcePollingChannelAdapter instead of letting the source push. The poller pulls from a FileReadingMessageSource, which lists the directory, applies patternFilter("*.csv") plus its default once-only filter, and returns a java.io.File. That File becomes the message payload, and the adapter decorates it with file headers, which is exactly what recipe 12-3 is about.

Recipe 12-3 ships only the handler class in each module — no IntegrationConfiguration, no Main, nothing under src/main/resources — so the three variants are a study in method signatures the same inbound file message can drive, not runnable programs:

  • recipe_12_3_i: interrogateMessage(Message<File> message) — take the whole message and iterate message.getHeaders().
  • recipe_12_3_ii: interrogateMessage(@Header(MessageHeaders.ID) String uuid, @Header(FileHeaders.FILENAME) String fileName, File file) — two headers injected as parameters, the payload by type.
  • recipe_12_3_iii: interrogateMessage(@Headers Map<String, Object> headers, File file) — the whole header map injected, then headers.get(MessageHeaders.ID) and headers.get(FileHeaders.FILENAME) looked up manually.

All three are annotated @ServiceActivator, so the same bean could be dropped into any .handle(...) slot; Spring Integration's parameter-mapping resolves the message, the payload and the headers by annotation. Recipe 12-4 uses the fourth option — the plain Message<File> form — and reads only the payload.

Reading the flow. Nothing is event-driven here: the operator's only act is writing a file, and the SourcePollingChannelAdapter created by Pollers.fixedRate(Duration.ofSeconds(10)) does the pulling on a task scheduler. When FileReadingMessageSource.receive() returns a File, the adapter publishes GenericMessage with that File as payload and headers that include FileHeaders.FILENAME alongside the standard MessageHeaders.ID; if the source returns null the poller simply produces no message. The handler returns void, so the file is the end of the line — no reply channel is involved.

Reading the diagram. The four classes are the four classes named InboundFileMessageServiceActivator or InboundHelloWorldFileMessageProcessor in the chapter; the two right-hand nodes are not classes in the recipes but the Spring annotations @Header and @Headers that make the argument-level bindings work. The mechanism on every edge is the same: the @ServiceActivator endpoint hands the incoming Message to a MethodInvoker that matches parameters by annotation and type — Message gets the message, a File parameter gets the payload, a String parameter annotated @Header("id") or @Header(FileHeaders.FILENAME) gets that header value (and throws if the header is absent), a Map annotated @Headers gets everything.

Recipe 12-5

Transforming a JMS map into a domain object, headers included

Recipe 12-5 adds one stage to the 12-2 flow and uses it to make a point about Message identity. The flow is .from(Jms.messageDrivenChannelAdapter(...).extractPayload(true).destination("recipe-12-5")).transform(customerTransformer()).handle(customerServiceActivator()). InboundJMSMessageToCustomerTransformer.transformJMSMapToCustomer reads payload.get("id") as a Long, the two names as Strings, and defaults telephone to null and creditScore to 0f with getOrDefault, to build the Customer record.

The variants differ only in the declared return type:

  • recipe_12_5_i returns Customer. Spring Integration wraps the result in a new message, so only the payload survives the stage.
  • recipe_12_5_ii returns Message<Customer>, built explicitly: MessageBuilder.withPayload(customer).copyHeadersIfAbsent(inbound.getHeaders()) .setHeaderIfAbsent("randomlySelectedForSurvey", Math.random() > .5).build(). Returning a Message from a transformer hands the framework your message as-is — that is the only way to preserve or add headers, and 12-5-ii uses it to stamp a routing flag onto the record.

Downstream, both variants land on the identical InboundCustomerServiceActivator.doSomethingWithCustomer(Message<Customer>), which only reads the payload — the header work is therefore invisible until something routes on it (which is exactly what 12-6 and 12-8 then do with exceptions and with a payload field).

Reading the flow. Hop 1, the adapter converts and publishes Message<Map<String, Object>>. Hop 2, the .transform(...) endpoint invokes the @Transformer method; because the parameter type is Message, the whole message is passed and the method has access to getHeaders() — which 12-5-ii needs for copyHeadersIfAbsent. Hop 3 is the fork: a non-Message return (12-5-i) is wrapped in a fresh message by the framework, discarding the inbound headers; a Message return (12-5-ii) is forwarded verbatim. Hop 4, the .handle(...) endpoint calls doSomethingWithCustomer(Message<Customer>), which returns void and therefore ends the flow. Also note the two queue names: recipe-12-5 in variant i and the mistyped but self-consistent recipe-16-5 in variant ii — both producer and consumer use it, so 12-5-ii still works.

Recipe 12-6

Error channels: three levels of handling a bad message

Recipe 12-6 is the only recipe in the chapter split into a server context (ServerMain loads IntegrationConfiguration) and a client context (ClientMain loads ClientConfiguration with just a connection factory and a JmsTemplate). The client deliberately sends two messages: a good one with "id", 1234L and a poison one with "id", "1234L" — a String where the transformer casts to Long. That ClassCastException is the subject of all three variants.

  1. 12-6_i — wiring. The adapter spec adds .errorChannel("errorChannel"). Without it, an exception inside an endpoint still becomes an ErrorMessage, but it is published to whatever channel the framework resolves from the errorChannel header; naming it pins the destination. This module wires the route but installs no subscriber of its own.
  2. 12-6_ii — subscribing. A second flow, errorFlow(), is IntegrationFlow.from("errorChannel").handle(errorHandlingServiceActivator()).get(). Because errorChannel is the container-wide channel that @EnableIntegration registers (a publish-subscribe channel by default), DefaultErrorHandlingServiceActivator.handleThrowable(Message<Throwable>) now receives the failure and unwraps it: throwable instanceof MessagingException me, then me.getFailedMessage() to get the original payload back.
  3. 12-6_iii — routing by exception type. errorFlow() now ends in .route(exceptionTypeRouter()), where the router is an ErrorMessageExceptionTypeRouter configured with Map.of(MyCustomException.class.getName(), "customExceptionChannel", RuntimeException.class.getName(), "runtimeExceptionChannel", MessageHandlingException.class.getName(), "messageHandlingExceptionChannel"). Only customExceptionChannel has a consumer here (customExceptionFlow()); the other two channel names are demonstrated but left unsubscribed. The handler signature also changes to a bare handleThrowable(Throwable throwable), and the transformer gains a business failure: if (customer.id() == 321L) throw new MyCustomException();.

Two source-level traps in 12-6_iii

As committed, recipe_12_6_iii/.../IntegrationConfiguration.java listens on destination recipe-12-6 (twice calling .extractPayload(true) on the same spec), while ClientMain.java in that same module sends to recipe-1-6. And the MyCustomException trigger is id == 321L, which the client never produces — its two messages use 1234L and "1234L". So the custom-exception route cannot be exercised without editing one of the two files. The exception-type routing itself is still worth reading as the reference shape.

Reading the flow. The adapter is the only producer of error messages in this recipe: the JMS delivery happens on the listener's thread, so any exception thrown by the transformer or the service activator is caught by the framework, wrapped (usually as MessageHandlingException, with getFailedMessage() pointing at the offending message), stamped into the errorChannel header and published to the named error channel. The from("errorChannel") flow is an ordinary consumer of that channel — Spring Integration's ErrorMessageExceptionTypeRouter then takes the exception carried by the ErrorMessage and resolves a destination from setChannelMappings, whose keys are fully-qualified class names (MyCustomException.class.getName() in the source), and publishes the message to the channel name it returns. All three keys the recipe registers sit in one hierarchy — MessageHandlingException extends MessagingException, which extends NestedRuntimeException, which is a RuntimeException — so the figure is really about the mapping shape, and about the fact that customExceptionChannel is the only one of the three destinations a flow actually subscribes.

Reading the flow. Follow the second message: the failure is not detected by validation but by an ordinary Java cast inside transformJMSMapToCustomer. Spring Integration catches it at the endpoint boundary, so the JMS listener never sees the exception and the broker considers the message consumed — the error path is entirely inside the bus. The errorChannel("errorChannel") attribute on the adapter is what guarantees the ErrorMessage is published to a known place instead of relying on the header default, and handleThrowable's MessagingException branch is where you would write the failed payload to a dead-letter store or a table for replay.

Recipes 12-7 and 12-8

Splitter, aggregator and content-based router on a batch file

Recipes 12-7 and 12-8 reuse the file-inbound machinery of 12-4 and add the three patterns that make a bus useful. CustomerBatchFileSplitter is identical in both 12-7 modules and in 12-8:

@Splitter
public Collection<String> splitAFile(File file) throws IOException {
    return Files.readAllLines(file.toPath());
}

Returning a Collection from a @Splitter makes Spring Integration emit one message per element and stamp each with the sequence headers (sequenceNumber, sequenceSize, correlationId) that the framework's default aggregator correlates on. The three flows then differ only in what they do with the fan-out:

ModuleFlowPatternDirectory and filter
recipe_12_7_i from(Files.inboundAdapter, poller 1s).split(splitter()).handle(customerDeletionServiceActivator()) Splitter only — one deleteCustomer(String) call per line. ~/customerstoremove/new/, customerstoremove-*.txt
recipe_12_7_ii same, plus .aggregate().handle(summaryServiceActivator()) Splitter plus aggregator — SummaryServiceActivator.summary(Collection<Customer>) prints Removed N customers. ~/customerstoremove/new/, customerstoremove-*.txt
recipe_12_8 from(...).split(splitter()).transform(transformer()).route(customerCreditScoreRouter()) Splitter, transformer, content-based router into two named channels, each consumed by its own flow ending in .log(). ~/customerstoimport/new/, customers-*.txt

12-8's router returns a channel name from a business predicate — customer.creditScore() > 770 ? "safeCustomerChannel" : "riskyCustomerChannel" — and those two names are real beans, because the module also declares safeCustomerFlow() and riskyCustomerFlow() as IntegrationFlow.from("safeCustomerChannel")...log(...). The sample file recipe_12_8/src/main/resources/customers-0001.txt has exactly the split you would expect: rows 1 (1000) and 3 (785) route to the safe channel, rows 2 (500) and 4 (432) to the risky one. Two source details to know: the transformer method is literally named transfor (missing m) and reads columns[3] with Long.parseLong into the record's float creditScore, and the Customer record — including its Customer(long id) convenience constructor — is present in recipe_12_7_ii but never constructed there, because that module's splitter still hands raw String lines to a String-taking handler.

Reading the flow. Both subgraphs begin with the same pair of framework endpoints: a SourcePollingChannelAdapter (Pollers.fixedRate(Duration.ofSeconds(1))) firing a FileReadingMessageSource, whose File payload goes to the next stage. In 12-8 the .split(...) endpoint turns Files.readAllLines into N messages, .transform(...) parses each comma-separated line into a Customer, and .route(...) asks routeByCustomerCreditScore for a channel name; the returned string is resolved against the context, so the message physically leaves fileSplitAndDelete and enters safeCustomerFlow or riskyCustomerFlow, each terminating in a logging handler. In 12-7_ii the router slot is taken by .aggregate(), which gathers the per-line messages back into one group and emits a Collection to summary(Collection<Customer>). Caveat for anyone running it: the stage that feeds that aggregator, deleteCustomer(String), returns void, and a @ServiceActivator with a void return produces no reply message — so on the default behaviour nothing would reach the aggregator. The aggregator only pays off when the preceding stage emits something to collect (as 12-8's transformer does, or with Customer objects the unused record in this module hints at).

Recipes 12-9 and 12-10

Gateways: entering the bus from a method call

Everything above is driven by an external event (a JMS message, a file). Recipe 12-10 asks the opposite question: how does ordinary Java code get onto the bus? Two answers, one per variant.

12-10_i — a hand-built gateway over two direct channels

AdditionConfiguration holds the simplest flow in the chapter: IntegrationFlow.from("request").handle(additionService(), "add").channel("response").get(). Both request and response are channel names, not beans, and Spring Integration's default channel factory materialises them as point-to-point (DirectChannel) beans — which is why Main can immediately do ctx.getBean("request", MessageChannel.class). Note .handle(additionService(), "add"): the second argument names the method, because AdditionService is a plain class with no @ServiceActivator on add(Operands). Main then builds the gateway twice over — once with GatewayProxyFactoryBean (given default request and reply channels, setBeanFactory(ctx), afterPropertiesSet(), start(), and then never used, since no service interface is set), and once with SimpleMessagingGateway, a three-line subclass of MessagingGatewaySupport that exposes the protected sendAndReceive(Object) as convertSendAndReceive. That call sends the Operands record to request, blocks on response, and prints System.out.printf("Result: %f%n", ...) prints Result: 26.000000. It is the gateway pattern stripped to its mechanics: request channel, replyChannel header, synchronous receive with the framework's default timeout.

12-10_ii — @MessagingGateway all the way out to JMS

The holiday example splits the same JVM into two contexts that Main starts side by side: ServerIntegrationContext and ClientIntegrationConfig. The client side is the pattern everyone copies:

@MessagingGateway
public interface VacationService {
    @Gateway
    List<HotelReservation> findHotels(HotelReservationSearch search);
}

ClientIntegrationConfig.vacationGatewayFlow() is IntegrationFlow.from(VacationService.class).handle(Jms.outboundGateway(connectionFactory()) .requestDestination("inboundHotelReservationSearchDestination") .replyDestination("outboundHotelReservationSearchResultsDestination")).get(). The from variant that takes an interface creates the gateway endpoint from its annotations — the proxy Main retrieves with clientCtx.getBean(VacationService.class). The server side mirrors it with Jms.inboundGateway(...).requestDestination("inboundHotelReservationSearchDestination") feeding .handle(vacationService()); VacationServiceImpl seeds four reservations in a @PostConstruct, sleeps one second via Utils.sleep (from shared-resources) and filters hr.price() <= search.maxPrice(). Because the reply destination is set explicitly, the reply travels back as a real JMS message rather than a temporary queue.

12-9 — the same idea, aimed at Spring Batch

recipe_12_9 is the batch handoff: .transform(transformer).handle(handler) where the transformer builds new JobLaunchRequest(job, builder.toJobParameters()) with the file path added as the filename job parameter, and the handler is spring-batch-integration's JobLaunchingMessageHandler around a JobLauncher. Two things must be said about it as committed: IntegrationConfiguration carries no @Configuration and no @EnableIntegration (the @Bean methods still register, but in lite mode), and no Job or JobLauncher bean is defined anywhere in the module, so Main — whose try-with-resources body is empty — cannot start this flow without supplying them.

Reading the flow. The @MessagingGateway proxy turns findHotels(search) into a GenericMessage whose payload is the HotelReservationSearch record and whose replyChannel header points at a channel the gateway is blocking on. from(VacationService.class) is what binds that proxy to the flow, so the message enters vacationGatewayFlow rather than a named channel. The Jms.outboundGateway handler is a request-reply adapter: it serialises the payload into a JMS message, sends it to the request destination, and correlates the reply from outboundHotelReservationSearchResultsDestination by JMS correlation id. On the far side, Jms.inboundGateway is also request-reply, so the list returned by VacationServiceImpl.findHotels becomes the JMS reply the client gateway is waiting for; the gateway then converts it to List<HotelReservation> and unblocks Main. The one-second Utils.sleep is there to prove the call really is asynchronous across the broker.

Reading the diagram. Left half is 12-10_i: SimpleMessagingGateway gains nothing but visibility — the superclass MessagingGatewaySupport already implements the send-and-receive, lifecycle (afterPropertiesSet, start) and header handling; the subclass just re-exposes sendAndReceive through the generic convertSendAndReceive. The additionFlow node is the IntegrationFlow bean mediating between the two channels and AdditionService.add, and GatewayProxyFactoryBean is drawn where the source puts it: fully configured, started, and never called. Right half is 12-10_ii: the @MessagingGateway interface is the contract the client context publishes, VacationServiceImpl is the @ServiceActivator behind the server's inbound gateway, and the two records are the request and reply payloads that cross the broker — HotelReservation generates its id with UUID.randomUUID() in a compact constructor overload, so ids differ on every run.

Practical

Building and running the recipes

Module paths are Gradle project paths of the form :ch12:recipe_12_X_Y (the root settings.gradle walks every ch*/recipe* directory and colon-joins it). Build any single recipe with:

./gradlew :ch12:recipe_12_2_i:build
./gradlew :ch12:recipe_12_8:build

No module in this chapter has a src/test directory, so build here means compile plus jar — it proves the DSL code type-checks, nothing more.

Chapter 12 does not apply the shadow plugin the way chapters 10 and 11 do, and it declares no Main-Class manifest, so the runnable fat jar comes from the root project's uberJar task and the main class has to be named yourself:

./gradlew :ch12:recipe_12_10_i:uberJar
java --enable-preview -cp ch12/recipe_12_10_i/build/libs/recipe_12_10_i-6.0.0-SNAPSHOT-all.jar \
     com.apress.spring6recipes.springintegration.Main

--enable-preview is not decoration: the root build.gradle compiles every recipe with --enable-preview on a Java 19 toolchain, and gradle.properties pins org.gradle.java.home to a JDK 17 path, so expect to let Gradle provision 19 or to align that property with your own JDK.

Why your console looks empty

Almost every handler in this chapter logs with logger.debug or logger.info (InboundHelloWorldJMSMessageProcessor, the 12-3 and 12-4 file handlers, both InboundCustomerServiceActivator classes), and the logging setup pulled in by shared-resources/src/main/resources/simplelogger.properties pins org.slf4j.simpleLogger.defaultLogLevel=WARN. Add org.slf4j.simpleLogger.log.com.apress.spring6recipes.springintegration=DEBUG there (or -Dorg.slf4j.simpleLogger.defaultLogLevel=debug) before concluding a flow did not run. That is also why recipes 12-7 and 12-8 fall back to System.out.printf, and why the 12-8 flows use the DSL's .log(), which logs at INFO. Finally, note the credentials mismatch: the broker above is created with AMQ_USER=admin and AMQ_PASSWORD=admin, while the recipes connect with no username and password — expect an authentication error unless your broker instance permits anonymous JMS connections.

For a first tour with no infrastructure at all: run recipe_12_10_i to watch a request-reply round trip over two direct channels, then recipe_12_8 against a directory to watch one file become four messages and split into two channels by credit score.

Chapter 13 — Spring Testing

The whole chapter rehearses one thing: how a test gets its context and its lifecycle. Twenty recipe modules exercise a single bank domain shipped in ch13/recipe_13_bank, starting from an assertion on a plain object and ending with a real PostgreSQL container. Almost every recipe ships twice — once on JUnit 5 with SpringExtension, once on TestNG with a Spring base class — so you can see exactly which behaviour belongs to the runner and which belongs to the TestContext framework.

Overview and module map

The domain under test is deliberately tiny so that the test plumbing is the interesting part. ch13/recipe_13_bank/src/main/java/com/apress/spring6recipes/bank/ holds Account, the AccountDao interface with a InMemoryAccountDao and a JdbcAccountDao, SimpleAccountService annotated @Service @Transactional, a web layer with DepositController plus BankWebConfiguration, and an outbound client OpenIBANValidationClient extends RestGatewaySupport. Configuration is BankConfiguration with two @Profiled nested classes: jdbc selects JdbcBankConfiguration (DataSource, DataSourceTransactionManager, JdbcTemplate, JdbcAccountDao) and anything else selects InMemoryBankConfiguration.

Recipes 13.1 and 13.2 need none of that plumbing. From 13.3 onward the chapter is a steady climb of context complexity: bean lookup, then injection, then a database, then a servlet context, then a real database engine. The variant suffix is a convention, not a sequence: _i is the JUnit 5 form, _ii the TestNG port of the same recipe (13.1 uses _i/_ii for JUnit and _iii/_iv for TestNG because each runner gets two variants).

Reading the flow. Each arrow adds exactly one dependency that the TestContext framework must now manage. Up to 13.2 the test constructs its own objects (new SimpleAccountService(accountDao)), so JUnit 5's @BeforeEach or TestNG's @BeforeMethod is the whole story. At 13.3 the test asks applicationContext.getBean(AccountService.class), so a context has to be booted. 13.4 replaces that lookup with an @Autowired field, which means injection is now the framework's job. 13.5 adds @Sql and @Transactional, so listeners must start and roll back a transaction around each method. 13.6 adds @WebAppConfiguration, which changes the kind of context that gets created. 13.7 is the odd branch: it needs no context at all, because MockRestServiceServer wraps the client object itself. 13.8 keeps the 13.5 lifecycle and only swaps the DataSource provider for a container.

There is no Spring Boot in this chapter

ch13/build.gradle declares spring-webmvc, spring-jdbc, spring-test, junit-jupiter, mockito-core, testng and org.testcontainers:* — and the root build's platform pins spring-framework-bom:6.0.3. No module references spring-boot-starter-test, so none of the Boot vocabulary exists here: there is no @SpringBootTest, no @WebMvcTest, no @DataJpaTest, and neither @MockBean nor @MockitoBean (the latter is a Spring Framework 6.2 addition anyway). The equivalent of a "slice" in this chapter is a small @Configuration class written in src/test/java — see 13.4 and 13.5. Mocking is plain Mockito: @Mock and @InjectMocks with @ExtendWith(MockitoExtension.class) in the JUnit modules (recipe_13_2_iv, recipe_13_2_v, recipe_13_3_i, recipe_13_4_i, recipe_13_5_i), and Mockito.mock(...) inside @BeforeMethod in the TestNG modules (recipe_13_3_ii, recipe_13_4_ii, recipe_13_5_ii), because MockitoExtension is a JUnit 5 extension with no TestNG counterpart.

Testing without a container

Recipes 13.1 and 13.2 never touch Spring. SimpleInterestCalculatorTests news up SimpleInterestCalculator in @BeforeEach/@BeforeMethod and asserts on calculate, with assertThrows(IllegalArgumentException.class, …) in JUnit and @Test(expectedExceptions = …) in TestNG. The interesting material starts in 13.2, where SimpleAccountService needs an AccountDao and the chapter shows four ways to give it one.

Reading the graph. Everything on the left is production code in ch13/recipe_13_bank/src/main/java; the two right-hand implementations (AccountDaoStub, MockAccountDao) exist only inside test sources. Note the stereotype trap: InMemoryAccountDao and JdbcAccountDao carry no @Repository, so they can only enter a context through a @Bean method — that single fact drives every configuration class in recipes 13.3 to 13.5. Both classes are package-private, which is why InMemoryAccountDaoTests must sit in src/test/java/com/apress/spring6recipes/bank/: same package, different Gradle module, and package-private access still works because the runtime package is what matters. The stub in recipe_13_2_ii implements only findAccount and updateAccount and leaves createAccount/removeAccount as empty bodies — enough to drive deposit, and the assertion then reads the stub's own balance field back. recipe_13_2_iii replaces that hand-written state with mock(AccountDao.class) plus when(...).thenReturn(account) and asserts on interactions with verify(accountDao, times(1)).updateAccount(account). recipe_13_2_iv is the same test with the boilerplate removed: @Mock AccountDao and @InjectMocks SimpleAccountService, populated by MockitoExtension before @BeforeEach runs.

Package-private is a test design decision here. recipe_13_2_iii/src/test/java/com/apress/spring6recipes/bank/SimpleAccountServiceMockTests.java and most other JUnit classes in 13.1/13.2 are not public: JUnit 5 instantiates package-private test classes happily (two leftovers, SimpleAccountServiceStubTests in recipe_13_2_ii and SimpleAccountServiceTests in recipe_13_2_v, are still declared public). Every TestNG port is public class with public methods, because TestNG's runner only selects public @Test methods.

Getting a context into the test

Recipes 13.3 and 13.4 are the same lesson told twice, once per runner. 13.3 fetches its collaborator by hand — accountService = applicationContext.getBean(AccountService.class) in @BeforeEach (ch13/recipe_13_3_i/src/test/java/.../AccountServiceContextTests.java) — and in the TestNG port that applicationContext field is not even declared by the test: it is inherited from AbstractTestNGSpringContextTests. 13.4 drops the lookup for an @Autowired AccountService field, and replaces the application configuration with a test-local one.

Reading the hierarchy. On the TestNG side the framework is reached by inheritance: AbstractTestNGSpringContextTests exposes applicationContext (which is why recipe_13_3_ii can call applicationContext.getBean(...) without declaring the field) and hooks @BeforeClass-style callbacks to bootstrap the context. Its subclass AbstractTransactionalTestNGSpringContextTests adds the transaction, which is exactly what recipe_13_5_ii and recipe_13_8_ii need — neither of them writes @Transactional on the class, because the base class supplies that behaviour. On the JUnit side there is no base class at all: @ExtendWith(SpringExtension.class) delegates every callback to TestContextManager, and the same effects are requested with plain annotations — recipe_13_5_i writes @Transactional itself, and recipe_13_5_i/recipe_13_8_i keep their @Sql. Read the two halves of the diagram as one table: the _i node and its _ii twin do the same job through opposite mechanisms. That asymmetry is the reason TestNG ports exist in this chapter — you can see which annotations are TestContext framework features and which are JUnit plumbing.

Walking the arrows. Order is the whole point. Jupiter calls SpringExtension.beforeAll first, which builds the TestContext from the class's annotations (@ContextConfiguration(classes = BankConfiguration.class), @Transactional, @Sql(scripts = "classpath:/bank.sql")) — this is where the merged configuration key is computed. Only then is a test instance created, and postProcessTestInstance triggers prepareTestInstance; DependencyInjectionTestExecutionListener asks DefaultCacheAwareContextLoaderDelegate for the context, which either returns a cached one or lets DelegatingSmartContextLoader build an AnnotationConfig-driven context. The transaction is opened after injection and before @BeforeEach, so init()'s createAccount and deposit are already inside it, and @Sql runs in the same transaction — that is why bank.sql's CREATE TABLE ACCOUNT does not collide with the next test method. Finally afterTestMethod rolls back and nothing closes the context: with @DirtiesContext absent, the context survives until the JVM ends. Compare recipe_13_5_ii: the identical sequence, except TestNG's base class supplies the transaction and the @BeforeMethod hook.

Two source-level traps I found while reading 13.3 and 13.4

1. A shadowed BankConfiguration. com.apress.spring6recipes.bank.BankConfiguration exists twice on the test classpath of recipe_13_3_i, recipe_13_3_ii, recipe_13_4_i and recipe_13_4_ii: once in recipe_13_bank/src/main/java (profiles, DAO beans) and once in the module's own src/test/java. Gradle puts a module's own test output ahead of its dependencies, so @ContextConfiguration(classes = BankConfiguration.class) binds to the local copy. And recipe_13_4_i's copy declares only @Bean InMemoryAccountDao accountDao() with no @ComponentScan, while recipe_13_3_i's copy declares @ComponentScan and no beans — since neither InMemoryAccountDao nor JdbcAccountDao is annotated, one module is missing an AccountService candidate and the other is missing an AccountDao. recipe_13_4_ii is the self-consistent pair (@ComponentScan plus accountDao()), and 13.5, 13.6 and 13.8 are consistent too. Expect a Failed to load ApplicationContext or an unsatisfied @Autowired in 13.3_i and 13.4_i; I inspected the sources and did not run the build, so treat this as "run it and see".

2. An assertion that cannot fail. In ch13/recipe_13_3_i/src/test/java/com/apress/spring6recipes/bank/AccountServiceContextTests.java the withDraw test reads assertEquals(50, accountService.getBalance(TEST_ACCOUNT_NO), 50) — that third argument is JUnit's delta, so anything between 0 and 100 passes. The _ii port and the other modules use 0.

What the TestContext framework caches

Context creation is the expensive part of a Spring test, so the framework keeps an ApplicationContext per merged configuration, not per test class. Every one of the ten *ContextTests classes in this chapter declares a configuration that differs from its neighbours, and each lives in its own module — so the chapter demonstrates ten context boots and zero cache hits, which is worth knowing before you try to "optimise" it.

Reading the topology. The key that TestContextManager computes for a test class is built from the context loader plus the @ContextConfiguration attributes (locations or classes), the initializer list, the @ActiveProfiles set and the declared property sources. Three edges at the bottom name the three ways this chapter changes that key. First, 13.3 and 13.4 declare BankConfiguration as different Class objects in different source sets, so even an identical annotation would not share a slot. Second, 13.8 adds @ActiveProfiles("jdbc") where 13.5 relies on the default, and the active profile is part of the key — so 13.8's slot holds JdbcBankConfiguration's dataSource, transactionManager, jdbcTemplate and accountDao instead of an in-memory map. Third, 13.6's @WebAppConfiguration changes the loader itself, which is why its slot is a GenericWebApplicationContext over a MockServletContext rather than a plain context. Practical consequence: the diagram pairs each _i with its _ii twin by annotation shape only, and because Gradle runs :ch13:recipe_13_5_i:test and :ch13:recipe_13_5_ii:test in separate JVMs they never share an instance. Two context test classes inside the same module with the same annotations would share one context, and that is the optimisation the framework offers.

Test-class scope matters as much as the key. recipe_13_5_i's @Transactional and @Sql are class-level, but the transaction they create is per method: the two methods deposit and withDraw each get a fresh transaction, a fresh CREATE TABLE ACCOUNT and a fresh rollback. That is why no module in 13.5 or 13.8 has an @AfterEach cleanup method, while 13.3 and 13.4 do.

Schema, data, rollback

Recipe 13.5 is where the chapter becomes useful in real projects. The test-local BankConfiguration in ch13/recipe_13_5_i/src/test/java/.../BankConfiguration.java builds a SimpleDriverDataSource on jdbc:h2:mem:bank-testing, a DataSourceTransactionManager named transactionManager, a JdbcTemplate, JdbcAccountDao as the AccountDao, and @EnableTransactionManagement @ComponentScan so that SimpleAccountService's @Transactional gets a proxy. The @Sql script is not copied into the module: classpath:/bank.sql resolves to ch13/recipe_13_bank/src/main/resources/bank.sql, on the test classpath because of implementation project(':ch13:recipe_13_bank').

Reading the transitions. The edge worth internalising is Asserted --> RolledBack. Because the test's transaction is the outer one, the @Transactional proxy on SimpleAccountService (propagation REQUIRED) joins it rather than starting a second transaction, and the CREATE TABLE ACCOUNT that SqlScriptsTestExecutionListener runs is itself transactional DDL on both H2 and PostgreSQL. So the rollback at the end of method one removes the table, letting method two re-create it — the loop back to TxOpen is only possible while @Transactional is on the test. Delete that annotation from recipe_13_5_i and the second method fails on an already-existing table, which is the fastest way to feel what the annotation buys. The TestNG variant recipe_13_5_ii reaches the same states by extending AbstractTransactionalTestNGSpringContextTests instead of writing @Transactional; in both cases the transactionManager bean from the test configuration is what the listener drives.

MockMvc against a real web context

Recipe 13.6 keeps the production web configuration (ch13/recipe_13_bank/src/main/java/com/apress/spring6recipes/bank/web/config/BankWebConfiguration.java, with @EnableWebMvc and an InternalResourceViewResolver prefixing /WEB-INF/views/ and suffixing .jsp) and adds @ContextConfiguration(classes = { BankWebConfiguration.class, BankConfiguration.class }) plus @WebAppConfiguration. Here BankConfiguration is the shared one — 13.6 has no test-local copy — so with no active profile the @Profile("!jdbc") branch supplies InMemoryAccountDao. The test then seeds data by injecting the DAO directly, builds MockMvcBuilders.webAppContextSetup(webApplicationContext).build() in @BeforeEach, and asserts on the forward and status.

Reading the hops. Nothing here is faked except the servlet API. The MockHttpServletRequest built by perform(post("/deposit")) carries the form parameters, TestDispatcherServlet consults the RequestMappingHandlerMapping that @EnableWebMvc registered, and DepositController.deposit is invoked by the annotation-based handler adapter with @RequestParam conversion from the string "50.0" to double. The controller calls accountService.deposit(...) then accountService.getBalance(...), and returns the literal view name success; the resolver turns that into a forward to /WEB-INF/views/success.jsp, which MockMvc records on the mock response instead of rendering — so the JSP file never has to exist. Two mechanism notes from the configuration: no @EnableTransactionManagement is registered in this pair of contexts, so SimpleAccountService's @Transactional creates no proxy and the DAO calls are plain method calls; and @WebAppConfiguration with its default value expects src/main/webapp, which does not exist in recipe_13_6_i or recipe_13_6_ii — if the context fails to load with "Resource base path … does not exist or is not a directory", that is the cause, and giving the annotation an existing directory fixes it. recipe_13_6_ii additionally posts to /deposito, a typo that maps to no handler, so its forwardedUrl assertion cannot hold.

Stubbing an outbound HTTP client

Recipe 13.7 answers "how do I test a class that calls someone else's API" without a container, without Mockito, and without a network. OpenIBANValidationClient extends RestGatewaySupport and calls getRestTemplate().getForObject(URL_TEMPLATE, IBANValidationResult.class, iban); the test in ch13/recipe_13_7_i/src/test/java/com/apress/spring6recipes/bank/web/OpenIBANValidationClientTest.java instantiates that package-private class directly (same package trick again) and hands it to MockRestServiceServer.createServer(client) — the overload that takes a RestGatewaySupport, which I confirmed from the compiled test class.

Reading the interception. The only Spring mechanism in play is the ClientHttpRequestFactory swap: after createServer(client), the RestTemplate owned by RestGatewaySupport no longer produces real connections, it produces mock requests that MockRestServiceServer matches against the recorded requestTo expectation. The URI must match exactly, including the query string from URL_TEMPLATE (?getBIC=true and validateBankCode=true), which is why the test hard-codes the full expectedUri. The response body comes from src/test/resources/NL87TRIO0396451440-result.json (or the invalid NL28XXXX389242218-result.json) and is deserialised into the IBANValidationResult record by Jackson — which explains the otherwise odd testImplementation 'org.hamcrest:hamcrest' and jackson-databind lines in ch13/build.gradle for this module. One caveat you should copy carefully: neither test method calls mockRestServiceServer.verify(), so an assertion holds only because a wrong URI throws when the request arrives; a method that made no request at all would still pass.

Testcontainers and dynamic properties

Recipe 13.8 is the payoff: the same AccountServiceContextTests body, but now the JDBC beans come from the application's own @Profile("jdbc") configuration and the database is a real PostgreSQL server in a container. The trick that makes it work without editing application.properties is @DynamicPropertySource. Note where that annotation comes from: the import is org.springframework.test.context.DynamicPropertySource, and inspecting the compiled test class shows the registry type resolving to org/springframework/test/context/ — that is spring-test 6.0.3, not Spring Boot, which is not on this chapter's classpath at all.

Reading the resolution chain. @ActiveProfiles("jdbc") is what selects BankConfiguration.JdbcBankConfiguration instead of the in-memory branch; the nested configuration's constructor takes Environment and calls env.getRequiredProperty("jdbc.url") and friends while the dataSource() bean is being created. Those four lookups are the collision point: @PropertySource("classpath:/application.properties") supplies jdbc.url=jdbc:h2:mem:bank with the H2 driver, while registerPgProperties supplies the container's URL and driver — and the container values are the ones that must win, because org.testcontainers:postgresql and org.postgresql:postgresql are the only JDBC dependencies in ch13/build.gradle for recipe_13_8_i and _ii; com.h2database:h2 is not on their classpath at all, so the file's values could not produce a working DataSource. The registry hands over Supplier lambdas (POSTGRES::getJdbcUrl) rather than strings, which is what lets the value be read after Docker has allocated a port. From there the chain is ordinary: dataSource feeds jdbcTemplate and DataSourceTransactionManager, JdbcAccountDao becomes the AccountDao, component scanning supplies SimpleAccountService, and @Sql(scripts = "classpath:/bank.sql") creates the same ACCOUNT table on PostgreSQL as it did on H2. Lifecycle difference to keep straight: recipe_13_8_i is annotated @Testcontainers with a @Container static final field, so the JUnit extension starts and stops it; recipe_13_8_i's TestNG twin declares the same static field but has no JUnit extension available, so it starts and stops the container explicitly in @BeforeSuite/@AfterSuite — and its module omits org.testcontainers:junit-jupiter from the dependencies accordingly.

A dependency oddity worth copying. Both 13.8 modules declare io.quarkus:quarkus-junit4-mock:2.11.2.Final, with the build comment "Some empty JUnit4 classes as Testcontainers has a hard dependency on them". The root build excludes junit:junit and junit-vintage-engine from every configuration, so Testcontainers 1.17.6 would fail to load its JUnit 4 base classes without that stub.

Building and running these tests

Module paths in Gradle are colon-qualified by directory, so chapter 13's tasks are :ch13:recipe_13_N_M:test. Nothing here needs a running server, a browser or a database you provision yourself — except 13.8.

# one recipe, JUnit 5 module (prints passed, skipped, failed per test)
./gradlew :ch13:recipe_13_5_i:test --tests "*AccountServiceContextTests"

# the TestNG port of the same recipe (module switches to useTestNG in ch13/build.gradle)
./gradlew :ch13:recipe_13_5_ii:test

# the whole chapter
./gradlew :ch13:recipe_13_1_i:test :ch13:recipe_13_1_ii:test :ch13:recipe_13_1_iii:test \
          :ch13:recipe_13_1_iv:test  :ch13:recipe_13_2_i:test  :ch13:recipe_13_2_ii:test \
          :ch13:recipe_13_2_iii:test :ch13:recipe_13_2_iv:test :ch13:recipe_13_2_v:test  \
          :ch13:recipe_13_3_i:test   :ch13:recipe_13_3_ii:test :ch13:recipe_13_4_i:test  \
          :ch13:recipe_13_4_ii:test  :ch13:recipe_13_5_i:test  :ch13:recipe_13_5_ii:test \
          :ch13:recipe_13_6_i:test   :ch13:recipe_13_6_ii:test :ch13:recipe_13_7_i:test

Report output lands in ch13/recipe_13_N_M/build/reports/tests/test/index.html; the repository already contains such a report for recipe_13_2_iv, which is proof those tests were run at some point. Prerequisites and gotchas, all read out of the build files:

  • JDK 19. The root build.gradle pins java.toolchain.languageVersion = 19 and adds --enable-preview to JavaCompile, Test and JavaExec JVM args, while the checked-in gradle.properties sets org.gradle.java.home to a JDK 17 path on the author's machine. Point that at a JDK 19 you actually have (or drop the line and let the toolchain resolve) before expecting a compile.
  • Gradle 7.6 via the wrapper, and dependency management from spring-6-recipes-dependencies: Spring Framework 6.0.3, JUnit 5.9.1, Mockito 4.10.0, Testcontainers 1.17.6, TestNG 7.6.1, H2 2.1.214, PostgreSQL driver 42.4.1, Jackson 2.14.1.
  • Docker for 13.8 only. The container is created from the image string postgres:14.5; no port or credentials are configured because the container exposes them through @DynamicPropertySource. Everything else runs in-process.
  • No profiles or property overrides to set by hand. 13.5 supplies its own H2 URLs (jdbc:h2:mem:bank-testing) in the test configuration, and the shared application.properties (jdbc:h2:mem:bank, user sa, empty password) is only consulted by the jdbc profile in 13.8 — where it is superseded as described above.
  • Runner mismatch is expected. The root build forces useJUnitPlatform() on every Test task and ch13/build.gradle selects useTestNG() for recipe_13_1_iii, _iv, and the _ii modules. A module that has JUnit tests but a TestNG task (or the reverse) will report zero tests, so check the module's block in ch13/build.gradle before concluding a test "did not exist".
  • Expect the four problems flagged above in recipe_13_3_i, recipe_13_4_i (shadowed BankConfiguration and its missing beans), recipe_13_6_i/_ii (@WebAppConfiguration base directory absent, plus the /deposito typo). The unit-test recipes 13.1 and 13.2, the 13.5 pair, and 13.7 are self-consistent on inspection.

What I could not establish from the source alone: whether any of the four suspect modules currently pass. Verifying that requires executing Gradle, which is outside what I did here.

Chapter 8 — Spring Batch

Sixteen modules, one job. Every recipe in this chapter builds the same single-step, chunk-oriented import — insertIntoDbFromCsvJob / step1, chunk size 5, CSV in, USER_REGISTRATION rows out — and varies exactly one thing around it: how the batch infrastructure is declared, how the reader and writer are assembled, what happens to a bad row, how a deadlock is retried, how the launch is made asynchronous, and who triggers it. Read the deltas, not the boilerplate.

Overview and module map

The domain example is a US state-licensing CSV dump. Each line is eleven comma-separated columns that map onto the UserRegistration record shipped in almost every module, and the job turns those lines into INSERT statements against USER_REGISTRATION in an H2 file database at jdbc:h2:~/batch. The same database holds Spring Batch's own metadata (BATCH_JOB_INSTANCE, BATCH_JOB_EXECUTION, BATCH_JOB_PARAMS, BATCH_STEP_EXECUTION and the two context tables), which is why a chapter about "reading a file" spends most of its code on JobRepository plumbing.

Recipes group by what they change:

  • 8-1 — get the infrastructure into the container, by hand (recipe_8_1_i) or with @EnableBatchProcessing (recipe_8_1_ii). No job yet; Main just prints the three beans.
  • 8-2 — the first working job: read a flat file, write JDBC. Setter assembly (recipe_8_2_i) versus the fluent item builders (recipe_8_2_ii).
  • 8-3 — hand-written ItemReader and ItemWriter against a service interface instead of a file and a table.
  • 8-4 — the ItemProcessor slot: validate, normalise, or drop a row.
  • 8-5, 8-6 — fault tolerance. 8-5 opens the faultTolerant() block and leaves the policies commented out; 8-6 shows three places to put retry (step level, writer level with RetryTemplate, declarative @Retryable).
  • 8-7 — flow control. One class, HoroscopeDecider.
  • 8-8 — four ways to get the job off the calling thread (SimpleAsyncTaskExecutor, taskExecutorRef, @EnableAsync plus @Scheduled).
  • 8-9 — the scheduled launcher as the normal way to run the job.

Reading the flow. Left to right is the data path inside one chunk: FlatFileItemReader.read() pulls a line, the tokenizer splits it on commas, DefaultLineMapper hands the FieldSet to BeanWrapperFieldSetMapper, which produces the UserRegistration that is fed to the processor. In recipe_8_2_i and _ii the processor edge is absent from the builder chain, so items go straight to the writer; from recipe_8_4 onward .processor(processor) is present and a null return removes the item from the chunk. The writer receives the whole accumulated chunk, not one item at a time — that is the definition of chunk-oriented processing and it is why chunk(5, txManager) is the single most load-bearing call in the chapter. Both edges into JobRepository are the metadata writes: the job and step lifecycle events plus the per-commit counters, landing in the BATCH_* tables that live in the same H2 file as the business table.

Reading the flow. This is the reading order, not a dependency graph — no module depends on another; each is a standalone Gradle project under ch08/ that copies its predecessor and edits one thing. The evidence for the ordering is that the bean names (csvFileReader, jdbcItemWriter, step1, insertIntoDbFromCsvJob) and the job and step display names are byte-identical across twelve modules, while the deltas are single lines: 8-2_i to 8-2_ii swaps setters for FlatFileItemReaderBuilder; 8-4 adds the processor; 8-5 to 8-6_i fills in the retry call that 8-5 left commented; the 8-8 chain replaces the launcher's threading model. Two side branches (8-3, 8-7) contribute classes without a runnable entry point, so they are dead ends in the build sense.

Declaring the batch infrastructure (8-1)

ch08/recipe_8_1_i is the chapter's Rosetta stone because it names every bean Spring Batch needs and shows who consumes it. jobRepository() is a JobRepositoryFactoryBean given the DataSource and the PlatformTransactionManager; jobLauncher() is a TaskExecutorJobLauncher given that repository; jobRegistry() is a plain MapJobRegistry; and jobRegistryBeanPostProcessor() is what gets each Job bean into that registry at context refresh, which is why the recipe can later do context.getBean(Job.class). Schema comes from DataSourceInitializer with a ResourceDatabasePopulator that runs org/springframework/batch/core/schema-h2.sql (inside the spring-batch-core jar) followed by sql/reset_user_registration.sql, with setContinueOnError(true) so a second run does not die on the existing USER_REGISTRATION table.

ch08/recipe_8_1_ii deletes those four bean methods and puts @EnableBatchProcessing on the class instead. The change is observable in Main: the hand-wired module asks for beans by type, the annotated one asks getBean("jobRegistry", …), getBean("jobLauncher", …), getBean("jobRepository", …) — the fixed names Spring Batch's own registrar publishes. From recipe_8_2_ii onward a handful of modules drop the explicit transactionManager bean and let the annotation supply it: recipe_8_5 declares no transaction manager at all yet injects a PlatformTransactionManager into UserJob's constructor, which only resolves if @EnableBatchProcessing exposes one over the single DataSource bean.

Reading the flow. Start at batch.properties: @PropertySource("classpath:batch.properties") loads it into the Environment, and the dataSource(Environment) bean method pulls datasource.url, datasource.username, datasource.password with getRequiredProperty on the URL only — so a wrong key name fails at refresh, not at first connection. DriverManagerDataSource opens a fresh connection per request (no pool; that matters for the Derby variants in 8-5 and later). DataSourceInitializer is a InitializingBean, so the two scripts run the moment the container is refreshed, before any job executes. JobRepositoryFactoryBean is a FactoryBean: the container exposes the JobRepository it builds, and that object is the only path to the metadata tables. TaskExecutorJobLauncher holds the repository and is what Main calls run on. Finally, JobRegistryBeanPostProcessor is the reason a Job declared as a plain @Bean in UserJob is discoverable by name — without it, getBean(Job.class) still works but the registry stays empty.

Two naming quirks worth knowing before you copy either module

In recipe_8_1_ii, recipe_8_2_i and most later modules the bean method called databasePopulator() actually returns a DataSourceInitializer, so the bean named databasePopulator is the initializer, not the populator. And in recipe_8_1_i the same role is played by a method honestly named dataSourceInitializer. Otherwise the two files are interchangeable.

Reader, processor, writer (8-2, 8-3, 8-4)

ch08/recipe_8_2_i/src/main/java/com/apress/spring6recipes/springbatch/config/UserJob.java is the fullest statement of the item pipeline in the chapter. The reader is assembled in four beans: FlatFileItemReader.csvFileReader(…) gets a Resource injected from @Value("file:${user.home}/batches/registrations.csv") and a DefaultLineMapper, which itself is built from a DelimitedLineTokenizer (delimiter ,, eleven names) and a BeanWrapperFieldSetMapper whose targetType is UserRegistration.class. The writer is a JdbcBatchItemWriter with a single multi-row INSERT and a BeanPropertyItemSqlParameterSourceProvider, so :firstName-style named parameters are filled from the item's bean properties — the same mapping recipe_8_2_ii requests with .beanMapped(), collapsing both ends into builders: FlatFileItemReaderBuilder … .delimited().names(…) and JdbcBatchItemWriterBuilder … .beanMapped() — and the four intermediate beans disappear.

ch08/recipe_8_3 answers "what if my items come from a service, not a file". Its UserRegistrationItemReader implements ItemReader directly and its UserRegistrationServiceItemWriter implements ItemWriter and loops over the Chunk, calling registerUser per item and logging the result. Note the asymmetry the book's own code keeps: the reader asks the service for getOutstandingUserRegistrationBatchForDate(1, LocalDate.now()) inside read() and builds a fresh iterator each call, so it returns the head of the outstanding set every time rather than walking it — a stateful reader would hold the iterator between calls, or be an ItemStream so its position is checkpointed. Since the module ships no job, that code never runs here.

ch08/recipe_8_4 is the only module that puts a business rule inside the pipeline. UserRegistrationValidationItemProcessor.process(…) strips non-digits from ZIP and phone, checks phone length 10, ZIP length 5 or 9, and that the state code is in a hard-coded list, then returns a new record with the normalised values — or returns null, which is how Spring Batch expresses "filter this item out, it is not an error". Filtered items are counted in FILTER_COUNT, a column already visible in the chapter's own sql/create_schema.sql.

Reading the flow. The three interfaces at the top are the only thing the step builder cares about — SimpleStepBuilder.reader(…) .processor(…).writer(…) accepts them by type, which is why recipe_8_2_i can inject ItemReader of UserRegistration and receive the FlatFileItemReader bean. The solid arrows on the right show the two interchangeable implementations of each slot: file plus JDBC in recipes 8-2, 8-4 to 8-9, and the service-backed pair from recipe_8_3 (with recipe_8_6_ii's retrying writer as its hardening). The ItemWriter to Chunk edge is the one people get wrong: the writer is invoked once per chunk with everything buffered, whereas UserRegistrationServiceItemWriter and RetryableUserRegistrationServiceItemWriter both loop over it, restoring per-item semantics by hand.

Reading the flow. SimpleStep — what StepBuilder.chunk(5, txManager).build() produces — is the driver. It opens a transaction, then calls FlatFileItemReader.read() repeatedly; the reader pulls one line per call and returns null at end of file, and that null is the loop's terminator, not an error. Each item crosses to the processor; in recipe_8_4 a row whose state is not in the list or whose digits come back the wrong length yields null and is dropped, which is exactly the FILTER_COUNT you can then read out of BATCH_STEP_EXECUTION. Only after five survivors does the writer see anything, and it sees a Chunk. The commit is per chunk, so a failure in the third chunk reprocesses items 11 to 15, not the whole file — that is the property every fault-tolerance recipe in 8-5 and 8-6 is exploiting.

Launching a job and writing metadata

Each Main in the chapter is the same five moves: build an AnnotationConfigApplicationContext over BatchConfiguration, fetch JobLauncher and Job, build a JobParameters containing a date, call jobLauncher.run(job, jobParameters), then spin while (batchStatus.isRunning()) (500 ms in recipe_8_2_i and recipe_8_6_i via Utils.sleep from shared-resources, 1000 ms elsewhere) before printing getExitStatus().getExitCode() and getJobInstance().getId().

The date parameter is not decoration. Spring Batch identifies a JobInstance by job name plus the identifying parameters, and the constraint is right there in the chapter's own DDL: constraint JOB_INST_UN unique (JOB_NAME, JOB_KEY) in ch08/recipe_8_2_i/src/main/resources/sql/create_schema.sql. Changing the date on every run is what lets the recipe be launched twice in a row and get a new instance id printed. Drop it and the second launch collides with the completed one instead of doing work.

Metadata bookkeeping is entirely behind JobRepository. The reference DDL shipped in each module documents the tables and the counters you can query afterwards — COMMIT_COUNT, READ_COUNT, FILTER_COUNT, WRITE_COUNT, READ_SKIP_COUNT, WRITE_SKIP_COUNT, PROCESS_SKIP_COUNT, ROLLBACK_COUNT on BATCH_STEP_EXECUTION. Worth being precise about two things: that sql/create_schema.sql is not executed (the header admits it was copied from a Spring Batch 2.1.1 release and its BATCH_JOB_PARAMS table name predates 5.0); the scripts the populator actually runs are the jar's schema-h2.sql and the module's reset_user_registration.sql, which only creates USER_REGISTRATION. drop_all.sql and truncate_all.sql are shipped but unreferenced.

Reading the flow. Because the launcher is a TaskExecutorJobLauncher (recipe_8_1_i:75), run(...) hands the job to another thread and returns immediately — that single fact explains why every Main in this chapter has a busy-wait loop on BatchStatus.isRunning() rather than a blocking call. JobRepository.createJobExecution is the gatekeeper: it creates or refuses the instance under JOB_INST_UN. From there the step's own transaction manages data consistency while JobRepository updates metadata in its transaction, which is why a crashed run still shows accurate counters in BATCH_STEP_EXECUTION. The retry branch is chunk level, not item level: the transaction rolls back, the reader rewinds to the checkpoint stored in BATCH_STEP_EXECUTION_CONTEXT (a FlatFileItemReader is an ItemStream, so it can), and up to five items are read, processed and written again — three times at most under retryLimit(3). The skip branch is drawn but unreachable: no module in ch08 calls .skip(...) or .skipLimit(...), so READ_SKIP_COUNT, PROCESS_SKIP_COUNT and WRITE_SKIP_COUNT stay at zero and any non-retried exception ends the step.

Fault tolerance: retry without skip (8-5, 8-6)

ch08/recipe_8_5 is the honest starting point. Its step calls .faultTolerant() and nothing else — the two lines that would name a policy are comments, one of them literally .noRollback(com.yourdomain.exceptions.YourBusinessException.class) and one bare .retry(). Calling faultTolerant() on its own changes nothing observable: it just creates the SimpleStepBuilder fault-tolerant branch with the default policies, so every exception still rolls the chunk back and fails the step.

The three 8-6 modules are the same job with retry bolted on in three different places, and the chapter keeps the step-level policy in all three: .retryLimit(3).retry(DeadlockLoserDataAccessException.class) appears in recipe_8_6_i:62, recipe_8_6_ii:61 and recipe_8_6_iii:61. That is the interesting part — the variants do not replace it, they add a second, narrower retry underneath it:

  • recipe_8_6_i — step level only. One policy, five items retried as a unit.
  • recipe_8_6_ii — declares RetryTemplate and ExponentialBackOffPolicy beans and a RetryableUserRegistrationServiceItemWriter that wraps each registerUser call in retryTemplate.execute(...), so retry happens per item before the chunk ever fails. Caveat from the source: that writer is never registered as a @Bean — UserJob.jdbcItemWriter is still the injected ItemWriter, so the retry template is inert unless you swap the writer.
  • recipe_8_6_iii — moves the policy onto the business contract: @Retryable(backoff = @Backoff(delay = 1000, maxDelay = 10000, multiplier = 2)) on UserRegistrationService.registerUser(...), activated by @EnableRetry on BatchConfiguration. Now any caller of the service retries, batch or not.

Reading the flow. Take the middle path first, because it is the one all three modules actually configure: the step builder's retry list holds exactly DeadlockLoserDataAccessException, so the chunk transaction is rolled back, the ItemStream readers are reset to the position recorded in the step execution context, and the entire chunk — up to five reads, five processes and one write — is attempted again, three times in total. Anything the retry list does not name goes straight down the right-hand branch and, with no skip call in the chapter, terminates the step. The left-hand branch is the 8-6_iii addition: @EnableRetry puts an AOP proxy in front of the service, so retry happens before the exception can even reach the step, per item, with the exponential backoff. 8-6_ii sits between the two by calling RetryTemplate.execute explicitly inside the writer — same effect, no proxy, and you can see the RetryContext if you want it.

Retry granularity is the real lesson

A step-level retry re-runs up to five INSERTs, so the writer must be idempotent or the table must reject duplicates. A per-item retry inside the writer re-runs one registerUser call only. Nothing in the ch08 USER_REGISTRATION DDL enforces uniqueness, so the difference is observable as duplicate rows — that is why 8-6_ii and 8-6_iii exist at all.

Flow control and execution status (8-7)

ch08/recipe_8_7 contains exactly one class and no configuration, no job and no Main. HoroscopeDecider implements JobExecutionDecider and its decide(JobExecution, StepExecution) rolls ThreadLocalRandom.current().nextDouble() and returns FlowExecutionStatus.FAILED when it exceeds 0.9, otherwise FlowExecutionStatus.COMPLETED. That is the whole recipe: a decider is a callback that turns an execution into a routing key. Be aware of what the module does not show — the consuming side. There is no decision(…), split(…), flow(…) or next(…) call anywhere in the chapter's twelve job definitions, so the routing table that would interpret COMPLETED versus FAILED is left to the reader.

What the chapter does exercise is status reading. Every Main and both JobScheduler classes consume BatchStatus and ExitStatus, and only ever compare against running or print a code — no module assigns STOPPED, ABANDONED or UNKNOWN, and there is no JobExplorer or JobOperator bean in any of the sixteen modules, which is the machinery a stop would need.

Reading the flow. The signature is the contract: the decider receives the live JobExecution and the StepExecution that just finished (the latter is null when the decision sits before the first step), and its return value is a status string, not a step reference. The job definition is what binds FlowExecutionStatus names to targets, and since recipe_8_7 has no job, the only honest reading of the diagram is that the last edge is unimplemented in the source. Use the recipe_8_2_ii builder chain and add a decision node to see the routing.

Reading the flow. The transitions are the ones the source can produce: JobLauncher.run moves the execution out of CREATED once JobRepository has written its rows, and the terminal state is decided by the chunk loop. The loop while (batchStatus.isRunning()) { … sleep … } is a hand-rolled wait on this machine, and it is more fragile than it looks — batchStatus is captured once from jobExecution.getStatus() into a local before the loop and never refreshed, so it is a snapshot rather than a poll. Either the execution is already terminal at the first test and the body never runs, or the flag stays RUNNING forever and Main spins. The states the metadata schema permits but these recipes never reach are STOPPING, STOPPED, ABANDONED, UNKNOWN and NO_START: they require an operator call that is not in this chapter.

Async launching and scheduled launching (8-8, 8-9)

The 8-8 series is one question — who owns the thread — answered four times.

ModuleExecutor declaredHow the launcher finds it
recipe_8_8_inonenothing but @EnableBatchProcessing
recipe_8_8_iISimpleAsyncTaskExecutor taskExecutor() by the conventional bean name taskExecutor
recipe_8_8_iiiSimpleAsyncTaskExecutor customTaskExecutor() by explicit reference: @EnableBatchProcessing(taskExecutorRef = "customTaskExecutor")
recipe_8_8_iv, recipe_8_9 ThreadPoolTaskExecutor taskExecutor() group batch-executor max 10, and ThreadPoolTaskScheduler taskScheduler() group batch-scheduler pool 10 @EnableAsync and @EnableScheduling pick the beans up by type

recipe_8_8_iv is where the job gets a timer. JobScheduler is a @Component constructor-injected with JobLauncher and Job; runRegistrationsJobOnASchedule() carries @Scheduled(fixedDelay = 10_0000) — note that literal is one hundred seconds, an extra zero over the ten seconds the comment-free recipe_8_9 version writes as fixedDelay = 1000 * 10. Each tick builds parameters with addLocalDateTime("date", date) plus addString("input.file", "registrations") and calls jobLauncher.run(job, jobParameters), then prints the exit code. Because the date is the identifying parameter, every tick legitimately creates a new JobInstance — which is exactly what you want here, and exactly what would blow up on JOB_INST_UN if you dropped it from a scheduled job.

Two of these modules carry dead ends you should know about before running anything: recipe_8_8_iI/Main.java and recipe_8_8_iii/Main.java both construct a ClassPathXmlApplicationContext("batch.xml", "user-job.xml"), and no XML exists anywhere in ch08; recipe_8_8_iI also reads its DB username from the key datsSource.username, which is not in batch.properties. And recipe_8_9/Main.java asks for a job bean named dailySalesFigures that this module does not define (its only Job bean is insertIntoDbFromCsvJob), while its JobScheduler passes a java.util.Date to runRegistrationsJob(LocalDateTime) — that does not compile.

Reading the flow. @EnableScheduling registers ScheduledAnnotationBeanPostProcessor, which discovers the @Scheduled method on the JobScheduler bean and schedules it on the ThreadPoolTaskScheduler the module declares — the thread group name batch-scheduler is what you will see in a thread dump. The scheduler component holds JobLauncher and Job by constructor injection, so no ApplicationContext lookup is needed any more; that is the structural difference between 8-8 and the earlier recipes, where Main played container. run is still non-blocking, and here nobody waits for it — the tick just prints the exit code of whatever the launcher handed back, which in a synchronous test is the finished execution. The ThreadPoolTaskExecutor named taskExecutor is what lets several job runs overlap; with a fixed delay of ten seconds and a CSV big enough to take longer, you get concurrent instances of the same job, which is the point of 8-8's maxPoolSize(10).

Building and running the recipes

Each module is its own Gradle project; ch08/build.gradle applies the shadow plugin to all of them, attaches spring-context, spring-jdbc, spring-expression, spring-batch-core and h2, and sets Main-Class to com.apress.spring6recipes.springbatch.Main. The build is finalised by shadowJar, so one command gives you a runnable fat jar:

cd C:\Users\sahuk\IdeaProjects\spring-6-recipes
./gradlew :ch08:recipe_8_2_ii:build
java -jar ch08/recipe_8_2_ii/build/libs/recipe_8_2_ii-6.0.0-SNAPSHOT-all.jar

Replace recipe_8_2_ii with any module directory name exactly as spelled — :ch08:recipe_8_8_iI:build has a capital I, unlike its siblings. recipe_8_3 and recipe_8_7 have no Main, so the manifest points at a class that is not in the jar and java -jar cannot start them; build them to read them. The toolchain is Java 19 with --enable-preview on compile, test and exec, so run the jars on a matching JDK.

Prerequisites the source actually imposes

  • An input file. Every job reads @Value("file:${user.home}/batches/registrations.csv"). No CSV is checked into the chapter, so create ~/batches/registrations.csv with eleven comma-separated columns per row in the order firstName, lastName, company, address, city, state, zip, county, url, phoneNumber, fax (the order the tokenizer names in all twelve job definitions).
  • The database. recipe_8_1_i, 8_1_ii, 8_2_i, 8_2_ii, 8_3 and 8_4 point at jdbc:h2:~/batch, which H2 creates on first run — no server, no port. (The 8_3 copy is inert: that module has no configuration class.) Batch metadata and USER_REGISTRATION land in the same file, so imported rows accumulate across runs: the populator only ever runs CREATE TABLE USER_REGISTRATION, whose failure the continueOnError flag swallows. Use the shipped-but-unreferenced sql/truncate_all.sql by hand if you want a clean slate.
  • Derby, if you trust the properties file. Every module from recipe_8_5 to recipe_8_9 (ten of them) instead declares datasource.url=jdbc:derby://localhost:1527/batch;create=true and datasource.driverClassName=org.apache.derby.jdbc.ClientDriver, with app/app credentials except in recipe_8_8_iv, which uses sa/sa. Two things follow: no bean method ever reads datasource.driverClassName — DriverManagerDataSource is configured with URL, username and password only, so the driver has to be discoverable by DriverManager — and the chapter's dependency list contains H2 only, so a Derby-backed run needs derbyclient added to ch08/build.gradle (plus a Derby server on port 1527) or the URL changed back to jdbc:h2:~/batch.

Modules that need an edit before they start

Verified in source, not inferred:

  • recipe_8_5, 8_8_i, 8_8_iii and 8_9 read env.getRequiredProperty("dataSource.url") while their batch.properties defines datasource.url — capital S. That throws at context refresh, before any job runs.
  • recipe_8_5's step1 takes an ItemProcessor<UserRegistration, UserRegistration> parameter, but the module contains no processor class and no processor bean (that is recipe_8_4's UserRegistrationValidationItemProcessor). The context cannot satisfy the step.
  • recipe_8_8_iI and recipe_8_8_iii Mains load batch.xml and user-job.xml, which do not exist in the chapter; the Java @Configuration classes in the same module are ignored by those entry points. recipe_8_8_iI additionally reads datsSource.username.
  • recipe_8_8_iv's UserJob is the only one on the deprecated JobBuilderFactory / StepBuilderFactory API and sets .transactionManager(new DataSourceTransactionManager()) — a transaction manager with no DataSource, so it cannot govern the chunk.
  • recipe_8_9 does not compile: JobScheduler passes new Date() to runRegistrationsJob(LocalDateTime), and Main resolves a dailySalesFigures job the module never defines.
  • recipe_8_2_i, recipe_8_2_ii and recipe_8_3 declare the record component as stat, while the tokenizer names and the INSERT placeholder :state both say state — so in those three modules the column can never be bound. recipe_8_4 renames it. Separately, the INSERT string in recipe_8_2_ii (and recipe_8_4) ends with a trailing semicolon that the other ten definitions do not carry.

With the CSV in place and the H2 URL, recipe_8_1_i, 8_1_ii, 8_2_i, 8_2_ii and 8_4 are the modules whose properties, property keys and bean graph are all self-consistent, so their context refreshes and their Main reaches jobLauncher.run. The three 8_6 modules use matching datasource.* keys in Java and only need the Derby URL swapped for jdbc:h2:~/batch; the 8_8 modules additionally need their entry point repaired. Where a writer binds a named parameter to a property the record does not expose under that name, expect the failure at the first write, not at startup.

Things to watch while a job runs

  • The console prints Still running... from the isRunning() loop in Main, not from the batch itself — and per the caveat in Flow control and execution status, that flag is a snapshot, so you will see either none of those lines or an endless stream of them.
  • After a run, query the metadata: SELECT STEP_NAME, STATUS, COMMIT_COUNT, READ_COUNT, FILTER_COUNT, WRITE_COUNT, ROLLBACK_COUNT FROM BATCH_STEP_EXECUTION ORDER BY STEP_EXECUTION_ID DESC. On recipe_8_4 with a dirty CSV you should see READ_COUNT greater than WRITE_COUNT, the gap being FILTER_COUNT. On every module in the chapter the three skip counters read 0, because no skip rule is declared.
  • recipe_8_1_i and recipe_8_1_ii print the JobRegistry, JobLauncher and JobRepository toStrings and stop — that is the entire intended output of recipe 8-1, an infrastructure smoke test.

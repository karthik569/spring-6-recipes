Chapter 14 — Caching

This chapter starts from a computation that deliberately sleeps for 500 milliseconds and asks how to stop paying for it twice. It caches by hand first, then caches with Spring's Cache API by hand, and finally deletes the cache code entirely in favour of @Cacheable, @CachePut and @CacheEvict. The model that has to stick: the caller never touches the cache — a proxy created under @EnableCaching intercepts the call, asks a CacheManager, and either returns a stored value or lets the real method run and stores what comes back.

Mental model

Overview and module map

Two domain examples carry the chapter. Recipes 14.1 to 14.4 use CalculationService.heavyCalculation(BigDecimal base, int power), a method that sleeps 500 ms through com.apress.spring6recipes.utils.Utils.sleep (from shared-resources) and then returns base.pow(power). Because Main repeats the same arguments five times, the per-call elapsed time is a direct readout of whether caching happened. Recipes 14.5 to 14.7 switch to CustomerRepository and record Customer(long id, String name), where the interesting problem is no longer speed but coherence: what a cached entry does while the underlying data is created, updated and deleted underneath it.

The teaching order is deliberate. 14.1 caches without Spring. 14.2 caches with Spring's cache abstraction but still writes the code by hand. 14.3 deletes that code and annotates the method. 14.4 customises the key. 14.5 works through the write and evict annotations one at a time. 14.6 adds a transaction. 14.7 moves the cache out of process.

Two things this chapter does not contain

There is no @Caching (the container annotation for stacking several cache operations on one method), and no CacheErrorHandler, @CacheConfig, sync, condition or allEntries usage anywhere in ch14/ — checked by grepping every .java file in the fifteen modules. Nor is there a cache event listener. The only listener-shaped artefact is recipe_14_7_i/out/production/resources/cache-client.xml, a Spring GemFire namespace config declaring a gfe:local-region named customers with a gfe:cache-listener pointing at com.apress.springrecipes.caching.LoggingCacheListener — a class that does not exist in this repository, under an out/ directory that is IDE build output and not part of the Gradle build. It is a leftover from an earlier edition, not a recipe.

Recipes 14.1 to 14.7

The escalation ladder

Each rung removes one more piece of cache code from the service and moves it into configuration or an annotation.

Reading the flow. The load-bearing transition is 14_2_ii to 14_3_i. Before it, PlainCachingCalculationService.heavyCalculation contains the read-through pattern itself — cache.get(key, BigDecimal.class), a null check, the computation, then a write — and the class holds an org.springframework.cache.Cache field injected through its constructor. After it, the class holds no cache field at all: heavyCalculation is just return calculate(base, power) annotated @Cacheable("calculations") (ch14/recipe_14_3_i/src/main/java/com/apress/spring6recipes/caching/PlainCalculationService.java). The three 14_1_x rungs deserve a second look, because they already cache successfully with cache.get(key, k -> this.calculate(base, power)): Caffeine's own loader does the read-through, so Spring's abstraction buys provider swappability and annotation-driven code, not the caching itself. And note that the mechanism taught in 14.3 is orthogonal to the store — 14_3_i and 14_3_ii configure a byte-equivalent CaffeineCacheManager; only who applies the advice changes.

The core mechanism

Proxy interception, hit and miss

Everything else in the chapter assumes this picture. Once @EnableCaching is present, the container registers caching infrastructure and wraps any bean with a cache annotation in a proxy. Main obtains the bean with context.getBean(CalculationService.class) and therefore holds the proxy; the PlainCalculationService instance is reachable only from inside the interceptor.

Reading the flow. Hop by hop. (1) Main calls getBean and receives the proxy. (2) The call to heavyCalculation lands on the proxy's InvocationHandler, which delegates to Spring's CacheInterceptor — the advice class wired by @EnableCaching, in org.springframework.cache.interceptor, not in the chapter source. (3) The interceptor asks the KeyGenerator for a key from (target, method, params). (4) It asks the CacheManager for the Cache named in the annotation, here "calculations". (5) Cache.get(key) decides the branch. On a hit the interceptor returns the stored BigDecimal and the target method is never invoked — that is the entire optimisation, and it is why 14.1's five 500 ms lines become one slow line followed by four near-zero ones. On a miss the interceptor calls invocation.proceed(), the real calculate() runs, and the interceptor performs the put itself on the way out — the target has no idea a store exists. The CacheManager bean in ch14/recipe_14_3_i/…/config/CalculationConfiguration.java is a CaffeineCacheManager with maximumSize(1000) and expireAfterWrite(Duration.ofMinutes(5)), so the Cache participant is a CaffeineCache view over an in-heap Caffeine map.

Reading the flow. The left column is literal source: CalculationConfiguration declares @Configuration, @EnableCaching, a CacheManager cacheManager() bean and a CalculationService calculationService() bean returning new PlainCalculationService(). @EnableCaching is what pulls the advisor into the context, and it is not optional — its absence is exactly why 14_1_iii and the 14_2_x modules still cache correctly without it, since those services call the cache themselves. The decision node is the debugging rule to remember: annotate a private method, or call an annotated method from another method of the same object, and you take the lower branch — no interception, no error, just a cache that never appears to work. The edge from cmb to px records where the manager is injected: into the advice. And in 14_4_i this same configuration class additionally implements CachingConfigurer, so the graph gains one more edge from infra back to cfg for the KeyGenerator.

Recipe 14.5

Read, write and evict paths

The four annotations are not symmetric, and the asymmetry is where the bugs live. Three rules account for every variant in 14.5:

  • @Cacheable may skip the method body. @CachePut never does — the body always runs, then its result is stored.
  • @CacheEvict fires after the method returns successfully, because every recipe leaves beforeInvocation at its default of false. If the method throws, nothing is evicted.
  • @CachePut stores the return value, so a create method declared void could not use it.

Reading the flow. Start from ch14/recipe_14_5_iv/src/main/java/com/apress/spring6recipes/caching/MapBasedCustomerRepository.java. find carries @Cacheable(value = "customers", unless = "#result == null"); the unless expression is evaluated after the body against the returned value, and it is what stops a miss from storing a null. 14_5_i uses the bare @Cacheable(value = "customers"), so there the miss does store null under the probed id — ConcurrentMapCache and CaffeineCache both represent null with Spring's NullValue placeholder, since the underlying maps cannot hold one. create carries @CachePut(value = "customers", key = "#result.id"): #result is available to @CachePut and @Cacheable but not to a before-invocation @CacheEvict, and using the generated id as the key is the only option, because the caller does not know that id yet. update carries @CacheEvict(value = "customers", key = "#customer.id"), naming the method parameter so that eviction targets the Long key rather than the Customer object. remove carries the shorthand @CacheEvict("customers") and needs no key at all, because its only parameter is the primitive long customerId. One sentence to keep: reads may be short-circuited, writes never are, and eviction is a post-invocation action.

Reading the transitions. Loaded to Stale is the bug 14_5_i and 14_5_ii still have: update is unannotated in both, so customers.put(...) changes the map but not the cache, and the next find is served straight from Caffeine. The StopWatch prints about 0 ms, which reads as success, while the printed value is still Customer[id=1, name=Marten Deinum] after the rename to Josh Long. 14_5_iii fixes exactly that edge by adding @CacheEvict(value = "customers", key = "#customer.id"), turning Loaded into Cold so the following read reloads. Loaded to Ghost is the 14_5_i-only edge: remove has no annotation, so a deleted customer stays readable from cache. The self-loops on Stale and Ghost are the point of the diagram — a cached wrong answer is fast, so no timing signal warns you, and the only escape hatch is the 5-minute expireAfterWrite. The transition that never happens in these recipes is NullCached to Loaded: once a null is cached for an id, a later insert of that id stays invisible for up to five minutes, which is what unless = "#result == null" in 14_5_iv forecloses. In 14.5 that hazard is latent, because Main probes customerRepository.find(System.currentTimeMillis()) — an id the repository's AtomicLong will never generate. Change that probe to a small id and unless becomes load-bearing.

Recipe 14.4

Key resolution

Two keys must agree or the cache never hits: the one @Cacheable writes under, and the one a later read or @CacheEvict looks up with. Spring resolves the key in a fixed precedence order, and recipe_14_4_i occupies the third slot.

Reading the flow. A key attribute always beats a KeyGenerator, which is why 14_5_iii has to spell out key = "#customer.id". Left to the default generator, update(Customer customer) would key on the Customer instance while find(long) keyed on a Long; the eviction would then target an entry that does not exist, the stale value would survive, and the code would still look correct. The middle branch is drawn for completeness only — no module in this chapter uses the keyGenerator attribute. The interesting leaf is 14_4_i: CustomKeyGenerator implements org.springframework.cache.interceptor.KeyGenerator and returns params[0] + "^" + params[1], and it is installed by CalculationConfiguration implements CachingConfigurer overriding keyGenerator() as a @Bean. Because that makes it the context default, every cache annotation in the container uses it without naming it — and note that @Cacheable("calculations") in 14_4_i is character-identical to the one in 14_3_i yet stores under a completely different key. That is the operational hazard: add a second annotated service to this context and its key shape changes too, silently, along with its hit rate. CustomKeyGenerator indexing params[0] and params[1] blindly is also a latent break the moment the method signature changes.

Why key = "#customer.id" works on a record

Customer is record Customer(long id, String name), so it exposes id(), not getId(). Spring 6's SpEL resolves the property through that record-style accessor, which is what lets #customer.id and #result.id evaluate. On an older Spring, or if you prefer the dependency spelled out, #customer.id() is the method-call form of the same expression.

Types under cache

Cached domain types

One interface, three implementations across 14.5 to 14.7 — and the annotations sit on the implementation, never on the interface. That placement is not cosmetic: in proxy mode Spring inspects the target class's method.

Reading the structure. The load-bearing detail is hidden in one member line: PlainCachingCalculationService's -Cache cache field is a different type in the two recipe groups. In 14.1 ii and iii it is com.github.benmanes.caffeine.cache.Cache, the provider's own class, so replacing Caffeine means editing the service. In 14.2 it is org.springframework.cache.Cache (ch14/recipe_14_2_i/…/PlainCachingCalculationService.java), and that is what lets the same source file compile against ConcurrentMapCacheManager in 14_2_i and CaffeineCacheManager in 14_2_ii — the abstraction earning its keep in one line. From 14.3 the field disappears entirely. One member that the diagram deliberately omits is calculate: the 14.1 pair keep a private calculate(base, power) for the sleep-and-pow work, whereas 14.2 inlines it into heavyCalculation (and 14_2_ii even bypasses Utils.sleep for a raw Thread.sleep(500) with the InterruptedException swallowed). On the right, note that JdbcCustomerRepository is the only implementation carrying class-level @Repository and @Transactional, and that MapBasedCustomerRepository is reused verbatim by the Redis recipe. So in 14_7_i the system of record is a ConcurrentHashMap that dies with the JVM while the cache is a network service that survives it — an inversion worth checking before you copy the wiring into something real.

Recipe 14.6

Caching inside a transaction

recipe_14_6_i is the only module where cached data and a transaction share a method. Its configuration does one thing no other recipe does — it refuses to publish the Caffeine manager directly:

@Bean
public CacheManager cacheManager() {
    var caffeine = Caffeine.newBuilder()
                    .maximumSize(1000)
                    .expireAfterWrite(Duration.ofMinutes(5));
    var cacheManager = new CaffeineCacheManager();
    cacheManager.setCaffeine(caffeine);
    return new TransactionAwareCacheManagerProxy(cacheManager);
}

ch14/recipe_14_6_i/src/main/java/com/apress/spring6recipes/caching/config/CustomerConfiguration.java

Reading the flow. Two independent pieces of advice wrap this one bean: the transaction interceptor from @EnableTransactionManagement and the caching interceptor from @EnableCaching. Both default to the lowest precedence, so the order between them is not something the recipe may rely on — the nesting in the diagram is one plausible order, not a guaranteed one, and that is precisely why the CacheManager is wrapped rather than the advice reordered. Under TransactionAwareCacheManagerProxy, every Cache the caching interceptor receives is a transaction-aware decorator whose put, evict and clear are queued against the active transaction and replayed only in afterCommit; outside a transaction they apply immediately, and reads always go straight through. The consequence for find, which is annotated @Cacheable(value = "customers") and inherits the class-level @Transactional: a database read inside an uncommitted transaction does not warm the cache yet, so two find calls in one transaction both hit H2. The other reason to care is what happens on the way back: without the decorator, a rollback after a put would leave the cache holding a row the database does not have — wrong data served fast — whereas an evict lost to a rollback is merely slow. Last, note that find here uses jdbc.queryForObject, which throws EmptyResultDataAccessException for a missing id instead of returning null, and this variant dropped the unless guard along with the null-tolerant map. The map-backed recipes print Get 'Unknown Customer' (result) : null; this one aborts on that same first StopWatch step.

H2 is the database, not the cache

It is tempting to file 14.6 as "the JDBC cache recipe". It is not. There is no JDBC-backed CacheManager and no cache table; the store is still Caffeine. spring-jdbc and h2 are on the classpath because JdbcCustomerRepository reads and writes the customer table created by ch14/recipe_14_6_i/src/main/resources/schema.sql, loaded via new EmbeddedDatabaseBuilder().setType(EmbeddedDatabaseType.H2).setName("customers").addScript("classpath:/schema.sql").build(). The recipe teaches caching in front of JDBC, and the transaction interaction that comes with it.

Recipe 14.3_ii

Proxy mode versus AspectJ mode

14_3_i and 14_3_ii have the same service, the same private calculate, the same @Cacheable("calculations") and the same CaffeineCacheManager. Only the configuration annotation differs — and with it, the thing that applies the advice.

Reading the flow. Concretely, ch14/recipe_14_3_ii/…/config/CalculationConfiguration.java carries @EnableLoadTimeWeaving and @EnableCaching(mode = AdviceMode.ASPECTJ), and ch14/build.gradle gives that one module spring-aspects, spring-instrument, aspectjweaver and aspectjrt — every other ch14 module gets only spring-context, spring-context-support and caffeine from the subprojects block. Both branches still resolve the CacheManager from the container, so the store is identical; what changes is who holds the interception code. Be honest about the payoff here: Main in both modules calls through context.getBean(CalculationService.class), and calculate is private and unannotated, so the two variants print the same five timings. The ASPECTJ branch only earns its agent when you actually have self-invocation or non-bean instances, which is what the right-hand column of this diagram is for. Practically: run 14_3_ii without -javaagent and you get no interception and no exception — five slow calls, and a misleading conclusion that the cache is broken rather than unapplied.

Configuration and infrastructure

Providers, caches and eviction policy

One build file decides the classpath for all fifteen modules, so classpath presence and provider in use are different facts. ch14/build.gradle puts caffeine on every module, then adds AspectJ only to recipe_14_3_ii, spring-jdbc plus h2 only to recipe_14_6_i, and jedis plus spring-data-redis only to recipe_14_7_i. The provider actually used is whatever cacheManager() returns.

Reading the topology. Everything inside the subgraph boundary is in-heap: Caffeine and ConcurrentMapCache hold object references, which is why 14.5 can cache a Customer record with no serialization consideration at all and why restarting Main empties the cache completely. The single crossing is 14_7_i: RedisCacheManager.create(connectionFactory) over a bare new JedisConnectionFactory(), so host and port are the Jedis defaults (localhost:6379) — nothing is configured, nothing is externalised, no property file exists in the module. That is the one module that requires a running external service, and it is also why ch14/recipe_14_7_i/…/Customer.java uniquely declares implements Serializable: the cached value must be JDK-serialised onto the wire, so a hit still costs a socket round trip plus deserialisation. Read the edge back into px as the durability inversion: entries outlive the process, which turns 14.5's "the cache forgets" behaviour into 14.7's "the cache remembers something that is no longer true". The H2 cylinder sits inside the boundary on purpose — EmbeddedDatabaseBuilder starts a private in-memory database per process, so 14.6 needs no server either.

Two asymmetries to carry away

Expiry. Every Caffeine-based recipe sets expireAfterWrite(Duration.ofMinutes(5)) and maximumSize(1000) except 14_2_i, whose ConcurrentMapCacheManager has neither: that module's cache grows unbounded and lives until the JVM exits, so a missed @CacheEvict there is permanent rather than self-healing after five minutes. Shared state. 14_7_i sets no TTL either, and the store is out of process and persistent, so the 14_5_i-style "only remove evicts" bug is a classroom demonstration in 14.5 and a production incident in 14.7 — it survives a redeploy.

Practice

Building and running

Chapter 14 modules are plain main methods, not web applications, and none of them applies Gradle's application plugin. ch14/build.gradle applies the shadow plugin to every subproject, sets Main-Class to com.apress.spring6recipes.caching.Main (the same fully qualified name in all fifteen modules) and makes build finalise with shadowJar. So build, then run the fat jar from that module's build/libs:

# from the repository root
./gradlew :ch14:recipe_14_5_iv:build

java --enable-preview -cp "ch14/recipe_14_5_iv/build/libs/*" com.apress.spring6recipes.caching.Main

--enable-preview is not decoration. The root build.gradle passes it to every JavaCompile and pins toolchain { languageVersion = JavaLanguageVersion.of(19) }, and classes compiled with preview features must be run on the same major release with the flag. Expect one slow line and four fast ones in 14.1 to 14.4, and a StopWatch.prettyPrint() table in 14.5 to 14.7.

The connection is opened lazily by RedisCacheManager, so an unreachable server surfaces on the first cache operation rather than at context startup. redis-cli KEYS "*" shows the customers entries after a run, and they are still there when you restart Main — the visible proof that this cache is not in the JVM.

Comparing the 14.5 variants in one sitting

The five 14.5 modules share an identical Main, which makes them a hand-run regression suite. The diagnostic lines are Get 'Updated Customer 1' and Get 'Deleted Customer 1':

for r in 14_5_i 14_5_ii 14_5_iii 14_5_iv 14_5_v; do
  ./gradlew ":ch14:recipe_${r}:build" -q
  java --enable-preview -cp "ch14/recipe_${r}/build/libs/*" com.apress.spring6recipes.caching.Main
done

In 14_5_i the updated-customer lines print the old name (a stale hit at near 0 ms) and the deleted lines keep returning the customer. In 14_5_ii only the deleted lines move, to a genuine miss. In 14_5_iii the updated lines become a real miss too. In 14_5_iv the unknown lookup stops being cached and the post-create lookup is a hit instead of a 500 ms miss. 14_5_v prints the same thing as iv, because it is the same thing.

Build notes

The root gradle.properties pins org.gradle.java.home to a JDK 17 path on this machine while the toolchain asks for 19; if a :ch14:… compile task cannot find a 19 compiler, install a matching JDK or drop that line locally. Module coordinates come from the spring-6-recipes-dependencies platform: Spring Framework 6.0.3, Caffeine 3.1.2, Jedis 4.3.1, H2 2.1.214, AspectJ 1.9.19, project version 6.0.0-SNAPSHOT — so the shadow jar is recipe_14_x_y-6.0.0-SNAPSHOT-all.jar, which is why the classpath wildcard form above is the version-proof way to run it.

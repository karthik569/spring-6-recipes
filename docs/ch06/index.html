Chapter 6 — Spring Data Access

The chapter is a ladder of removals: every recipe strips one more piece of JDBC/ORM boilerplate off the same two toy domains until no persistence code is left to write. Recipes 6.0–6.5 push a VEHICLE table around with plain JDBC, then JdbcTemplate, then named parameters, then Spring's exception translation. Recipes 6.6–6.10 do the same for a COURSE entity: raw Hibernate, raw JPA, Spring-built SessionFactory/EntityManagerFactory, declarative transactions, and finally an interface-only Spring Data repository. 6.11 repeats the arc on the reactive R2DBC stack.

Overview and module map

Two unrelated domains are used on purpose. Vehicle (ch06/recipe_6_vehicle/src/main/java/com/apress/spring6recipes/vehicle/Vehicle.java) is a plain POJO with a caller-assigned natural key, and it is the subject of every relational-template recipe. Course (ch06/recipe_6_course/src/main/java/com/apress/spring6recipes/course/Course.java) is the chapter's only @Entity, and it is the subject of every ORM recipe. There is no relationship anywhere in the chapter — no @ManyToOne, no @OneToMany, no second table to join to — so the "entity graph" of Chapter 6 is a single node. That is deliberate: the recipes are about the plumbing between an object and one table, not about the object-relational metadata.

Two modules are not recipes at all. recipe_6_vehicle and recipe_6_course are java-library modules that ch06/build.gradle attaches to every other module: the vehicle one pulls in spring-jdbc, the course one pulls in spring-orm and hibernate-core. Everything from 6.0 to 6.5 depends on recipe_6_vehicle; everything from 6.6 to 6.10 depends on recipe_6_course; the 6.11 modules declare their own local Vehicle and VehicleDao because they need reactive return types.

Reading the flow. Each arrow means "delete code that the next recipe lets you delete". 6.0 to 6.1 removes try-with-resources and SQLException handling; 6.1 to 6.2 removes the ResultSet loop; 6.2 to 6.3 removes the new JdbcTemplate(dataSource) that every 6.1/6.2 method builds for itself; 6.3 to 6.4 replaces positional ? placeholders with :name ones; 6.5 changes nothing in the DAO and only varies how the resulting failure is observed. The dotted edge from 6.5 to 6.6 is the chapter changing domain, not technology — recipe_6_6_i is less Spring-integrated than recipe_6_5_i, since its Main still does new HibernateCourseDao(). 6.6 to 6.7 moves factory creation into @Bean methods, 6.7 to 6.8/6.9 moves transaction boundaries into annotations, and 6.9 to 6.10 deletes the DAO implementation class outright.

The bean graph that recipe 6.3__i (ch06/recipe_6_3_i/src/main/java/com/apress/spring6recipes/vehicle/config/VehicleConfiguration.java) assembles is three @Bean methods resolving right to left: dataSource() needs nothing and returns the HikariDataSource (setMinimumIdle(2), setMaximumPoolSize(5)); jdbcTemplate(DataSource) is called with that instance; vehicleDao(JdbcTemplate) is called with the template. This is the one structural change of recipe 6.3: in 6.1 and 6.2 the container only supplied a DataSource and the DAO built a throwaway JdbcTemplate per method call; here the template is a singleton, so its prepared-statement handling and its SQLException translation are shared. In 6.3__ii the last edge changes shape: JdbcVehicleDao extends JdbcDaoSupport and the bean method calls setJdbcTemplate(jdbcTemplate) instead of passing it through the constructor — which is also how every 6.4 and 6.5 DAO is wired, via NamedParameterJdbcDaoSupport.

Reading the flow. Steps 4 to 8 are exactly what JdbcTemplate replaces from recipe 6.0: it obtains the connection, executes, and closes the handle in a finally. Because Hikari owns the physical socket, that close is a pool return, not a disconnect — which is why 6.0's SimpleDriverDataSource and 6.0's pooled variants run identically but differ in cost. Note over T,P is the important part for the rest of the book: none of the JDBC recipes in this chapter declares a transaction, and there is no DataSourceTransactionManager bean anywhere in ch06/. Each update runs in its own implicit autocommitted transaction. Transactions first appear in 6.8, and only for Hibernate and JPA.

The JdbcTemplate call path

The layering the whole chapter converges on is four deep, and each recipe deletes one level of it. The names below are all real types used in ch06/; note that JdbcTemplate is the implementation of Spring's JdbcOperations contract, but no ch06 source ever declares a field of that interface type — every DAO and @Bean method spells JdbcTemplate.

Reading the flow. Follow JdbcVehicleDao down: the DAO hands SQL plus arguments to JdbcTemplate, the template asks HikariDataSource for a connection, PostgreSQL answers, and the template converts any SQLException before it reaches the DAO. Nothing intercepts that path — there is no proxy on any vehicle DAO, because no vehicle recipe enables @EnableTransactionManagement. On the ORM side the picture changes at 6.8: the CourseDao bean the container hands to Main is a proxy, and the transaction advice runs before store reaches HibernateCourseDao. That advice is what makes sessionFactory.getCurrentSession() and the injected EntityManager resolve to a thread-bound resource instead of throwing. The bottom edge shows recipe 6.10's odd position: CourseRepository has no class to annotate, so the generated proxy applies transaction advice around a Spring Data-supplied implementation that ultimately uses an EntityManager too.

Reading the flow. Three things are worth noticing. The hollow triangle (implements) chain is stable across the whole chapter: the container always hands Main a VehicleDao, so swapping PlainJdbcVehicleDao for NamedJdbcVehicleDao is a one-line config edit. The <|-- edge into JdbcDaoSupport only exists in recipe_6_3_ii — that inheritance is why the DAO can call getJdbcTemplate() with no field of its own, and the book treats it as the older style. Finally NamedJdbcVehicleDao keeps calling getJdbcTemplate() for its positional SELECT statements while only insert uses getNamedParameterJdbcTemplate(); both templates come from the same DataSource. Vehicle is the shared POJO from recipe_6_vehicle; it is not drawn as a class with relationships because none of these collaborators hold one another across calls.

Named parameters

Recipes 6.4__i to _iv (ch06/recipe_6_4_i/src/main/java/com/apress/spring6recipes/vehicle/NamedJdbcVehicleDao.java) all use the same statement, which is positional JDBC underneath:

INSERT INTO VEHICLE (COLOR, WHEEL, SEAT, VEHICLE_NO)
VALUES (:color, :wheel, :seat, :vehicleNo)

What differs is only how the four values are supplied: a HashMap with string keys (_i), that map wrapped in a MapSqlParameterSource (_ii), a BeanPropertySqlParameterSource built from the Vehicle itself (_iii), and in _iv an array of BeanPropertySqlParameterSource passed to batchUpdate so a whole collection is inserted in one named batch. The SELECT, UPDATE and DELETE statements in these modules are still written with ?, because the DAO reaches for getJdbcTemplate() for those.

Reading the flow. NamedJdbcVehicleDao.insert calls getNamedParameterJdbcTemplate().update(INSERT_SQL, source). The template parses INSERT_SQL, records color, wheel, seat, vehicleNo in the order their :name tokens appear, and rewrites the statement to the four ? placeholders PostgreSQL actually accepts. For each placeholder it resolves the name: Map and MapSqlParameterSource do a key lookup, while BeanPropertySqlParameterSource invokes the matching getter — which is why the names in the SQL must be property names (vehicleNo), never column names (VEHICLE_NO). The order of the columns in the INSERT list is irrelevant; only the order of first appearance of the names matters, and that is the safety this buys over 6.1__iv's positional varargs, where a swapped argument compiles fine and corrupts a row.

Objects, tables and the one entity

Course is the chapter's only mapped entity, and its mapping is deliberately flat. Every column name is stated explicitly with @Column(name = ...), so nothing depends on an implicit naming strategy; the id is DB-generated, so course.getId() is null before store and populated afterwards — which is exactly what every Main in 6.6 to 6.10 prints to demonstrate.

Reading the flow. The solid edge from Course is metadata read once at factory build time: @Entity plus @Table(name = "COURSE") pick the table, @Id with @GeneratedValue(strategy = GenerationType.IDENTITY) makes ID a database-assigned identity column, @Column(name = "TITLE", length = 100, nullable = false) constrains the title, and beginDate/endDate of type LocalDate map onto BEGIN_DATE/END_DATE. Because the id is generated, the DAOs branch on it: HibernateCourseDao.store calls session.persist(course) when course.getId() == null and session.merge(course) otherwise. The Vehicle edge is the opposite world — no annotations at all, a natural key the caller types by hand (new Vehicle("TEM0031", "Red", 4, 4)), and the mapping split across prepareStatement on the way in and a RowMapper on the way out. The dotted edge is the point: the two domains never meet, so there is no cascade, fetch mode or collection-valued end anywhere in this chapter.

Because BeanPropertyRowMapper matches columns to properties by relaxed name rules, VEHICLE_NO resolves to vehicleNo and BEGIN_DATE to beginDate. That is why 6.2__iii works with zero mapping code, and it is the same convention Spring Data relies on later.

Exception translation

Recipes 6.5__i, _ii and _iii ship the same NamedJdbcVehicleDao. Only Main and the classpath change, and the failure is reproducible by construction: each Main inserts VEHICLE_NO = EX0001, which is the primary key, so the first run succeeds and every later run violates it.

VariantWhat is addedWhat you see
6.5__inothing — Main has no try A Spring DataAccessException subtype escapes and kills the JVM, instead of a raw SQLException. That is the win: the DAO never mentions SQLException.
6.5__iicatch (DataAccessException e) then (SQLException) e.getCause() Prints getErrorCode() and getSQLState() — vendor detail is still reachable, it is just no longer mandatory.
6.5__iiisrc/main/resources/sql-error-codes.xml declaring SQLErrorCodes for product PostgreSQL with useSqlStateForTranslation=true and a CustomSQLErrorCodesTranslation for code 23505 The stack trace names MyDuplicateKeyException, which extends DataIntegrityViolationException — a type of your own, thrown by Spring's translator.

Reading the flow. The translation happens inside the template, which is why 6.5 changes no DAO code: the template catches the SQLException and asks for an SQLErrorCodes definition for the database product it is talking to. recipe_6_5_iii (ch06/recipe_6_5_iii/src/main/resources/sql-error-codes.xml) places its own sql-error-codes.xml on the classpath with a bean literally named PostgreSQL, sets useSqlStateForTranslation true, and adds one CustomSQLErrorCodesTranslation mapping code 23505 to com.apress.spring6recipes.vehicle.MyDuplicateKeyException. Everything downstream of the template keeps coding against the unchecked DataAccessException hierarchy, so a catch written for 6.5__ii would also catch 6.5__iii's custom type — it is a subtype, not a sibling.

The HibernateJpaVendorAdapter is where the vendor-specific knowledge lives: in 6.7__iv and _v setShowSql(true) and setGenerateDdl(true) replace both the hibernate.show_sql property and the hbm2ddl.auto=update property of 6.6/6.7__i-_iii, and the dialect is resolved from the live connection rather than named. _v adds setPackagesToScan and is the only 6.7 variant with no META-INF/persistence.xml at all — the last step before recipe 6.10's pure Spring Data configuration.

Two real traps in this ladder

The persistence.xml files under recipe_6_6_iii and recipe_6_7_iii/recipe_6_7_iv are not consistent: 6.6__iii uses jakarta.persistence.jdbc.url, while the two 6.7 files still use the javax.persistence.jdbc.* keys against a version="3.1" persistence unit under Hibernate 6. Expect to correct those keys before 6.7__iii can connect; 6.7__iv is less exposed because its DataSource is supplied by the container.

recipe_6_9_i and recipe_6_9_ii scan "com.apress.springrecipes.course" — no 6 in the package name. The entities live in com.apress.spring6recipes.course, so those two variants declare a scan that finds nothing, and recipe_6_10 has the corrected string.

Declarative transactions

Recipes 6.8 and 6.9 are where the chapter finally declares a transaction, and the code change is subtractive: three try/catch/finally blocks in recipe_6_7_i's store become four lines. Compare ch06/recipe_6_7_i/src/main/java/com/apress/spring6recipes/course/hibernate/HibernateCourseDao.java (open session, getTransaction().begin(), commit, rollback on RuntimeException, close in finally) with the same class in recipe_6_8_i: @Transactional public Course store(Course course) calling sessionFactory.getCurrentSession() and nothing else.

Reading the flow. Main never knows it holds a proxy: context.getBean(CourseDao.class) returns one because @EnableTransactionManagement turns the container's post-processor on and the DAO has @Transactional methods. The advice asks the transaction manager for a transaction before the DAO body runs, and the manager binds the resource to the thread. That binding is the whole trick behind the two apparently magic lines in these recipes: in 6.8 sessionFactory.getCurrentSession() returns the session the manager just bound rather than throwing, and in 6.9 the @PersistenceContext field is a shared, thread-resolving EntityManager proxy instead of one you create and close. The readOnly = true attribute on findById and findAll marks the flush mode read-only for those calls. Note the version skew the recipes leave in place: 6.9__i's delete does find then remove, while 6.9__ii does getReference then remove — one extra select versus one delete.

Spring Data repositories, imperative and reactive

Recipe 6.10 is the end of the imperative ladder: the DAO class disappears. ch06/recipe_6_10/src/main/java/com/apress/spring6recipes/course/CourseRepository.java is the entire persistence layer — an interface with an empty body — and @EnableJpaRepositories("com.apress.spring6recipes.course") on CourseConfiguration makes the container produce an implementation for it at startup. Everything 6.9 wrote by hand (merge, find, createQuery) now comes from generic methods declared on CrudRepository.

Recipe 6.11 walks the same four rungs on R2DBC: _i manages io.r2dbc.spi.Connection inside Mono.usingWhen with an explicit close callback; _ii replaces that with DatabaseClient.create(cf) and a fluent sql(...).bind(...).map(...).one(); _iii moves to R2dbcEntityTemplate with query(where("vehicleNo").is(vehicleNo)), requiring @Id on vehicleNo; _iv deletes R2dbcVehicleDao entirely and declares VehicleDao extends ReactiveCrudRepository<Vehicle, String> under @EnableR2dbcRepositories and AbstractR2dbcConfiguration.

Reading the flow. Both solid edges mean "no class was written". At startup @EnableJpaRepositories registers a RepositoryFactoryBean for each interface found in the base package, and @EnableR2dbcRepositories does the same for R2DBC; the bean Main gets from ctx.getBean(CourseRepository.class) is a proxy that dispatches save, findById, deleteById to Spring Data's own store implementation. In 6.10 the transaction advice also wraps those calls, which is why CourseConfiguration keeps @EnableTransactionManagement, a JpaTransactionManager and a LocalContainerEntityManagerFactoryBean — the repository still needs an EntityManagerFactory to sit on. In recipe_6_11_iv Main is unchanged from _i: it still does ctx.getBean(VehicleDao.class) and still calls save, findAll, delete, returning Flux/Mono — the name VehicleDao is re-declared in every 6.11 module, and only in _iv does it extend a Spring Data interface.

That is the same relaxed-name rule BeanPropertyRowMapper applied in 6.2__iii, and the same rule that makes @Id on vehicleNo mandatory in _iii.

Building and running

No module in ch06/ applies the application plugin, so there is no run task and no Main-Class in any manifest. The practical loop is compile, then launch the Main class from your IDE, or build the uber jar the root build.gradle registers:

# every module in the chapter, or one of them
./gradlew :ch06:build
./gradlew :ch06:recipe_6_3_i:build

# an all-in-one jar per recipe, then launch Main yourself
./gradlew :ch06:recipe_6_3_i:uberJar
java -cp ch06/recipe_6_3_i/build/libs/recipe_6_3_i-all.jar \
     com.apress.spring6recipes.vehicle.Main

The toolchain is fixed to JDK 19 with --enable-preview (root build.gradle), so a plain java of the same major version is needed to run the output.

Who creates the tables

  • VEHICLE, JDBC recipes (6.0–6.5): not created for you. The file ch06/recipe_6_vehicle/src/main/resources/sql/vehicle.sql and the copies under recipe_6_1_ii, recipe_6_1_iii, recipe_6_1_iv, recipe_6_1_v, recipe_6_2_i, recipe_6_2_ii, recipe_6_2_vi and recipe_6_4_iv are never referenced by any bean — there is no DataSourceInitializer or ResourceDatabasePopulator in these modules. Run it yourself with psql -U postgres -d vehicle -f vehicle.sql before the first insert.
  • VEHICLE, R2DBC recipes (6.11_*): created automatically. Each VehicleConfiguration declares a ConnectionFactoryInitializer with a ResourceDatabasePopulator(new ClassPathResource("/sql/vehicle.sql")), so the schema runs on every container start. Those copies begin with DROP TABLE VEHICLE;, which is why 6.11's Main can insert, print and delete and still be re-runnable.
  • COURSE: generated by Hibernate. 6.6 and 6.7__i to _iii and 6.8_* set hbm2ddl.auto=update (AvailableSettings.HBM2DDL_AUTO or the hibernate.hbm2ddl.auto property); 6.7__iv/_v, 6.9_* and 6.10 use HibernateJpaVendorAdapter.setGenerateDdl(true) instead. Either way the course database must exist first — DDL generation does not create it.

Reproducing the interesting behaviour

  • Recipe 6.5: run Main twice. The first insert of EX0001 succeeds silently; the second is what produces the DataAccessException. Only on the second run does 6.5__iii print MyDuplicateKeyException.
  • Recipes 6.0–6.4 are insert-only against the same table and will violate the VEHICLE_NO primary key on a second run for the same reason. Each variant uses a different literal (TEM0001, TEM0012, TEM0021, TEM0031, TEM0041, TEM0442), and 6.11 drops and recreates the table, so they mostly avoid colliding with one another.
  • Set hibernate.show_sql / setShowSql(true) output on the console to watch the identity insert assign COURSE.ID — every Main in 6.6 to 6.10 prints the object before and after store precisely to show that.

Three variants that do not work exactly as committed

  • recipe_6_0_iii: Main loads ClassPathXmlApplicationContext("vehicle-context.xml"), but the module contains no XML resource. Use its sibling VehicleConfiguration instead.
  • recipe_6_9_i and recipe_6_9_ii: setPackagesToScan("com.apress.springrecipes.course") names a package that does not exist in the repo.
  • recipe_6_11_iv: unlike recipe_6_11_iii, its Vehicle carries no @Id, while ReactiveCrudRepository<Vehicle, String> requires an id property. It also imports @Query and Flux without using either.
  • recipe_6_2_v: the top-level VehicleRowMapper is present but unreferenced — the DAO in that module actually uses BeanPropertyRowMapper.newInstance(Vehicle.class). The class is only exercised as a separate type in 6.2__ii, where it is a private inner class.
  • recipe_6_4_iii contains two DAOs, NamedJdbcVehicleDao and JdbcVehicleDao, both extending NamedParameterJdbcDaoSupport; the configuration wires NamedJdbcVehicleDao.

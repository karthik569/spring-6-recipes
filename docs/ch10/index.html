Chapter 10 — Spring Enterprise Integration

Every recipe in this chapter wires one Spring bean to one thing that lives outside the JVM: an MBeanServer, an SMTP host, a scheduler thread, a SOAP dispatcher, a metrics registry. The thread running through them is the endpoint/gateway shape — a Spring abstraction that owns the connection details and a thin bean of yours that only expresses intent. All of it is demonstrated on the same two domain examples: the replicator folder-copy service (JMX, mail, scheduling) and the weather temperature service (Spring Web Services), plus the court REST app borrowed from Chapter 3 for metrics.

Mental model

The chapter at a glance

Chapter 10 is not about messaging brokers. Read the imports and ch10/build.gradle and the external surfaces are exactly five: the JMX platform MBeanServer (recipes 10.1–10.3 and 10.11), an SMTP host (10.4), a quartz scheduler or Spring's own TaskScheduler (10.5, 10.6, 10.10), a SOAP endpoint hosted by Spring WS in a servlet container (10.7–10.9), and the JFR event stream (10.10). There is no spring-jms, no spring-rabbit, no spring-ldap and no jsch/commons-net dependency anywhere in the chapter, so no broker, directory or file server needs to be installed.

What each recipe teaches is the same structural move: pick the Spring gateway class (MBeanExporter, JavaMailSenderImpl, SchedulerFactoryBean, WebServiceTemplate, JmxMeterRegistry), declare it as a @Bean, and let it convert your method calls into protocol traffic. The eight 10.1 variants are the clearest illustration — one behaviour, eight progressively less verbose ways of reaching the same MBeanServer.

Reading the topology. Everything left of pms is an outbound adapter: MBeanExporter.register pushes bean:name=documentReplicator into the platform server, Transport.send in recipe_10_4_i/src/main/java/com/apress/spring6recipes/replicator/EmailErrorNotifier.java pushes a MimeMessage at port 3025, and JmxMeterRegistry in ch10/recipe_10_11_i/src/main/java/com/apress/spring6recipes/court/MemberClient.java registers one MBean per meter. Everything right of pms is inbound: a console attaches, calls setAttribute/invoke, and the MBeanServer reflectively calls JMXFileReplicator.replicate() on your bean. The dotted paths to reg and tom are the two places where a second JVM must be reachable — the RMI registry for recipe 10.3 and a servlet container for 10.8/10.9.

Recipe 10.1

Exposing a bean as an MBean

The management bean you want is an ObjectName, a description, a set of readable/writable attributes and a set of operations. Spring's MBeanExporter derives all four from an MBeanInfoAssembler, and the eight variants of 10.1 are simply eight assemblers — starting from doing the whole job by hand in Main.

Reading the ladder. Only 10_1_i uses the JMX API directly: its Main builds DescriptorSupport/ModelMBeanAttributeInfo objects, wires getSrcDir/setSrcDir descriptors onto the SrcDir attribute, and calls ManagementFactory.getPlatformMBeanServer().registerMBean(...) itself (ch10/recipe_10_1_i/src/main/java/com/apress/spring6recipes/replicator/Main.java, lines 26–72). From 10_1_ii the exporter takes over, and note the deliberate Map<String, Object> value "documentReplicator" — a bean name string, not the instance, so the exporter resolves it lazily from the context. The next three rungs only change how the management interface is discovered: hard-coded method names (setManagedMethods), the FileReplicator interface (setManagedInterfaces(FileReplicator.class)), and finally annotations. The annotations are only read from 10_1_v onwards — @ManagedResource/@ManagedAttribute/@ManagedOperation first appear in recipe_10_1_v/.../JMXFileReplicator.java and are absent from variants i through iv. 10_1_vi swaps in AnnotationMBeanExporter, which autodetects annotated beans, so the explicit setBeans map disappears; 10_1_vii adds setDefaultDomain("bean") so the generated ObjectName is deterministic, and 10_1_viii pins it outright with @ManagedResource(objectName = "bean:name=fileCopier,type=JMXFileReplicator") while adding the connector server.

Reading the collaborators. The only hard dependency of the exporter on your code is the assembler: JmxConfig.mbeanExporter(MBeanInfoAssembler assembler) in recipe_10_1_iii … _v takes it as a method parameter, so @Bean ordering guarantees the assembler exists before setAssembler is called. MetadataMBeanInfoAssembler is useless without AnnotationJmxAttributeSource — the assembler.setAttributeSource(new AnnotationJmxAttributeSource()) line in recipe_10_1_v/.../config/JmxConfig.java is what teaches it to look for @ManagedAttribute. @EnableMBeanExport (used by 10_1_viii, 10_2_i, 10_3_i, 10_3_ii) is the end state of the same idea: a context-level switch that contributes an AnnotationMBeanExporter, so no JmxConfig class is needed at all — which is exactly why recipe_10_2_i has no config/JmxConfig.java while recipe_10_2_ii does (it must call setNotificationListenerMappings, which the annotation cannot express).

Recipe 10.2

Publishing JMX notifications

A management bean that only exposes operations is write-blind: the console cannot see what happened while it was not looking. 10.2 makes JMXFileReplicator a notification source by implementing NotificationPublisherAware, and 10.2_ii then binds an in-process NotificationListener to the exported ObjectName.

Reading the round trip. Two hand-offs matter. First, hop 2: the caller is not your code but the MBeanServer, which invokes replicate() reflectively on the managed resource — that is why the method is synchronized in every 10.1/10.2 variant. Second, hops 5–7: notificationPublisher is not injected by the Spring container but by the exporter itself, through the setNotificationPublisher(NotificationPublisher) callback at the bottom of recipe_10_2_ii/.../JMXFileReplicator.java; the exporter forwards the new Notification("replication.complete", this, sequenceNumber.incrementAndGet()) to the server, which then dispatches to any listener registered for that ObjectName. The registration is the one line that makes 10.2_ii different from 10.2_i: mbeanExporter.setNotificationListenerMappings(Map.of("bean:name=documentReplicator,type=JMXFileReplicator", nl)) — and notice the type=JMXFileReplicator key. Because @ManagedResource declares no explicit objectName here, the default naming strategy builds domain:name=beanId,type=ShortClassName from setDefaultDomain("bean") plus the bean id documentReplicator. Get either of those wrong and the mapping silently never fires.

Recipe 10.3

Driving the MBeanServer from another JVM

Recipes 10.1 and 10.2 manage the JVM they run in. 10.3 splits the application in two: Server.main publishes its platform MBeanServer over a JMX RMI connector, and Client.main connects back. Variant _i works with the raw MBeanServerConnection; variant _ii wraps the same connection in MBeanProxyFactoryBean so the remote bean looks like the local FileReplicator interface.

Walking the arrows. Both ends use one identical service URL, defined in recipe_10_3_i/.../config/JmxServerConfiguration.java and recipe_10_3_i/.../config/JmxClientConfiguration.java and pinned in recipe_10_3_ii/.../config/JmxServerConfiguration.java as service:jmx:rmi://localhost/jndi/rmi://localhost:1099/replicator. The ConnectorServerFactoryBean is a FactoryBean whose product is a JMX JMXConnectorServer; on afterPropertiesSet it starts the connector and rebinds the JMXServiceURL into the RMI registry under the name replicator — so the registry must already be listening on 1099 when the server starts. On the client side MBeanServerConnectionFactoryBean also implements FactoryBean, and its product is the MBeanServerConnection that Client.main fetches with context.getBean(MBeanServerConnection.class). From there it is plain JMX: getAttribute(mbeanName, "SrcDir"), then setAttribute(mbeanName, new Attribute("DestDir", srcDir + "_backup")), then invoke(mbeanName, "replicate", null, null), with addNotificationListener(mbeanName, listener, null, null) registered before the invoke so the replication.complete event is not missed. In 10.3_ii all four calls collapse into fileReplicatorProxy.getSrcDir() / setDestDir(...) / replicate(): the MBeanProxyFactoryBean combines a connection factory, an ObjectName and a proxyInterface, and its InvocationHandler translates a getter into getAttribute, a setter into setAttribute and everything else into invoke.

Recipe 10.4

Sending mail through JavaMail

The task is fixed — report a copy failure to admin@localhost — and the five variants are a countdown of how much of Jakarta Mail Spring is willing to hide. ch10/build.gradle adds com.sun.mail:jakarta.mail to recipe_10_4_i through _v and to nothing else, so mail is the only place in the chapter where jakarta.mail.* types appear.

Reading the ladder. In recipe_10_4_i the bean is pure Jakarta Mail: Session.getDefaultInstance(props, null) with mail.smtp.host=localhost/mail.smtp.port=3025, a hand-built MimeMessage, and a static Transport.send(message). Nothing is injectable, so the connection details live inside the method. 10_4_ii moves them to JavaMailSenderImpl.setHost/setPort/setUsername/setPassword in config/MailConfiguration.java and narrows the injection point to the MailSender interface, so only send(SimpleMailMessage) is reachable — enough for plain text, not enough for attachments. 10_4_iii adds a second collaborator, the copyErrorMailMessage SimpleMailMessage template, and the notifier becomes new SimpleMailMessage(template) followed by setText(String.format(template.getText(), ...)) — a copy-then-fill idiom, because SimpleMailMessage is mutable and shared. 10_4_iv widens the dependency to JavaMailSender so it can call createMimeMessage(), wraps the result in MimeMessageHelper(message, true) for multipart, and attaches new ClassPathResource("beans.xml") — that attachment is why beans.xml survives in the resources of 10_4_iii, _iv and _v, although only _iv and _v actually read it. Finally 10_4_v hands the whole build to a MimeMessagePreparator lambda and calls mailSender.send(preparator), so the sender owns session creation, message assembly and the send, and the helper never escapes the callback.

Where these recipes go wrong as committed

recipe_10_4_ii/Main.java and recipe_10_4_v/Main.java scan "com.apress.springrecipes.replicator.config" — note the missing 6 — and the actual package is com.apress.spring6recipes.replicator.config. No beans are found, so context.getBean(ErrorNotifier.class) throws. The same typo appears in the leftover beans-jmx.xml/beans.xml component-scan lines of 10.1, 10.2_ii, 10.5 and 10.6 (all of which use Spring 3.2-era schema locations and are not loaded by the Java Main classes at all). recipe_10_4_iii/_iv/_v use MailConfiguration.class and are fine.

Recipes 10.5, 10.6, 10.10

Triggering work on a timer

Three ways to make replicate() happen by itself. 10.5 uses Quartz twice raw (_i, _ii) and twice through Spring's Quartz integration (_iii, _iv); 10.6 and 10.10 use Spring's own scheduler with no third-party library at all. The distinction the book cares about is where the trigger lives: Quartz keeps JobDetail and Trigger objects (and can persist them), while ScheduledAnnotationBeanPostProcessor keeps an in-memory list of ScheduledMethodRunnables that die with the context.

Reading the hand-off. The hop from WQ to JOB is the interesting one, because a Quartz job is not a Spring bean: Quartz instantiates FileReplicationJob.class reflectively per fire. In recipe_10_5_i/_ii the collaborator therefore has to travel through the JobDataMap: jobDataMap.put("fileReplicator", documentReplicator) in Main, then (FileReplicator) dataMap.get("fileReplicator") inside execute(JobExecutionContext). From recipe_10_5_iii the job instead extends QuartzJobBean and declares a setFileReplicator setter; the job instance is created by Quartz but the property is populated by Spring from the scheduler context, so executeInternal(JobExecutionContext) can use the field directly — and the wiring moves out of Java and into QuartzConfiguration, where JobDetailFactoryBean.setJobDataAsMap(singletonMap(...)) supplies the value. The two trigger flavours are the whole difference between _iii and _iv: SimpleTriggerFactoryBean with setStartDelay(5000) and setRepeatInterval(60000), versus CronTriggerFactoryBean with setCronExpression("0/60 * * * * ?") — which is the Spring-side mirror of SimpleScheduleBuilder.simpleSchedule().withIntervalInSeconds(60).repeatForever() versus CronScheduleBuilder.cronSchedule(...) in _i/_ii. SchedulerFactoryBean.scheduler(Trigger[] triggers) collects every trigger bean in the context by type, so adding a second trigger bean needs no change to the scheduler definition.

Without Quartz

recipe_10_6_i/.../config/SchedulingConfiguration.java is 20 lines: @EnableScheduling plus a ThreadPoolTaskScheduler bean with setThreadNamePrefix("s6r-scheduler-") and setPoolSize(10). The annotation switch registers ScheduledAnnotationBeanPostProcessor, which finds @Scheduled(fixedDelay = 60_000) on SimpleFileReplicator.replicate() and submits it to any bean of type TaskScheduler — matched here by name, taskScheduler. Because @Bean returns the concrete SimpleFileReplicator, the post-processor sees the annotated class rather than the FileReplicator interface. recipe_10_6_ii additionally implements SchedulingConfigurer and calls taskRegistrar.addFixedDelayTask(() -> fileReplicator.replicate(), Duration.ofSeconds(60)); the annotation is still on the bean, so the folder is replicated on two independent 60-second schedules. recipe_10_10_i starts from the 10.6_ii shape and changes only observability: Main calls ctx.setApplicationStartup(new FlightRecorderApplicationStartup()) before ctx.scan(cfg); ctx.refresh(), so every built-in startup step lands in JFR. _ii wraps the registration itself in a custom step by implementing ApplicationStartupAware and bracketing configureTasks with applicationStartup.start("s6r.register-task") / step.end(); _iii adds step.tag("task", "file-replicator") so the step is attributable in the recording.

All four 10.5 Main classes exit before the first fire

Unlike 10.1/10.2/10.3/10.6/10.10, none of recipe_10_5_i … _iv call System.in.read(). Their try-with-resources closes the context the instant scheduler.scheduleJob(job, trigger) returns, which shuts the scheduler down before the 5-second startDelay elapses. Add a blocking read (or a CountDownLatch) to actually observe a replication run.

Recipes 10.7, 10.8, 10.9

Document-driven web services

10.7 produces the contract: the README.txt runs the sample request.xml and response.xml through XMLBeans inst2xsd -design rd -enumerations never and hand-tightens the result into temperature.xsd. 10.8 and 10.9 implement that schema twice — once with DOM, once with JAXB — and each recipe is a matched pair of _Server (a WAR) and _Client (a console app).

Reading the endpoints. Three beans define the server surface. @EnableWs on SpringWsConfiguration installs the Spring WS infrastructure (MessageDispatcherServlet plus its MessageMapping post-processors); Initializer extends AbstractAnnotationConfigMessageDispatcherServletInitializer registers that servlet with the container and hands it getServletConfigClasses() = SpringWsConfiguration.class (with getRootConfigClasses() returning null, so there is exactly one context); and the bean name temperature on DefaultWsdl11Definition is what publishes the WSDL — Spring WS resolves a WSDL request to the bean of that name, and the bean pulls its schema from SimpleXsdSchema over /META-INF/xsd/temperature.xsd. On the client the gateway is WebServiceTemplate with setDefaultUri("http://localhost:8080/springws/services"); the WAR is renamed to springws.war by ch10/build.gradle, so /springws is the context and /services is the dispatcher path the template is expected to reach — confirm the exact mapping from the container's deployment log, since Initializer does not override getServletMapping().

Walking it. WeatherServiceClient.getTodayTemperature("Houston") builds Collections.singletonList(LocalDate.now()) and calls the WeatherService interface — the client never knows it is talking to a web service, because weatherServiceProxy is injected in its place. The proxy's job is payload assembly and one WebServiceTemplate call. On the server, the @PayloadRoot(localPart = "GetTemperaturesRequest", namespace = namespaceUri) annotation is the routing key that MessageDispatcherServlet matches, and the parameter binding is where the two recipes fork: 10.8 binds @RequestPayload Element and runs two pre-configured DefaultXPath objects (cityPath, datePath, both with setNamespaceURIs(Map.of("weather", namespaceUri))) and builds the reply with DocumentHelper.createDocument(); 10.9 binds @RequestPayload GetTemperaturesRequest, and that is only possible because SpringWsConfiguration extends WsConfigurerAdapter and registers new MarshallingPayloadMethodProcessor(marshaller()) in both addArgumentResolvers and addReturnValueHandlers — the same processor class plays the request-unmarshaller and response-marshaller role. WeatherServiceImpl is @Component("weatherService") and returns random values, so nothing here needs a weather backend. One detail to watch in 10.9: the JAXB classes carry the http://spring6recipes.apress.com/... namespace matching the code, while ch10/recipe_10_7/temperature.xsd still declares http://springrecipes.apress.com/weather/schemas; the copies of the schema under src/main/resources/META-INF/xsd/ in both server modules use the spring6recipes form, as the modules' own TemperatureEndpoint requires.

Recipe 10.11

Publishing metrics over JMX

The chapter closes by looping back to JMX, but through Micrometer instead of MBeanExporter: every HTTP request observed on either side of the wire becomes an MBean you can watch in a console. The REST app is the Chapter 3 court service (implementation(project(":ch03:recipe_3_shared"))), packaged as court.war.

Reading both halves. Client side: MemberClient.main gets a TaskScheduler and a RestTemplate from its own context, then scheduler.scheduleAtFixedRate(() -> listMembers(restTemplate), Duration.ofMillis(100)) polls http://127.0.0.1:8080/court/members. The template records a request only because restTemplate.setObservationRegistry(observationRegistry) is called in MemberClientConfiguration. Server side the observation is installed at the servlet-container boundary: CourtRestApplicationInitializer.getServletFilters() returns new DelegatingFilterProxy("metricsFilter"), and CourtRestConfiguration declares the bean metricsFilter(ObservationRegistry or) as a ServerHttpObservationFilter. That two-step matters — the filter instance Tomcat holds is a DelegatingFilterProxy shell that looks the real filter up by name in the DispatcherServlet context produced by getServletConfigClasses() = CourtRestConfiguration.class. From either observation, the single registered DefaultMeterObservationHandler(meterRegistry) turns the timer into Micrometer meters, and JmxMeterRegistry(JmxConfig.DEFAULT, Clock.SYSTEM) publishes them as MBeans. 10.11_ii's only delta is MeterBinderRegistrar: a @Component injecting MeterRegistry and ObjectProvider<MeterBinder>, whose @PostConstruct register() calls binders.forEach(b -> b.bindTo(registry)). It is picked up by @ComponentScan("com.apress.spring6recipes.court") in the WAR and by @Import({MeterBinderRegistrar.class, MeterBindersConfiguration.class}) in the client, and the client is the only place that declares actual binders — UptimeMetrics, JvmThreadMetrics, JvmMemoryMetrics — so the server registers the machinery and binds nothing.

Running

Building and running for real

Every ch10 module is a Gradle project — settings.gradle walks directories matching ^(?i)(ch|recipe|appendix).*$ and includes anything named recipe*, so the paths are :ch10:recipe_10_1_i … :ch10:recipe_10_11_ii. The chapter applies the shadow plugin to every subproject and finalises build with shadowJar, giving you a runnable fat jar at ch10/<module>/build/libs/<module>-6.0.0-SNAPSHOT-all.jar (version comes from gradle.properties).

# console recipes: build, then run the fat jar
./gradlew :ch10:recipe_10_1_vii:build
java --enable-preview -cp ch10/recipe_10_1_vii/build/libs/recipe_10_1_vii-6.0.0-SNAPSHOT-all.jar \
     com.apress.spring6recipes.replicator.Main

# the 10.3 pair, in two shells
./gradlew :ch10:recipe_10_3_i:build
java --enable-preview -cp ch10/recipe_10_3_i/build/libs/recipe_10_3_i-6.0.0-SNAPSHOT-all.jar \
     com.apress.spring6recipes.replicator.Server
java --enable-preview -cp ch10/recipe_10_3_i/build/libs/recipe_10_3_i-6.0.0-SNAPSHOT-all.jar \
     com.apress.spring6recipes.replicator.Client

Toolchain facts from the root build worth knowing before you start: java.toolchain.languageVersion is 19, gradle.properties pins org.gradle.java.home to a JDK 17 install, and --enable-preview is added to every JavaCompile, Test and JavaExec. Preview-flagged class files are only accepted by the exact JVM version they were compiled for, so run the jars on a Java 19 with --enable-preview, and let Gradle provision a 19 toolchain if you do not have one.

Source defects that stop a recipe cold

These are worth knowing before you spend time debugging wiring that the book never ran.

  • recipe_10_2_ii/.../Main.java starts new AnnotationConfigApplicationContext(FileReplicator.class, JmxConfig.class). It registers an interface as a component class and never loads FileReplicatorConfig, so there is no documentReplicator bean for the listener mapping to attach to. Add FileReplicatorConfig.class to run it.
  • recipe_10_3_ii/.../Client.java passes "bean:name=documentReplicator,type=JMXFileReplicator" as the scan package instead of JmxClientConfiguration.class, so fileReplicatorProxy is never defined.
  • recipe_10_4_ii and recipe_10_4_v Main classes scan com.apress.springrecipes.replicator.config (typo, missing the 6).
  • recipe_10_9_SpringWS_Client/.../SpringWSInvokerClient.java assigns SpringWsClientConfiguration.class to a local cfg and then builds an empty new AnnotationConfigApplicationContext(), so the very next getBean(WeatherServiceClient.class) fails. The 10.8 client does pass cfg.
  • recipe_10_1_i–viii, 10_2_ii, 10_4_iii–v, 10_5_ii–iv and 10_6_i–ii still ship beans.xml/beans-jmx.xml with Spring 3.2 schema locations and the misspelled scan package. They are reference material; nothing in a Main loads them.

Chapter 11 — Spring Messaging

Every recipe in this chapter is the same postal parcel travelling between two JVM processes — a FrontDesk producer and a BackOffice consumer — over a real message broker. The chapter is a ladder: variant i drives the broker with its own native client, then Spring’s JmsTemplate, message converters, transaction managers, listener containers and connection pooling are added one rung at a time; the last two recipes repeat the same ladder for RabbitMQ and Kafka. Nothing here is WebSocket, STOMP or GraphQL — spring-websocket, spring-messaging and spring-graphql appear nowhere in ch11/.

Mental model

One parcel, three brokers

The domain is a mail room tracking parcels. The payload is identical in all 32 modules: Mail with mailId, country, weight — a record in most modules, and a plain JavaBean with getters and setters in the four modules where a bean-style class is required (recipe_11_1_iii_BackOffice, recipe_11_1_iv_BackOffice, recipe_11_4_iv_FrontDesk, recipe_11_7_ii_FrontDesk). Producers run FrontDeskMain, consumers run BackOfficeMain; both boot a standalone AnnotationConfigApplicationContext and exit, so the two processes only ever meet through the broker.

Two destination names carry everything in the chapter: the queue mail.queue (JMS in 11.1–11.5, and the same literal reused as an AMQP routing key / queue name in 11.6) and the Kafka topic mails (11.7). Every destination is point-to-point: no JMS Topic and no pub/sub fan-out, no reply destination and no request-reply — JmsTemplate.sendAndReceive is never called and @SendTo is never declared anywhere in ch11/.

Reading the flow. Three producer entry points, three brokers, one payload. The left branch is what most of the chapter is: FrontDeskMain looks up a FrontDesk bean, that bean hands a Mail to a JmsTemplate (or, in recipe_11_1_i_FrontDesk, to a plain JMSContext), and Artemis parks a MapMessage on mail.queue. The middle of the branch matters: the queue has two possible readers — the polling BackOfficeImpl used by 11.1–11.3, and the push-based listener containers introduced in 11.4, which is exactly the axis the chapter turns on. The AMQP branch reuses the literal mail.queue but on a different broker: in 11.6_i it is published to the default exchange with that routing key, in 11.6_ii through RabbitTemplate.setRoutingKey("mail.queue"). The Kafka branch is the only one with an asynchronous return type — KafkaOperations.send("mails", ...) yields a future that FrontDeskImpl completes with whenComplete.

Where chapter 11 stops and chapters 10 and 12 start

Chapter 10 (ch10/build.gradle) has no broker on its classpath at all: it is remote invocation and scheduling — the replicator and weather packages, jakarta.mail for SMTP, quartz for jobs, and spring-ws-core for SOAP. If a call blocks and returns a value to the caller, it is chapter 10. Chapter 11 is the broker-native layer: spring-jms, spring-rabbit, spring-kafka, JmsTemplate, message converters, MessageListener containers, @JmsListener, @RabbitListener, @KafkaListener. Fire-and-forget, one queue, one topic. Chapter 12 (ch12/build.gradle) then puts spring-integration-core and spring-integration-jms on top of the same Artemis queue and re-expresses it as IntegrationFlow DSL, channels, transformers and @MessagingGateway (e.g. ch12/recipe_12_2_i/.../IntegrationConfiguration.java with its jmsInbound flow). Same broker, one abstraction higher.

Recipe 11.1

Four ways to hold a JmsTemplate

11.1 does not change the wire format at all — the payload is a JMS MapMessage with the keys mailId, country, weight in every variant: built by hand with session.createMapMessage() from 11.1_ii onward, and handed to the provider as a plain Java Map in 11.1_i. What changes is who owns the connection plumbing and where the destination lives.

Reading the flow. In recipe_11_1_i_FrontDesk the whole try-with-resources block — cf.createContext(Session.AUTO_ACKNOWLEDGE), new ActiveMQQueue("mail.queue"), ctx.createProducer().send(destination, mapContext) — sits inside FrontDeskImpl.sendMail, and the configuration class contributes nothing but the bean. One step right, FrontOfficeConfiguration declares connectionFactory(), mailDestination() and jmsTemplate(ConnectionFactory cf), and sendMail shrinks to jmsTemplate.send(destination, session -> ...) — a MessageCreator lambda is all that is left of the JMS API. At iii the front desk template is given setDefaultDestination(destination) while the back office template uses setDefaultDestinationName("mail.queue"), so both sides now call the destination-free overloads send(MessageCreator) and receive(). At iv the two implementations extend JmsGatewaySupport and read the template through getJmsTemplate(); the config changed from constructor injection to backOffice.setJmsTemplate(jms). Note that iii and iv also replace the back-office Mail record with a mutable JavaBean — a leftover of the Spring 5 original, not a functional requirement.

Reading the classes. Only two application types exist per side — FrontDesk/FrontDeskImpl and BackOffice/BackOfficeImpl — and the variants differ by how the messaging client reaches them: field injection (recipe_11_1_ii), inheritance from JmsGatewaySupport (recipe_11_1_iv, and again in recipe_11_2, recipe_11_3 and recipe_11_5_FrontDesk), or a constructor-injected KafkaOperations (recipe_11_7_i_FrontDesk, which is the interface KafkaTemplate implements). The AMQP twin of the inheritance style is recipe_11_6_ii_FrontDesk’s FrontDeskImpl extends RabbitGatewaySupport calling getRabbitOperations().convertAndSend(mail). JmsTemplate is the single object every JMS recipe funnels through, and it is where each recipe installs its knobs — setReceiveTimeout, setDefaultDestinationName, setMessageConverter.

Recipe 11.2

convertAndSend, receiveAndConvert, and a converter of your own

11.2_i keeps the Map from 11.1 but stops building the message by hand: FrontDeskImpl.sendMail does getJmsTemplate().convertAndSend(map) and BackOfficeImpl.receiveMail does (Map<String, ?>) getJmsTemplate().receiveAndConvert() before reassembling a Mail with convert(Map). No setMessageConverter call exists in either configuration, so the template’s default conversion — the one that maps a Map payload to a MapMessage and back — is doing the work. 11.2_ii is the recipe where the chapter introduces MailMessageConverter, which implements org.springframework.jms.support.converter.MessageConverter with toMessage(Object, Session) and fromMessage(Message); the identical class is copy-pasted into eleven modules: both sides of 11.2_ii, 11.3, 11.4_iii and 11.5, the front desk of 11.4_i and 11.4_ii, and the back office of 11.4_iv.

Reading the sequence. The producer never sees jakarta.jms types: JmsTemplate.convertAndSend opens a connection and session from the ConnectionFactory bean, asks the registered converter for a Message, sends it and closes the session — a connection-per-send that 11.5 exists to fix. setDefaultDestinationName("mail.queue") is what lets convertAndSend be called with one argument. On the return leg, the crucial contract is symmetry: BackOfficeConfiguration installs new MailMessageConverter() on its own template, because fromMessage casts to MapMessage and would throw a MessageConversionException on anything else. setReceiveTimeout(10000) is only on the back-office template; with no message queued the consumer blocks for ten seconds and then receiveAndConvert yields null, which BackOfficeImpl.receiveMail happily prints as Recevied: null — the typos in BackOfficeMain are in the source.

Reading the classes. Spring’s three messaging projects each expose the same converter on the container factory idea, and the recipes show all three: JMS via SimpleJmsListenerContainerFactory / DefaultJmsListenerContainerFactory, AMQP via SimpleRabbitListenerContainerFactory with Jackson2JsonMessageConverter, Kafka via ConcurrentKafkaListenerContainerFactory with StringJsonMessageConverter. The important asymmetry is 11.4_ii versus 11.4_iii: both use @JmsListener(destination = "mail.queue"), but because ii registers no converter the listener method must take a Map, while iii registers MailMessageConverter on the factory and the method becomes displayMail(Mail mail). The converter therefore belongs to the receiving endpoint, not to the sending one — and the annotated container needs its own copy because it does not borrow the sending JmsTemplate.

Recipe 11.3

@Transactional over a JMS session

11.3 is the only recipe in the chapter that turns on Spring’s transaction machinery, and it does so on both sides symmetrically. recipe_11_3_FrontDesk/.../config/FrontOfficeConfiguration.java and its BackOfficeConfiguration twin are the 11.2_ii bean methods plus @EnableTransactionManagement and a JmsTransactionManager transactionManager(ConnectionFactory cf) bean; FrontDeskImpl.sendMail and BackOfficeImpl.receiveMail are the 11.2_ii methods plus @Transactional. Because the gateway classes implement interfaces, the proxy is a JDK dynamic proxy and context.getBean(BackOffice.class) in BackOfficeMain returns the proxy, not the target.

Reading the flow. Start at BackOfficeMain: the config class is the only input, and the container’s @Bean factory methods are invoked lazily in dependency order — connectionFactory() first, because both jmsTemplate(ConnectionFactory cf) and transactionManager(ConnectionFactory cf) request it. The @EnableTransactionManagement annotation registers the auto-proxy creator, so the backOffice bean that leaves the container is a proxy around the target BackOfficeImpl. When receiveMail() is invoked, the transaction interceptor opens a transacted JMS session through JmsTransactionManager and binds it to the thread before the target method body runs; JmsTemplate, given the same ConnectionFactory, detects that bound session instead of creating a fresh one, and the acknowledgment happens at commit rather than immediately. On the front-desk side the same pairing makes convertAndSend commit the send. Note the second-order effect: ch11/build.gradle adds spring-aop and aspectjtools to these two modules only — the annotation-driven proxying is what needs them.

Recipe 11.4

From MessageListener to @JmsListener

11.4 is where the back office stops asking and starts receiving. The FrontDesk half of 11.4_i–iii is unchanged from 11.3 and is only there to have something to send; all four variants differ in the BackOffice container, and each BackOfficeMain is now just AnnotationConfigApplicationContext followed by System.in.read() — the process exists only to keep the container alive.

  • recipe_11_4_i_BackOffice: a SimpleMessageListenerContainer returned from a bean method declared as Object container(ConnectionFactory cf, MailListener msgListener), configured with setDestinationName("mail.queue") and setMessageListener(msgListener); MailListener implements MessageListener and casts to MapMessage itself.
  • recipe_11_4_ii_BackOffice: @EnableJms and a SimpleJmsListenerContainerFactory; the listener is now an annotated POJO method @JmsListener(destination = "mail.queue") displayMail(Map).
  • recipe_11_4_iii_BackOffice: identical, except the factory gets setMessageConverter(new MailMessageConverter()) and the parameter becomes Mail. The mailListener() bean method stays in the config even though the annotation no longer needs an explicit reference.
  • recipe_11_4_iv_BackOffice: DefaultJmsListenerContainerFactory plus setSessionTransacted(true) and the converter. Its FrontDesk is also the only module in the chapter that boots XML: new GenericXmlApplicationContext("beans-front.xml").

Reading the sequence. Ordering is the whole story. The container bean is started by the context refresh — SimpleMessageListenerContainer and the @JmsListener containers are lifecycle beans, which is why 11.4_i can declare the bean with return type Object and still get started: the container inspects the instance, not the signature. System.in.read() then blocks the non-daemon main thread so the JVM survives long enough for the broker to push. From ii onwards the registration path changes: @EnableJms installs a post-processor that scans beans for @JmsListener and builds a container per method from the factory named jmsListenerContainerFactory — that bean-name match is the only link between the annotation and the configuration. iv’s DefaultJmsListenerContainerFactory.setSessionTransacted(true) is the substantive upgrade over iii: with a transacted session, acknowledgment is the container’s decision after displayMail returns without throwing; a listener that throws rolls the session back and the message is redelivered instead of silently consumed.

recipe_11_4_iv_FrontDesk does not run as checked in

FrontDeskMain in that module does new GenericXmlApplicationContext("beans-front.xml"), but there is no src/main/resources directory anywhere under ch11/ — no XML file to resolve. Pair recipe_11_4_iv_BackOffice with the Java-config producer from recipe_11_4_i_FrontDesk instead; the wire format is compatible, since that producer sends a Map that lands as a MapMessage which iv’s MailMessageConverter reads back.

Recipe 11.5

Two kinds of pooling, and which bean wins

11.5 is a performance recipe, and the two sides deliberately use different libraries. The front desk wraps Artemis in Spring’s own CachingConnectionFactory (spring-jms, reusing the connection and cached sessions for producers); the back desk wraps it in MessagingHub JmsPoolConnectionFactory from org.messaginghub:pooled-jms, added to these two modules only, and marks it @Primary. The listener side keeps 11.4_iv’s DefaultJmsListenerContainerFactory with setSessionTransacted(true) and the converter; the listener itself is unchanged (@JmsListener(destination = "mail.queue") displayMail(Mail mail)).

Reading the flow. Both subgraphs start from the same ActiveMQConnectionFactory bean and end in a decorated wrapper, but they show two different disambiguation rules. In the front desk there are two beans assignable to jakarta.jms.ConnectionFactory, so jmsTemplate(CachingConnectionFactory cf) narrows by the declared parameter type, while transactionManager(ConnectionFactory connectionFactory) stays ambiguous and falls back to matching the parameter name against the bean name — the raw factory, not the caching one. That is a real behavioural consequence, not a typo: a caching connection factory under a JMS transaction manager is the combination Spring warns about. In the back office the ambiguity is resolved declaratively instead: pooledConnectionFactory carries @Primary, so jmsListenerContainerFactory(ConnectionFactory cf) receives the pool and the container borrows pooled connections per consumer. Nothing else changed relative to 11.4_iv — the pooling recipe is purely an infrastructure swap.

Recipes 11.6 and 11.7

The same ladder on RabbitMQ and Kafka

11.6 and 11.7 replay 11.1_i → 11.2/11.4 for two non-JMS transports, and the module pattern is identical: i uses the vendor client directly, ii uses the Spring project. 11.6_i (recipe_11_6_i_FrontDesk) builds a com.rabbitmq.client.ConnectionFactory with host localhost, credentials guest/guest, port 5672, declares the durable queue, and publishes JSON from an ObjectMapper via basicPublish("", "mail.queue", null, bytes) — the empty exchange, i.e. the default exchange, whose routing rule is “deliver to the queue named by the key”. Its back office registers an anonymous DefaultConsumer in handleDelivery and calls channel.basicConsume("mail.queue", true, consumer) with auto-acknowledgment on; receiveMail() returns null because the method is there only to install the consumer.

11.6_ii replaces all of that with spring-rabbit: @EnableRabbit, SimpleRabbitListenerContainerFactory and @RabbitListener(queues = "mail.queue") on the consuming side, and on the producing side a RabbitTemplate configured with setRoutingKey("mail.queue") plus Jackson2JsonMessageConverter, injected into a FrontDeskImpl extends RabbitGatewaySupport and used as getRabbitOperations().convertAndSend(mail). The connection is org.springframework.amqp.rabbit.connection.CachingConnectionFactory("127.0.0.1") on 5672 — Spring AMQP’s caching factory, not the JMS one from 11.5.

11.7 is Kafka and the only place the chapter leaves point-to-point for a partitioned log. Note what is not here: no consumer-per-message acknowledgment control, no re-delivery, no transaction manager, and the destination is the topic literal mails in both KafkaOperations.send and @KafkaListener(topics = "mails").

Reading the sequence. The producer leg is asynchronous in a way the JMS recipes never were: FrontDeskImpl holds a KafkaOperations (the interface KafkaTemplate implements) and its send("mails", ...) returns a future, which whenComplete turns into a log line with sendResult.getRecordMetadata() — hence both FrontDeskMain classes end in System.in.read(), because the record would otherwise be sent and the JVM would exit before the callback ran. Two different KafkaTemplate generics distinguish the variants: i is KafkaTemplate<Integer, String> fed by StringSerializer, ii is KafkaTemplate<Integer, Object> fed by JsonSerializer, and that is why recipe_11_7_ii_FrontDesk’s Mail became a getter-driven JavaBean. On the consuming leg the deserializers were deliberately left alone — IntegerDeserializer and StringDeserializer in both variants — so ii bridges JSON-in-a-String to a Mail by putting StringJsonMessageConverter on the ConcurrentKafkaListenerContainerFactory. Offset management is the container’s, which is why consumerConfiguration() pins GROUP_ID_CONFIG to group1.

Running it

Build, start a broker, run both mains

Modules are addressed as :ch11:<dir>; settings.gradle walks every ch* directory containing “recipe” and includes it. There is no application plugin in this chapter, so there is no run task. ch11/build.gradle applies the shadow plugin to every subproject, makes build finalise on shadowJar, and sets the jar manifest’s Main-Class to com.apress.spring6recipes.post.FrontDeskMain or ...post.BackOfficeMain based on whether the module name contains Front or Back:

./gradlew :ch11:recipe_11_2_ii_FrontDesk:build
java --enable-preview -jar ch11/recipe_11_2_ii_FrontDesk/build/libs/recipe_11_2_ii_FrontDesk-6.0.0-SNAPSHOT-all.jar

The version comes from gradle.properties (version=6.0.0-SNAPSHOT) and the -all classifier from shadow, so list build/libs rather than typing the name. The root build passes --enable-preview to every JavaCompile and JavaExec task, so keep that flag on the command line when you run the jar, and note that gradle.properties pins org.gradle.java.home to a local JDK 17 path while the root build requests a Java 19 toolchain — adjust it for your machine before the first build.

Run the consumer first, then the producer. The consumer mains for 11.4 onwards block on System.in.read(), so press Enter to shut them down. Java 19 is the toolchain version pinned in the root build.gradle, and --enable-preview is passed to compile, test and exec tasks.

Verified constraints

  • No recipe in ch11/ starts an embedded broker. artemis-jakarta-server is on every subproject’s classpath from ch11/build.gradle, but no source file references a broker service — you must supply the process.
  • recipe_11_4_iv_FrontDesk fails to start standalone: it loads beans-front.xml, and no XML resource exists under ch11/.
  • recipe_11_6_i_FrontDesk’s configuration carries @EnableScheduling but nothing in the chapter declares a scheduled method — no @Scheduled exists in ch11/.
  • recipe_11_4_ii_BackOffice imports CachingConnectionFactory without using it; the plain factory is injected there. The caching wrapper first appears in 11.5.
  • Every recipe is a plain main method. There are no tests, no src/test sources, no application.properties and no Spring Boot in this chapter.

Chapter 9 — Spring Data Access with NoSQL

Chapter 9 takes one tiny domain — a Vehicle record of four fields, plus a Star Wars Character and Planet pair for the graph store — and walks it up the same six-step ladder against four different databases: MongoDB, Redis, Neo4j and Couchbase. Each step swaps one thing only: the raw client for a bean, the client API for a Spring Data template, the explicit collection name for entity metadata, the template for a repository proxy, and finally the imperative call for a Mono. Nothing in the chapter is mocked or embedded: every module opens a socket to a server you must start yourself.

Mental model

Chapter map and module index

Four recipe numbers, four stores, one shape of problem. recipe_9_1_* is MongoDB, recipe_9_2_* is Redis, recipe_9_3_* is Neo4j and recipe_9_4_* is Couchbase — confirmed straight from ch09/build.gradle, which pins mongodb-driver-sync and spring-data-mongodb on 9.1, jedis (plus lettuce-core on 9.2.viii) and spring-data-redis on 9.2, neo4j-java-driver and spring-data-neo4j on 9.3, and java-client with spring-data-couchbase on 9.4. Cassandra and Neo4j-HTTP are absent; there is no Cassandra driver anywhere in the chapter.

Three of the four stores are driven by the same Vehicle record (vehicleNo, color, wheel, seat) against a structure named vehicles. Only Neo4j gets a second domain: Character and Planet, because a document or a hash cannot demonstrate a relationship, and the whole point of 9.3 is that a join becomes an edge. Read any group as a diff: line up two variants and find the single annotation, bean or return type that changed.

Structure

One ladder, four stores

The chapter is a migration exercise repeated four times. Steps 1 and 2 are pure Spring Framework: AnnotationConfigApplicationContext plus @Bean methods, with the @PreDestroy annotation on cleanUp() doing the teardown when the context closes (for example ch09/recipe_9_1_ii/src/main/java/com/apress/spring6recipes/nosql/MongoVehicleRepository.java drops the whole database there). Steps 3 to 5 are pure Spring Data: a template that owns conversion, entity metadata that removes the repeated structure name, and finally a repository proxy that removes the template call from your code. Step 6 changes the return types to Mono and Flux and swaps the client jar.

One build-wide detail makes the wiring in step 2 possible without any @Autowired: the root build.gradle adds -parameters to every JavaCompile, so constructor parameter names such as vehicleRepository(RedisTemplate<String, Vehicle> redis) survive into the class file and Spring can match by name as well as by type.

Reading the ladder. Follow a single store up the rungs and count what you delete. From rung 3, getCollection() and the four dbVehicle.getString(...) calls of 9.1.i are gone, replaced by mongo.save(vehicle, collectionName) and mongo.findOne(query, Vehicle.class, collectionName). Rung 4 is the smallest change with the biggest effect: adding @Document(collection = "vehicles") to the record in 9.1.iv lets the repository drop the third argument on every call, because the template now asks the mapping metadata instead of the caller. The same rung lands differently elsewhere: @RedisHash("vehicles") in 9.2.vii replaces the DB_NAME constant, @Node plus @Relationship in 9.3.v replace the five Cypher constants of 9.3.iii, and @Id on vehicleNo in 9.4.iii removes the key argument that 9.4.i passes to upsert. Rung 5 is the one that changes your class: in 9.1.v MongoVehicleRepository disappears entirely and the findByVehicleNo body is replaced by a method name on an interface that extends MongoRepository — the @EnableMongoRepositories registrar posts a MongoRepositoryFactoryBean for it, so ctx.getBean(VehicleRepository.class) in Main is unchanged. Rung 6 keeps the method names but makes every return type a publisher, which is why the Main classes there grow a CountDownLatch.

Recipe 9.1

MongoDB: hand mapping, template, derived query

Recipes 9.1.i and 9.1.ii are the control group: the conversion is the application's job. MongoVehicleRepository holds two private transform overloads — Vehicle to new Document("vehicleNo", ...).append("color", ...) and back again through dbVehicle.getString("color") / dbVehicle.getInteger("wheel") — plus StreamSupport.stream(getCollection().find().spliterator(), false) to turn a FindIterable into a List. From 9.1.iii, MongoTemplate and its MappingMongoConverter do that work, and the record must then carry an id for Mongo's own _id — which is exactly why Vehicle grows a fifth component and every save call in Main starts with null.

Reading the classes. Two different edges out of MongoVehicleRepository are the whole lesson. On the 9.1.i path the repository holds a MongoClient, walks getDatabase(databaseName).getCollection(collectionName) itself, and calls its own transform on every row in and out — the Document to Vehicle edge is a private method in application code. On the 9.1.iii path the repository holds a MongoTemplate and the same two arrows are taken by MappingMongoConverter inside Spring Data instead; note that MongoTemplate has two save overloads here because 9.1.iii passes collectionName explicitly while 9.1.iv does not. The mechanism that makes the one-argument form legal is metadata: @Document(collection = "vehicles") on the record populates the MongoPersistentEntity that the template consults. The two inheritance edges at the bottom are the trap for readers: in 9.1_v and 9.1_vi the interface is still named VehicleRepository, but it no longer declares the five methods above — it extends MongoRepository<Vehicle, String> (or the reactive flavour) and adds only Vehicle findByVehicleNo(String vehicleNo), resolved by the derived-query parser from the method name.

Reading the round trip. Hop 1 is ordinary getBean wiring; nothing about MongoDB is special until hop 2, where the repository hands the object to the template rather than a document. The MappingMongoConverter hop is where id is read as the _id property and the remaining record components become fields; because records are immutable, conversion on read goes through the canonical constructor, which is precisely why Vehicle had to grow an id parameter at 9.1.iii — a four-argument record could not receive it back. The filter in hop 6 comes from Criteria.where("vehicleNo").is(vehicleNo), so the property name in the Java class and the field name in the document are the same string with no mapping layer between them, and no index exists to serve it. The last two hops are the Spring mechanism, not the store: AnnotationConfigApplicationContext.close() invokes @PreDestroy on the repository bean, and that callback runs mongo.execute(db -> { db.drop(); return null; }) — so a failed Main still leaves vehicledb gone.

Recipe 9.2

Redis: a hash used as a collection

Redis has no documents, so the chapter models the collection as one hash keyed vehicles whose fields are vehicleNo to serialised value. That single decision explains the whole 9.2 series: count() is HLEN (jedis.hkeys(DB_NAME).size() in 9.2.iii/iv, redis.opsForHash().size(DB_NAME) from 9.2.v), findAll() is a cursor over the hash (jedis.hkeys(...).stream().map(this::findByVehicleNo) in 9.2.iii/iv, opsForHash().scan(DB_NAME, ScanOptions.NONE) from 9.2.v), and what changes between the variants is only how the value becomes bytes: JDK serialisation into binary keys in 9.2.iii, ObjectMapper into String keys in 9.2.iv, the template's default JdkSerializationRedisSerializer in 9.2.v, an explicit GenericJackson2JsonRedisSerializer in 9.2.vi, and finally the repository abstraction in 9.2.vii where @RedisHash("vehicles") plus @Indexed replace the hand-written hash name entirely.

Reading the wiring. Three different dependency edges mean three different answers to "who writes the bytes". In 9.2.iii the repository calls SerializationUtils.serialize(vehicle) itself and hands raw arrays to jedis.hset(byte[], byte[], byte[]) — which is why that module's Vehicle record declares implements Serializable. In 9.2.iv the repository instead injects an ObjectMapper bean and stores a JSON String under a String field. From 9.2.v the repository touches no serializer at all: RedisTemplate applies one per key space, and because RedisConfig there configures only the connection factory, the template falls back to JDK serialisation — again requiring the Serializable marker. 9.2.vi is the one-line diff template.setDefaultSerializer(new GenericJackson2JsonRedisSerializer()) plus setEnableTransactionSupport(true), the latter binding a single connection to the thread so the hash writes can be batched. The bottom-right edge is the real ODM step: 9.2_vii's record is @RedisHash("vehicles") with @Id String id and @Indexed String vehicleNo, and the convenience constructor fills UUID.randomUUID().toString(), so findByVehicleNo is served from an index instead of a scan.

Reading the calls. opsForHash() is the pivot: it returns a HashOperations view that inherits the template's key, hash-key and value serializers, which is why the repository source in 9.2.v and 9.2.vi is character for character identical while the bytes on the server differ. The getConnection hop is the part that changes behaviour under load: with setEnableTransactionSupport(true) the connection is bound to the thread, so HSET commands queue in MULTI/EXEC rather than each opening its own connection. The cast in the second to last hop ((Vehicle) redis.opsForHash().get(...)) is the honest cost of that design: the template's value type is Vehicle but HashOperations is untyped on values, and in 9.2.vi the type is recovered from the @class marker that GenericJackson2JsonRedisSerializer writes. Note also that count() and findAll() are served from the same hash, so two runs of the same recipe against one Redis give a non-zero starting count until @PreDestroy cleanUp() deletes the fields.

Recipe 9.3

Neo4j: nodes, relationships, transactions

This is the only group with a second domain model, and the only one where the mapping is not one object per structure. Character has a name property, a generated id, a Planet location, a Character apprentice and a list of friends — four properties plus three edges. Recipes 9.3.iii and 9.3.iv write those edges as literal Cypher held in static final String constants (CREATE (a)-[r:FRIENDS_WITH]->(b) style), and deduplicate nodes by checking if (charr.getId() != null) return charr; before creating, then writing the id back from res.single().get(0).asString() — a hand-rolled unit of work. From 9.3.v the same graph is declared with @Node, @Id, @GeneratedValue(UUIDStringGenerator.class) and @Relationship(type = "LOCATION") and Neo4jTemplate.save generates the statements.

Reading the mapping. The four edges out of Character are the entity graph, and each has an exact store-side counterpart: @Relationship(type = "LOCATION") on the location field, @Relationship(type = "MASTER_OF") on apprentice, and @Relationship(type = "FRIENDS_WITH") on the friends list — which also carries @AccessType(AccessType.Type.FIELD) because the only setter is addFriend and Spring Data must write the list field rather than look for setFriends (9.3.vi is the one module that adds a package-private setFriends(Iterable); 9.3.v, vii and viii rely on field access). The transaction edge is the other real difference from Mongo and Couchbase here: Neo4jTransactionManager.with(driver).build() plus @EnableTransactionManagement mean the @Transactional proxy on Neo4jStarwarsRepository (9.3.v) and on Neo4jStarwarsService (9.3.vi–viii) opens one session and reuses it, so saving Yoda writes the character node, the planet link, the friend links and the apprentice link in a single executeWrite unit. In 9.3.iii and 9.3.iv that atomicity is manual and imperfect: save(Planet) opens its own db.session() inside the surrounding writeTransaction, so a cascade can span two sessions.

Reading the graph. Four Character nodes and three Planet nodes, seven edges, and every edge is the object call made in Main: yoda.setApprentice(luke) is the only reason a MASTER_OF edge exists, luke.addFriend(han) and luke.addFriend(leia) give the two FRIENDS_WITH edges out of Luke, and leia.addFriend(han) points at the same Han node rather than a copy. Han has no outgoing edge because new Character("Han Solo") never sets a location, an apprentice or a friend — a null reference in Java simply produces no edge in the store, which is the cheapest illustration of schemalessness in the chapter. Direction matters: in 9.3_v+ the mapping metadata is directional too, so reading Yoda back loads Luke as apprentice but reading Luke does not load Yoda as master.

Recipe 9.4

Couchbase: the document id as the only key

Couchbase is the most KV-flavoured of the four. The Vehicle record is annotated @Id String vehicleNo, so the record component is the document key and there is no generated id anywhere in the group — save is an upsert by key (bucket.defaultCollection().upsert(vehicle.vehicleNo(), vehicle) in 9.4.i/ii, couchbase.upsertById(Vehicle.class).one(vehicle) from 9.4.iii), and the read is a get by key whose payload is decoded by .contentAs(Vehicle.class) or by the template's MappingCouchbaseConverter. Because nothing in the group needs a query, no N1QL statement and no index definition appears anywhere in the 9.4 modules — which is why the repository in 9.4.v is a bare CrudRepository with no finder method, unlike 9.1.v's findByVehicleNo.

Reading the generations. The top path ( CouchbaseVehicleRepository to Bucket to Collection) is 9.4.i and 9.4.ii: the SDK's KV API, with the object-to-JSON step done by the client's own encoder. The middle path is 9.4.iii and 9.4.iv, where the repository never sees a Bucket: it asks the template for a fluent operation scoped to a type (findById(Vehicle.class).one(vehicleNo)), and the returned builder executes when you call one. The configuration inheritance edge at the bottom is the diff between those two modules — 9.4.iii writes five @Bean methods by hand, 9.4.iv overrides four getters and lets AbstractCouchbaseConfiguration build the client factory, converter and template for it. Two source facts worth knowing before you run this group: 9.4_v returns null from getUserName() and getPassword(), which will not authenticate against a normal Couchbase Server, and 9.4_iii additionally carries a stray src/main/java/Vehicle.java in the default package that duplicates the mapped record.

Rung 6

The reactive variants

Exactly one module per store is reactive — 9.1.vi, 9.2.viii, 9.3.viii and 9.4.vi — and in each case the change is the same three things at once: the client jar (mongodb-driver-reactivestreams, lettuce-core), the abstract configuration class (AbstractReactiveMongoConfiguration, AbstractReactiveNeo4jConfig) or reactive connection factory, and the repository interface (ReactiveMongoRepository, ReactiveCrudRepository, ReactiveCouchbaseRepository, or a hand-written repository returning Mono/Flux as in 9.2.viii). Because main returns before the publisher completes, all four reactive Main classes end in countDownLatch.await().

Reading the chains. Nothing is executed while the chain is being built — repository.count() in recipe_9_1_vi returns a cold Mono, and only the terminal subscribe() opens the cursor; that is also why the print callbacks hang off doOnSuccess rather than being ordinary System.out statements. Two ordering choices in the source are deliberate: 9.1.vi inserts last() after saveAll to collapse the write flux to a single completion signal before counting again, and 9.3.viii uses concatMap for characters but flatMap for planets, so the four character saves — each of which cascades relationships through @Relationship metadata — are ordered rather than interleaved. The cleanup semantics diverge, and the reactive ones are the weakest: 9.4.vi hands Flux.just("TEM0001", "TEM00004") to deleteById, and the second key does not exist (it is a typo for TEM0004), so that document stays in the bucket; in 9.3.viii deleteAll() is also annotated @PreDestroy but returns a Mono, which the lifecycle infrastructure would call without subscribing — the graph is only cleaned because Main puts service.deleteAll() in the chain itself.

Building and running

./gradlew :ch09:recipe_9_1_i:build          # compile and jar one recipe

Use -cp plus the class name rather than -jar: the Main-Class manifest entry set in ch09/build.gradle belongs to the plain jar task, not to uberJar.

Cluster.connect("couchbase://127.0.0.1", "s6r-user", "s6r-password") (9.4.i–iii), the same four values as overrides of AbstractCouchbaseConfiguration (9.4.iv, 9.4.vi), and SimpleCouchbaseClientFactory(cluster, "vehicles", null) where the null scope means the default scope. 9.4.i–iv remove the two documents they wrote (TEM0001, TEM0004); 9.4.v calls deleteById for both. 9.4.vi leaves TEM0004 in the bucket because its delete list contains the misspelled key TEM00004.

Running without a server at all

9.2.i and 9.2.ii are the only modules that use no Spring Data type, but they still open a socket to Redis in their first statement, so nothing in Chapter 9 degrades to an in-memory substitute. If you cannot start a store, read the 9.1 group as the reference implementation — the template, metadata and repository mechanisms it demonstrates are the same ones the other three groups re-use.
